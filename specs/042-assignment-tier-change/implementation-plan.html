Assignment Tier Change

A colleague asked for a tier upgrade on a licence they already hold, and approving that request fails outright. This spec makes a tier change on an active assignment an approvable, race-safe, auditable operation — and fixes two live bugs found in its blast radius along the way. It adds no new table and no migration: the mechanics already exist, scattered and unreconciled.

Drafted 2026-08-03 · revised same day after a 5-lens adversarial panel (2 blocking + 4 major findings adopted; scope cut by roughly half) · author: T. Studer · branch 042-assignment-tier-change · builds on specs 003, 032-v2, 037 · estimate: ~1.5 dev days

The reported blocker. Approving a licence request for someone who already holds that tool fails: “Requester already has an active assignment for this tool (assignment #N). Revoke the existing assignment first, or cancel this request.” (src/actions/license-requests.ts:274-278).
A latent transaction hazard, corrected. In Drizzle a value returned from the transaction callback commits — only a throw rolls back, which is why the race guard at license-requests.ts:371 throws RACE_LOST. The duplicate-seat refusal was returned, so on the face of it any writes already made in that transaction would have been committed alongside a failed approval.

It was not actually reachable, and an earlier draft of this plan wrongly claimed it leaked a Hub user. Traced properly: ensureRequesterUser (:283-295) inserts a user only when no row with that e-mail exists, and a brand-new user cannot already hold an active assignment — so the duplicate-seat refusal can never co-occur with a user insert. In the original code that refusal was the only in-transaction error return, so nothing was ever orphaned.

The discipline still has to change, because this spec adds in-transaction rejections that come after a real write (a retier that then loses the request-status race). Every in-transaction rejection now throws (§5) — hardening, not a bug fix.

1 · Goal & scope

In scope

  • Licence-request approval gains three modes (§5), as a discriminated union so create-only validation never runs on a retier: create (today), change_tier (retier the seat they already hold), link_existing (record that the seat was provisioned vendor-side; approve and link, mutate nothing).
  • updateAssignment’s existing tier branch made race-safe: a conditional UPDATE guarded on status and the observed tier_id, with a zero-rows sentinel — the pattern license-requests.ts already uses.
  • One small pure helper shared by the two real call sites (updateAssignment and approveRequest) that validates the target tier and builds the update values + audit change map.
  • One live bug fixed (plus the transaction hardening above): the unguarded tier <Select> on /assignments/[id] that lets an admin “change” a Copilot seat the next cron silently reverts (§6).
  • loadToolAndTier gains the missing access_tiers.is_active check — today the request path can put a live seat on a deactivated tier, which both other entry points forbid.
  • A tier timeline read from change_history on the assignment detail page — “Standard Seat → Premium Seat, 3 Aug 2026 by T. Studer”. No new column.
  • A unit test asserting the period-overlap double-count invariant — because integration tests do not run in CI (.github/workflows/ci.yml:96-117, commented out), a unit test is the only automated guard that can gate a merge.
  • Delete the dead getExpectedSpendForPeriod (zero callers repo-wide).

Cut from v1 after the challenge pass

  • A separate changeAssignmentTier action. updateAssignment already implements same-tool tier changes with validation, cost snapshot and audit diff, and is already wired to two of the three target surfaces. A second action would have been a parallel implementation of the thing this spec exists to unify.
  • A ChangeTierDialog on three surfaces. Two already have working tier-edit UI. Only the missing affordance is added.
  • Migration 0030 / tier_changed_at. change_history already stores old/new tierId with actor and timestamp — a column would have duplicated it and could hold only the most recent step. This spec is now migration-free.
  • Deferral “reconcile the two rival expected-spend readers”. There is no rivalry: getExpectedSpendForPeriod is dead code. Deleted instead of documented.

Out of scope

  • Mid-period proration and scheduled/effective-dated changes — both need effective-dated cost history (deferral D-1).
  • Self-service upgrades for viewers; e-mail notification on tier change.

3 · The costing decision (revised)

Per-period expected spend sums cost_at_assignment_cents by date overlap, flat monthly price, no proration: 

// src/actions/budget.ts:620-626 — getBudgetWithCosts (no status filter)
.filter((a) => a.assignedAt <= periodEnd &&
               (a.revokedAt === null || a.revokedAt >= periodStart))
.reduce((total, a) => total + a.costAtAssignmentCents, 0)

// src/actions/reports.ts:146-161 — fetchPerToolByPeriod, same but `>`
v1 of this plan claimed deactivate+insert was “strictly worse”. That was arithmetically false and the panel proved it. Both options are wrong; they are wrong in different places and by different magnitudes.

The actual arithmetic

One Claude seat held since March, upgraded €25 → €125 on 15 August, monthly periods:

OptionErrorWhere it lands
Deactivate + insert 1 period × old price = +€25, August only Both rows satisfy both predicates for the period containing the switch. Verified contained: July excludes the new row, September excludes the old one.
In-place (D-A) N closed periods × delta = +€100 × Mar–Jul = +€500 Every closed period the row spans restates upward. 20× larger here, and it grows with tenure.

The retroactive blast radius (v1 never enumerated this)

In-place re-pricing moves these already-published figures:

  • The budget-health status pill — budget-health-hero.tsx:137 accumulates closedExpected over closed periods, :169-170 derive closedVariance and ratio = closedActual / closedExpected. Ten upgraded seats can flip the pill to “Under” — reporting an under-spend that never happened. Rendered on /budget and /budget/[id].
  • period-allocations-table.tsx:97,126 · past-month-spotlight.tsx:36
  • Expected-monthly sparklines: dashboard.ts:221-224 · reports/page.tsx:119-122
  • Per-tool YTD: reports.ts:255-262 · MCP get_budget_report: mcp/data.ts:320
  • Month-over-month goes blind. getAssignmentSnapshotAt reconstructs an “as of” snapshot but reads the current cost, so both months read the new price and the delta contribution is exactly zero: the “Expected monthly / vs €X last month” KPI reads 0% on the very month a seat's price quintupled. Deactivate+insert would be correct here — this regression is specific to in-place.

Decision D-A (kept, on honest grounds)

In-place mutation stays — not because its error is smaller, but because:

  • It is the convention this codebase already committed to. src/actions/tools.ts:302-305 states it in a comment and migration 0024 backfilled production to match: active assignments follow the current tier price; only revoked rows keep a historical snapshot. Spec 037 shipped that with the user’s agreement. A feature whose purpose is to reconcile three rival tier-change semantics must not introduce a fourth costing model.
  • The double count corrupts the current month — the figure people act on now — whereas restatement moves closed history that the billed-cost column still anchors.
  • Preserves row identity: id, comment thread, api_key_encrypted, workspace, assigned_at (the seat’s true start) and the license_requests.assignment_id link.
  • Immune to the T00:00:00Z vs period-boundary timezone trap a fresh insert hits (license-requests.ts:291 builds a UTC-midnight date; periodEnd is new Date('YYYY-MM-DD')).
  • Accepted cost: closed periods restate, and MoM goes blind for that seat. Disclosed in the UI, not hidden — see §7.
The option nobody considered, recorded for the successor spec. Boundary-snapped supersede: close the old row at periodStart - 1ms and open the new one at periodStart. It double-counts under neither predicate and leaves closed periods at their historical price — the only option here that is cost-correct on every reader, MoM included. Rejected for v1 because it still breaks row/comment/API-key continuity and makes assigned_at lie about when the seat began, which would need a supersedes_assignment_id chain to repair. Deferral D-1.

4 · The tier-change path

No new action. updateAssignment stays the entry point; its tier branch is hardened and factored so the request path can share it.

The shared pure helper — one signature, settled

// src/actions/assignments.ts — pure, no db access, no tx.
// v1 gave two conflicting signatures; this is the only one.
export function buildTierChange(
  current: { tierId: number; costAtAssignmentCents: number; source: string },
  newTier: { id: number; monthlyCostCents: number },
): { values: TierChangeValues; changes: ChangeMap }
  | { noop: true }
  | { error: string }
  • newTier.id === current.tierId → { noop: true }. Callers decide what a no-op means — updateAssignment skips the write; approveRequest must still approve and link the request (v1 would have stranded it in pending_review).
  • current.source === 'copilot-sync' → error. Reached only when the tier actually differs — v1’s invariant ordering would have rejected every edit of a synced assignment, because the detail form always submits tierId.
  • Otherwise returns tierId, costAtAssignmentCents and the old/new change map for recordUpdate.

Race-safe write

The existing write is an unconditional .where(eq(id, id)) after a separate read (assignments.ts:191-201 read, :297-300 write). Five concurrent producers can close the row inside that window: revokeLicense, assignLicense’s deactivate leg, deactivateUser’s bulk revoke (users.ts:197-207) and copilot-sync’s removed-seat revoke. Retiering a just-revoked row would violate the very invariant D-A rests on. 

.where(and(
   eq(licenseAssignments.id, id),
   eq(licenseAssignments.status, "active"),
   eq(licenseAssignments.tierId, observedTierId),   // optimistic lock
   ne(licenseAssignments.source, "copilot-sync"),
 ))
 .returning({ id: licenseAssignments.id });

if (updated.length === 0) return { success: false,
  error: "This assignment changed while you were editing it. Refresh and try again." };

The tierId predicate doubles as the optimistic lock against a concurrent price cascade (updateTier / syncBillingData) stranding the row at a stale price.

Audit durability

recordUpdate is written after the update, matching the prevailing convention. If it throws, the tier moved with no history row — and the no-op early return would then make a retry report success, falsifying the audit acceptance criterion. Mitigation: write history inside the same transaction as the update for this path, so either both land or neither does. This is the stricter of the two conventions already present in the repo, and correctness wins here.

Revalidation

Today’s list (assignments.ts:310-312) misses every cost surface. Corrected for all updateAssignment fields, not just the tier — matching what the analogous price cascade in tools.ts already does: /assignments, /assignments/[id], /users/[userId], /tools/[toolId], /reports, /reports/budget, /budget, /.

No maxLicenses check — a same-tool tier change does not alter the seat count. Stated explicitly because GitHub Copilot is live at 63/63: any create-shaped implementation that omitted assignLicense’s “minus one for the user’s own row” adjustment (assignments.ts:73-88) would reject every Copilot upgrade.

5 · Licence-request approval modes

A flat mode flag cannot work. loadToolAndTier runs before the transaction (:338 vs :341) and unconditionally errors when tool.requiresApiKey && !licenseCode?.trim() (:201-207). Claude Console is the only requires_api_key tool and has the deepest tier ladder — so v1, which suppressed the key field on a retier, would have killed exactly the upgrades most likely to happen, with a misleading error.

A discriminated union, not a flag

approveRequestSchema = z.discriminatedUnion("mode", [
  z.object({ mode: z.literal("create"),        /* tool, tier, assignedAt, licenseCode, bodyMd */ }),
  z.object({ mode: z.literal("change_tier"),   /* assignmentId, tierId, bodyMd — NO assignedAt */ }),
  z.object({ mode: z.literal("link_existing"), /* assignmentId, bodyMd */ }),
]);

Create-only validation (the API-key rule, assignedAt) now lives only on the create member, so it cannot fire on the other two. mode is destructured out before anything is passed to loadToolAndTier.

modeExisting active assignmentOutcome
createnoInsert, as today.
createyesToday’s error, with updated advice (retier instead of revoke) — and now thrown, so the transaction rolls back.
change_tieryes, manualnew retier via buildTierChange; link assignment_id; approve.
change_tieryes, same tierNo-op on the row, but still approve and link.
change_tiernoThrow to roll back: “No active assignment to retier.”
link_existingyesnew mutate nothing; link assignment_id; approve. The answer for Copilot (§6).
Every in-transaction rejection must throw, never return. This is the single most important implementation note in the spec: a returned error commits the auto-created requester user. Use a sentinel per the existing RACE_LOST idiom and map it to a friendly message in the .catch.

Data the dialog actually needs

v1 claimed the collision could be detected “with no new query”. Half true: getRequestContext does return activeAssignments, but ActiveAssignmentSummary is { id, toolName, tierName, assignedAt } (:583-588, SQL at :618-625) — no toolId (so collision matching would key off a display name), no tierId, and no source (so it cannot tell a Copilot seat from a manual one). Add tool_id, tier_id and source to that SELECT — same query, three more columns.

Collision detection must key off toolId, and note that the dialog keys on requesterUserId while the transaction resolves the requester by e-mail: a request whose requesterUserId is NULL but whose e-mail already matches a Hub user shows no collision in the dialog yet collides server-side. The server’s mode revalidation is therefore the authority, and its error message must tell the admin to reopen the dialog.

Template context

renderTemplate leaves an unresolved path as the literal {{tier.previousName}} in the output — it does not render empty. Templates are keyed only by (tool_id, tier_id, kind) with no tier-change kind, so the same approval body serves all three modes. Therefore tier.previousName is always bound — the previous tier name on a retier, an empty string otherwise — so a template that references it can never leak braces into a message an admin pastes to a colleague.

Also: in change_tier/link_existing mode the key field is optional, not suppressed. Suppressing it made resolvedBody() substitute the empty string into the seeded Claude Console line Your API key: {{licenseCode}}, so the pasted message read “Your API key: —”.

6 · Copilot sync authority

syncSeatAssignments rewrites tier_id, cost_at_assignment_cents, source and workspace from GitHub’s seat.plan_type with no history entry (copilot-sync.ts:243-262). GitHub owns the entitlement; the Hub cannot win that argument.

Live bug. assignment-detail-client.tsx contains zero references to source and its page.tsx never passes it, so the tier <Select> there is fully editable for synced rows — [SAVED], then silently reverted by cron. Only assignments-client.tsx gates.
Blocking source='copilot-sync' is necessary but not sufficient. Sync takes over manual rows (needsSourceUpdate, copilot-sync.ts:243), so a tier change on a source='manual' GitHub Copilot assignment is equally reverted at the next cron — the same bug reached through a different value. The honest gate is therefore tool-based, not source-based: refuse tier changes on any assignment whose tool is the Copilot-sync-managed tool while a Copilot connection is active. Implemented as a single predicate so both the server guard and the UI gate read the same rule.

This is why link_existing exists. Without it, a Business → Enterprise request — the clearest upgrade ladder in the system, on the tool with 63 live seats — has no approvable outcome at all: refused by the create guard and by the sync guard. With it, the flow matches 032-v2’s provision-first philosophy: the admin upgrades the plan in GitHub, approves the request as link_existing, and the tier arrives on the next sync. The dialog says exactly that.

Noted, not fixed (deferral D-5): sync’s needsReactivate branch resets assigned_at = new Date() and revoked_at = null, destroying a resurrected seat’s original start date and corrupting its period attribution.

8 · Test plan

Integration tests do not run in CI — .github/workflows/ci.yml:96-117 has the integration-tests job commented out; only pnpm test (unit) gates a merge. v1 made an integration test the sole guard for its central claim, which would never have blocked a regression. The double-count guard is therefore a unit test.

Unit — the regression guard

  • Extract the overlap predicate used by getBudgetWithCosts into a pure exported function and test it directly: given one in-place-changed row vs. an old+new row pair spanning the same switch, assert the in-place result equals exactly one tier price and the pair sums to two — pinning the double-count as a known property of the rejected design, in CI, forever.
  • buildTierChange: no-op, sync refusal only when the tier differs, correct change map, signed delta both directions incl. Claude Console’s non-monotonic prices.
  • Non-admin → Unauthorized; inactive assignment refused; cross-tool tier refused; inactive tier refused on all three entry points (the loadToolAndTier gap).
  • Race guard: zero-rows update → the refresh error, not a silent success.
  • Mode matrix from §5, including that change_tier with no active assignment throws (asserting the user rolls back) and that same-tier still approves.

Integration — real DB, manual gate

  • Scoped, not global. getBudgetWithCosts sums the entire license_assignments table with no tool or budget scoping, so a global before/after delta absorbs rows other suites create concurrently. Assert instead on the seeded tool’s own rows: exactly one active row, and the predicate-matching sum equals the new tier price alone.
  • No active budget needed — getBudgetWithCosts filters on id only (budget.ts:556-557) and ignores status. Seed it archived, outside every claimed fiscal-year range. v1’s “claim FY ≥ 999,000” instruction would have collided with the suite that already owns that window.
  • Approval round trip: change_tier retiers in place, preserves id/assigned_at/API key, links the request; a failed create commits nothing at all.
  • Seeds its own tool/tiers/user — seed.ts creates only an admin.

Browser pass (Playwright via agent-browser-session)

  • Change a tier on a manual assignment; assert the new tier, the timeline entry, [SAVED].
  • A sync-managed assignment offers no tier edit on the detail page (bug fix).
  • Approve a request for an existing holder — manual (change tier) and Copilot (link existing).
  • Use page.innerText("body"), not textContent (RSC flight payload); allow ~17s for the first page.goto.

10 · Decisions, deferrals & risks

#Decision
D-AIn-place mutation — on the honest grounds in §3, not the false “strictly worse” claim of v1. Accepts closed-period restatement and MoM blindness.
D-BTier changes refused for Copilot-sync-managed assignments by tool, not by source — because sync takes over manual rows too.
D-CThree approval modes as a discriminated union. link_existing is what gives Copilot an approvable outcome. The legacy v1 path needed its own linkExistingAssignment action instead — approveRequest requires pending_review while those rows are already approved.
D-DNo maxLicenses check — seat count unchanged; explicit because Copilot is at 63/63.
D-ENo migration. change_history is the tier timeline.
D-FTier-change history written inside the transaction — the stricter of the repo’s two conventions, chosen because the audit trail is an acceptance criterion.
#DeferredWhy not now
D-1Effective-dated cost history — enables proration, scheduling, and boundary-snapped supersede (§3)New table + supersedes_assignment_id chain + rewriting four per-period readers. The right long-term answer.
D-2Restore MoM correctness after an in-place changeNeeds D-1. Until then the KPI under-reports the month a tier moves.
D-3Tier drift vs tool_mappingsNeeds a product rule for what drift means.
D-4Partial unique index on one active assignment per user+toolSync can transiently produce duplicates; the constraint could break cron.
D-5Sync’s needsReactivate resetting assigned_atReal defect, unrelated blast radius.

Risks

  • Claude Console tiers are entitlement caps, not seat fees — its cost is a monthly allowance while real spend arrives as metered Anthropic usage. The dialog’s delta copy must say “monthly tier cost”, never imply the bill changes.
  • Closed-period restatement is invisible from /budget, where the affected pill lives. Mitigation is disclosure at the point of change plus the change_history timeline; a real fix needs D-1.
  • Four write sites still touch license_assignments directly. This spec unifies the tier path and adds no fifth, but does not unify them.

11 · Acceptance checklist

  • A request from someone who already holds the tool can be approved — as a tier change (manual) or a linked existing seat (sync-managed) — without revoking anything.
  • A failed approval commits nothing — no partial retier, no orphan user (regression-tested).
  • A sync-managed assignment offers no tier edit on any surface, including the detail page (live-bug fix).
  • After a tier change: one active row, same id, same assigned_at, comments and API key intact, timeline entry visible.
  • A concurrent revoke during a tier change yields the refresh error, never a retiered revoked row.
  • No approval path can put a live seat on a deactivated tier.
  • The double-count property is pinned by a unit test that runs in CI.
  • A pasted approval message never contains literal {{…}} braces or an em-dash API key.
  • pnpm typecheck clean · eslint clean on changed files · pnpm test green · integration green locally · browser pass done.
