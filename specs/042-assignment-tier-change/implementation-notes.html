Assignment Tier Change — running log

Design decisions, deviations, tradeoffs, open questions, and the challenge / simplify / review / verification passes for spec 042. Appended as work proceeds. Companion to implementation-plan.html.

Started 2026-08-03 · branch 042-assignment-tier-change · author: T. Studer

The trigger

A tier-upgrade request arrived for a licence someone already held, and the Hub had no way to action it. Reconnaissance established that this is not one missing feature but three unreconciled implementations of the same operation — see plan §2.

The hard block

createAssignmentInTx (src/actions/license-requests.ts:266-278) refuses approval whenever the requester already holds an active assignment for the tool, and recommends revoke-then-recreate — which routes the admin into the worst of the three existing paths (orphaned comments, reset assigned_at, dropped API key, double-billed switch month).

Reconnaissance method

A dynamic workflow ran 7 parallel read-only explorers (assignment mutation layer · cost-snapshot semantics · licence-request workflow · UI surfaces · audit/history · tests & doc process · MCP and API read surfaces) followed by a gap critic that was allowed to read files itself to resolve contradictions between the reports. 8 agents, ~873k subagent tokens, ~13 min wall clock.

Open question at drafting time

Unanswered when the plan was drafted. Two questions were put to the user and went unanswered (away from keyboard), so the plan proceeds on stated assumptions rather than blocking:
  • Which surface blocked them. Assumed: the licence request, since the trigger was described as a request arriving. The plan therefore covers both the direct admin operation and the request-approval path, so the assumption being wrong costs nothing.
  • Upgrade-month costing. Assumed D-A (whole month at the new tier). Rationale in plan §3: it is the convention spec 037 already established and the user already accepted. If the user wants true proration, that is deferral D-1 and a materially larger spec — the plan says so explicitly rather than quietly choosing for them.
Both should be confirmed before merge.

Challenge pass

Five adversarial lenses ran in parallel against plan v1, each told to assume the plan was wrong and prove it against the real code: cost & reporting correctness, concurrency & data integrity, licence-request flow correctness, codebase fit / simplification, test adequacy & process. 5 agents, ~715k tokens, ~11 min.

Verdicts: 2 × has_blocking_flaw (concurrency, request-flow) · 3 × needs_revision (cost, simplification, tests). Nothing returned plan_is_sound. Every blocking and major finding below was verified independently against the code before being adopted.

The panel proved the plan’s central argument wrong. v1 §3 asserted deactivate+insert was “strictly worse” than in-place mutation. It is not. Double-count = 1 period × old price. In-place restatement = N closed periods × delta — for one Claude seat held since March, +€25 versus +€500. The decision (in-place) survived; the reasoning had to be replaced entirely, and the retroactive blast radius enumerated by file.

Blocking findings adopted

FindingVerifiedRevision
A flat mode flag cannot express change_tier: loadToolAndTier runs before the transaction and unconditionally errors on requiresApiKey && !licenseCode. v1 suppressed the key field on a retier → every Claude Console upgrade would die with a misleading message, and Claude Console is the only requires_api_key tool and has the deepest tier ladder. Confirmed: license-requests.ts:201-207, called at :338, transaction opens at :341. approveRequestSchema becomes a discriminated union; create-only validation lives only on the create member. Key field becomes optional, not suppressed.
Returning an error from inside the approval transaction commits it — so v1’s new in-transaction rejection would have persisted an auto-created requester user. Confirmed: the existing race guard throws RACE_LOST (:371) precisely because a return would commit. Every in-transaction rejection must throw. Called out as the single most important implementation note.
The tier UPDATE has no status guard, so it can retier a row a concurrent revoke just closed — violating the very invariant D-A’s costing argument rests on. Confirmed: unconditional .where(eq(id, id)) at assignments.ts:297-300 after a separate read at :191-201. Five concurrent producers can close the row. Conditional UPDATE guarded on status + observed tier_id (doubling as an optimistic lock against the price cascade) with a zero-rows sentinel.

Live bug the panel surfaced, beyond the plan’s scope

Because a returned error commits, and ensureRequesterUser runs before createAssignmentInTx, today’s “Requester already has an active assignment” refusal leaks a Hub user whenever the requester was not yet in the Hub — a viewer account created and abandoned while the request stays pending_review. That is the exact error path this spec was opened to fix, so the leak is squarely in the blast radius. Fixed by the throw-not-return revision; regression-tested.

Major findings adopted

  • Copilot had no approvable outcome at all. All 63 live Copilot seats are source='copilot-sync', so a Business → Enterprise request would be refused by the create guard and by D-B’s sync block — while v1’s acceptance checklist claimed such requests were approvable. Added a third mode, link_existing, matching 032-v2’s provision-first philosophy: upgrade in GitHub, approve as linked, tier arrives via sync. It also unsticks the legacy recordAssignment path, which shared the same dead end.
  • Blocking by source is the wrong gate. Sync takes over manual rows (needsSourceUpdate), so a tier change on a source='manual' Copilot assignment is reverted just the same. The gate became tool-based.
  • loadToolAndTier never checks is_active — so v1’s §5 callout (“all three require isActive, exactly as today”) was simply false, and the request path could put a live seat on a deactivated tier. Gap closed.
  • Month-over-month goes blind. getAssignmentSnapshotAt reads the current cost, so after an in-place change both compared months read the new price and the delta contribution is exactly zero — the KPI reads 0% on the month a seat’s price quintupled. A regression specific to in-place; recorded as deferral D-2 rather than hidden.
  • The helper’s invariant ordering broke every synced-row edit. The detail form always submits tierId, so refusing sync rows before the no-op check would reject workspace and API-key edits too. Sync refusal now fires only when the tier actually differs.
  • v1 gave the shared helper two different signatures (§1 applyTierChangeInTx vs §5 buildTierChange), which would have blocked writing the unit tests. Settled on one pure, db-free signature.
  • Revalidation still missed cost surfaces. v1 congratulated itself on adding /budget but omitted / and /reports/budget, which the analogous price cascade already revalidates. Fixed for all updateAssignment fields, not just the tier.
  • The dialog cannot do what v1 promised “with no new query”. ActiveAssignmentSummary lacks toolId, tierId and source, so collision matching would have keyed off a display name and could not distinguish a synced seat. Three columns added to the existing SELECT.
  • tier.previousName would have leaked braces. renderTemplate leaves unresolved paths as the literal {{tier.previousName}}, and one approval body serves all modes — so the token is now always bound (empty when not a retier). Relatedly, suppressing the key field made the pasted message read “Your API key: —”.
  • Same-tool/same-tier was an unhandled cell. A naive copy of updateAssignment’s zero-diff early return would report success while stranding the request in pending_review. The no-op contract now explicitly belongs to the caller.

Test-plan corrections

  • Integration tests do not run in CI. .github/workflows/ci.yml:96-117 has the integration-tests job commented out — only pnpm test gates a merge. v1 made an integration test the sole guard for its central claim, so a future “just reuse assignLicense” refactor could have reintroduced double-counting with nothing blocking it. The guard is now a unit test over an extracted overlap predicate.
  • The integration test was racy and mis-scoped. getBudgetWithCosts sums the whole license_assignments table with no tool or budget scoping, so a global before/after delta absorbs other suites’ concurrent rows. Now asserts on the seeded tool’s own rows.
  • v1’s fiscal-year instruction was actively harmful. It told the test to claim FY ≥ 999,000 — the window forecast-scenarios.test.ts already owns. And it was unnecessary: getBudgetWithCosts filters on id only (budget.ts:556-557) and ignores status, so the budget can be seeded archived outside every claimed range.

Confirmed correct — left alone

Recorded so a later reader does not “fix” a non-issue. The double-count in both getBudgetWithCosts and fetchPerToolByPeriod is real and exactly one period wide (July excludes the new row; September excludes the old). The spec-037 precedent is real and stronger than v1 claimed — tools.ts:302-305 states it in a comment and migration 0024 backfilled production to match. No per-tier historical breakdown exists anywhere, so in-place change misreports no per-tier chart. Nothing persists a computed expected-spend figure, so no stale stored number is left behind. D-D is well-founded: assignLicense’s minus-one capacity adjustment (assignments.ts:73-88) means a create-shaped implementation really would reject every Copilot upgrade at 63/63.
