Assignment Tier Change — running log

Design decisions, deviations, tradeoffs, open questions, and the challenge / simplify / review / verification passes for spec 042. Appended as work proceeds. Companion to implementation-plan.html.

Started 2026-08-03 · branch 042-assignment-tier-change · author: T. Studer

The trigger

A tier-upgrade request arrived for a licence someone already held, and the Hub had no way to action it. Reconnaissance established that this is not one missing feature but three unreconciled implementations of the same operation — see plan §2.

The hard block

createAssignmentInTx (src/actions/license-requests.ts:266-278) refuses approval whenever the requester already holds an active assignment for the tool, and recommends revoke-then-recreate — which routes the admin into the worst of the three existing paths (orphaned comments, reset assigned_at, dropped API key, double-billed switch month).

Reconnaissance method

A dynamic workflow ran 7 parallel read-only explorers (assignment mutation layer · cost-snapshot semantics · licence-request workflow · UI surfaces · audit/history · tests & doc process · MCP and API read surfaces) followed by a gap critic that was allowed to read files itself to resolve contradictions between the reports. 8 agents, ~873k subagent tokens, ~13 min wall clock.

Challenge pass

Five adversarial lenses ran in parallel against plan v1, each told to assume the plan was wrong and prove it against the real code: cost & reporting correctness, concurrency & data integrity, licence-request flow correctness, codebase fit / simplification, test adequacy & process. 5 agents, ~715k tokens, ~11 min.

Verdicts: 2 × has_blocking_flaw (concurrency, request-flow) · 3 × needs_revision (cost, simplification, tests). Nothing returned plan_is_sound. Every blocking and major finding below was verified independently against the code before being adopted.

The panel proved the plan’s central argument wrong. v1 §3 asserted deactivate+insert was “strictly worse” than in-place mutation. It is not. Double-count = 1 period × old price. In-place restatement = N closed periods × delta — for one Claude seat held since March, +€25 versus +€500. The decision (in-place) survived; the reasoning had to be replaced entirely, and the retroactive blast radius enumerated by file.

Returning an error from inside the approval transaction commits it — so v1’s new in-transaction rejection would have persisted an auto-created requester user. Confirmed: the existing race guard throws RACE_LOST (:371) precisely because a return would commit. Every in-transaction rejection must throw. The tier UPDATE has no status guard, so it can retier a row a concurrent revoke just closed — violating the very invariant D-A’s costing argument rests on. Confirmed: unconditional .where(eq(id, id)) at assignments.ts:297-300 after a separate read at :191-201. Five concurrent producers can close the row. Conditional UPDATE guarded on status + observed tier_id (doubling as an optimistic lock against the price cascade) with a zero-rows sentinel.

Correction — the “leaked Hub user” was not real

Working from the panel’s finding that a returned error commits, and that ensureRequesterUser runs before createAssignmentInTx, both the panel and plan v2 concluded that the “Requester already has an active assignment” refusal had been leaking an abandoned viewer account — and that it was doing so on the exact error path this spec was opened to fix. It was reported to the user in those terms.

That was wrong. Traced properly during implementation: ensureRequesterUser (license-requests.ts:283-295) inserts a user only when no row with that e-mail exists — it early-returns on requesterUserId, then on an e-mail match. A user who has just been inserted cannot already hold an active assignment, because assignments reference users. So the duplicate-seat refusal and a user insert are mutually exclusive, and since that refusal was the only in-transaction error return in the original code, nothing was ever orphaned.

The throw-not-return revision is kept, and is still required — but as hardening, not a bug fix. This spec adds in-transaction rejections that can follow a real write (a retier that then loses the request-status race), and for those a returned error would commit a partial change. Corrected in plan §5 and reported to the user.

Worth recording as a process note: a confident, well-cited finding from an adversarial reviewer still needs its reachability checked, not just its mechanism. The mechanism here was real; the path to it was not.

Major findings adopted

  • Copilot had no approvable outcome at all. All 63 live Copilot seats are source='copilot-sync', so a Business → Enterprise request would be refused by the create guard and by D-B’s sync block — while v1’s acceptance checklist claimed such requests were approvable. Added a third mode, link_existing, matching 032-v2’s provision-first philosophy: upgrade in GitHub, approve as linked, tier arrives via sync. It also unsticks the legacy recordAssignment path, which shared the same dead end.
  • Blocking by source is the wrong gate. Sync takes over manual rows (needsSourceUpdate), so a tier change on a source='manual' Copilot assignment is reverted just the same. The gate became tool-based.
  • loadToolAndTier never checks is_active — so v1’s §5 callout (“all three require isActive, exactly as today”) was simply false, and the request path could put a live seat on a deactivated tier. Gap closed.
  • Month-over-month goes blind. getAssignmentSnapshotAt reads the current cost, so after an in-place change both compared months read the new price and the delta contribution is exactly zero — the KPI reads 0% on the month a seat’s price quintupled. A regression specific to in-place; recorded as deferral D-2 rather than hidden.
  • The helper’s invariant ordering broke every synced-row edit. The detail form always submits tierId, so refusing sync rows before the no-op check would reject workspace and API-key edits too. Sync refusal now fires only when the tier actually differs.
  • v1 gave the shared helper two different signatures (§1 applyTierChangeInTx vs §5 buildTierChange), which would have blocked writing the unit tests. Settled on one pure, db-free signature.
  • Revalidation still missed cost surfaces. v1 congratulated itself on adding /budget but omitted / and /reports/budget, which the analogous price cascade already revalidates. Fixed for all updateAssignment fields, not just the tier.
  • The dialog cannot do what v1 promised “with no new query”. ActiveAssignmentSummary lacks toolId, tierId and source, so collision matching would have keyed off a display name and could not distinguish a synced seat. Three columns added to the existing SELECT.
  • tier.previousName would have leaked braces. renderTemplate leaves unresolved paths as the literal {{tier.previousName}}, and one approval body serves all modes — so the token is now always bound (empty when not a retier). Relatedly, suppressing the key field made the pasted message read “Your API key: —”.
  • Same-tool/same-tier was an unhandled cell. A naive copy of updateAssignment’s zero-diff early return would report success while stranding the request in pending_review. The no-op contract now explicitly belongs to the caller.

Test-plan corrections

Confirmed correct — left alone

Recorded so a later reader does not “fix” a non-issue. Deviation — the legacy path needed its own action

Plan v2 said the legacy recordAssignment dead end would be unstuck by approveRequest’s new link_existing mode. It cannot be. The delegated agent found this and stopped rather than wiring a call that would always fail — correctly.

RecordAssignmentDialog only opens for status === "approved" rows (isLegacyApproved), while approveRequest rejects anything not pending_review. The two guards are mutually exclusive, so every such call would have returned Cannot approve a request in status “approved”.

Resolved with a dedicated linkExistingAssignment action guarded on status='approved' AND assignment_id IS NULL, reusing loadTargetAssignmentInTx for the ownership and active checks and mutating nothing on the seat. The plan’s §7 row and D-C were corrected to match.

Deviation — user-detail gating is source-based

The “Change tier” affordance on the user detail page hides itself on source === 'copilot-sync' rather than via the tool-based isSyncManagedTool, because the server component feeding that card was outside the delegated agent’s file scope. Cosmetic only: the mutation stays protected server-side by the tool-based check, and the link lands on a page whose tier control is correctly disabled. Worth tidying if that page is touched again.

Two defects the integration run found that unit tests could not

This spec broke the suite’s teardown. change_history.changed_by is onDelete RESTRICT, and approving as a tier change now writes audit rows attributed to the test admin — so afterAll’s user delete failed with a 23503 FK violation on every run. Why the browser pass did not happen

@neondatabase/serverless falls back to Node’s built-in (undici) WebSocket when neonConfig.webSocketConstructor is unset, and on Node 24 that connects only intermittently — a raw ErrorEvent, then the 10s connectionTimeoutMillis in src/lib/db/index.ts aborts. Measured: with the ws package, 3/3 connections succeed; without it, failures are frequent. It is not specific to this feature — it also broke pnpm db:seed:agent and made drizzle-kit intermittent.

The integration suite was made reliable with a throwaway setupFiles shim (not committed). For pnpm dev the documented workaround — the shim in src/instrumentation.ts plus serverExternalPackages in next.config.ts — was tried temporarily and did not take effect; the mint route kept returning 500 from the same WebSocket failure, so no agent session could be created and no page could be driven. Both files were reverted; the tree is clean.

Consequence: the UI has no verification at all. The sync gate on the assignment detail page, the tier timeline, the mode-aware approval dialog and the legacy link path are covered by neither automated tests nor a manual pass. The server actions beneath them are covered. This is the largest remaining gap before merge.

Offered but not done, since it is a shared-harness change rather than part of this spec: committing the ws shim so pnpm test:integration is reliable on Node 24 for everyone. Without it, the integration results above are not reproducible on this Node version.

What the browser pass actually exercised

  • A real manual Claude seat moved Standard Seat → Premium Seat → Standard Seat — both directions, ending back on its original tier.
  • Header and cost followed the change ($25.00 ↔ $125.00); feedback arrived as inline [SAVED], not a toast.
  • The tier timeline rendered both hops from change_history, attributed and dated.
  • Database end state confirmed directly: exactly one active row for that user+tool (in place, no supersede, no duplicate), with tierId 5→6 and costAtAssignmentCents 2500→12500 written under a single timestamp — the transaction of decision D-F.
  • A real copilot-sync seat showed “Managed by sync”, its tier control disabled but still legible, and no re-pricing disclosure.
The browser pass earned its place — it found two UI bugs nothing else could. Typecheck, 659 unit tests and 56 integration tests were all green while both of these were live.
  1. The sync-managed badge crashed the whole assignment detail page (“Tooltip must be used within TooltipProvider”). The assignments table only works because DataTable happens to wrap its rows in a provider; the detail page has none. So the page rendered nothing but a heading for every sync-managed seat — exactly the case the badge exists to mark. SyncManagedBadge now owns its own provider.
  2. The tier control rendered empty on every assignment. Radix resolves a Select’s displayed value by looking up the selected item’s children, and the items arrive asynchronously from loadTiers — so the control painted blank until the list happened to be ready, and stayed blank whenever disabled. A placeholder does not help: it only shows for an empty value, and here it is a real tier id. Pre-existing, but it is this feature’s primary control.
Worth remembering next time the plan is tempted to treat a browser pass as optional: both defects were in rendering, and no amount of server-side testing would have surfaced either.

Note on reproducibility: the round-1 flakiness (@neondatabase/serverless falling back to Node’s undici WebSocket) did not recur here — the EU endpoint connects in ~200 ms where the free-tier US branch took ~7 s and brushed the 10 s connectionTimeoutMillis. The proposed ws devDependency was declined and is not in the tree; if the slow-endpoint case recurs, that is the fix.
