Spec 039 · Implementation Plan

Role-Scoped MCP Tools

Branch 039-mcp-role-scoping · builds on 038-mcp-v2 (PR #118) · 2026-06-11 · no schema changes · no new packages

§1Why

Feature 038 left one authorization question deliberately open: OAuth made MCP tokens user-bound, but every authenticated credential — viewer or admin — still reads the same org-wide spend, budget, and per-user cost data. The web UI doesn't work that way: viewers see their own profile and a utilization-free tool catalog; everything financial is admin-gated. This feature brings the MCP surface to exact parity with the web UI: an admin loses nothing, a viewer sees over MCP no more than they see in a browser.

§2Shape of the change

users.role → verifyAccessToken (existing join, +1 column) → AuthInfo.extra.role → callerFromAuthInfo → per-tool enforcement in tools.ts

Three access classes over the existing 14 tools

  • Admin-only (11) — all Claude/budget/Copilot/invoice/sync/user-directory tools. Viewer calls return a structured isError tool result naming the required role. The data function is never invoked.
  • Self-scoped (2) — get_user_cost_profile, list_license_assignments. Viewers are pinned to the token owner's identity; a foreign email is refused, never silently substituted. email on the profile tool becomes optional, defaulting to the token owner.
  • Viewer-safe catalog (1) — list_ai_tools. Viewers get the catalog without activeAssignments / maxLicenses / licenseUtilizationPct, mirroring the /tools page, which skips the license-count column for non-admins.

§3Key decisions

Live role, never frozen into the token

verifyAccessToken already inner-joins users to enforce status = 'active'; projecting users.role adds the live role to every request at zero query cost. Demoting an admin takes effect on their very next tool call — no waiting out the 60-day refresh-token window. Rejected alternative: role-scoped OAuth scopes at issuance (frozen, violates the immediacy requirement).

Enforce at invocation, not at discovery

createMcpHandler registers tools in a callback with no access to the request's AuthInfo — the advertised tool list is static. The MCP SDK passes RequestHandlerExtra.authInfo into every tool callback, so invocation is the natural, zero-cost enforcement seam. Tool names leak no data; denial messages are self-explanatory so an assistant can relay the reason.

Shared secret is explicitly admin — unknown roles are explicitly viewer

The shared-secret path returns extra: { role: "admin" } (the spec-034 org-credential judgment, unchanged). callerFromAuthInfo treats anything that isn't literally "admin" as viewer — least privilege by default, admin only by explicit assertion. The shared secret has no bound identity, so the profile tool with no email argument asks for an explicit one (matching how 034 clients always called it).

Denials are tool results, not protocol errors

Same philosophy as 038's safeJsonResult: a viewer hitting an admin tool gets isError: true with one shared message constant — the MCP session stays healthy, the client model can explain the refusal, and no org data (not even counts) rides along in the payload.

§6What deliberately does not change

  • No DB schema / migrations — users.role already exists.
  • No new packages, no route changes, no middleware changes.
  • Tool discovery — all credentials see the same 14 tools listed; only calls are gated.
  • Shared-secret behaviour on org-wide tools — byte-identical to 038.
  • OAuth flow, token rotation, revocation — untouched.

§7Risks & mitigations

RiskMitigation
A future 15th tool forgets the wrapper and ships org-wide data to viewers. Unit test asserts every registered tool is classified: the test enumerates registered names against the explicit access-class lists and fails on any unclassified tool.
Optional email on the profile tool breaks existing shared-secret automations. Backward compatible — passing an email keeps working everywhere; only the omitted case changes (error message asking for an email instead of a Zod required-field error).
Viewer denial message drifts per tool and confuses assistants. Single exported message constant; contract doc pins the exact string shape.
Role check bypassed if authInfo is absent in some transport path. withMcpAuth(..., { required: true }) already 401s unauthenticated requests; if authInfo is ever missing downstream anyway, callerFromAuthInfo yields a viewer with no identity — fail-closed.

§8Verification gates

  1. pnpm test tests/unit/mcp — new access tests + extended tool matrix green.

  3. Manual probe per quickstart.md: viewer token denied on get_budget_status, own profile works with no arguments, live demotion flips access on the next call.
  4. Full unit suite — no regression outside the MCP layer.
