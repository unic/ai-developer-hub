decisionCloses 038's open question; parity target is the web UI

The 038 notes flagged "should viewer-role tokens see org-wide per-user spend?" as an explicit open question. Answered: no. The tool-to-class mapping was derived by auditing the App Router's existing role gates rather than inventing a new policy — /users is AuthGuard requiredRole="admin" (so find_users is admin-only), /tools is viewer-visible but skips the license-count queries for non-admins (so list_ai_tools stays viewer-safe minus utilization), and every Claude/Copilot/budget/report surface redirects non-admins (so all 11 org-wide tools are admin-only).

decisionLive role via the existing verification join — zero extra queries

verifyAccessToken already inner-joins users to enforce status='active'; the role is one more projected column. No role-in-token, no caching layer, no propagation machinery: a demotion applies to the demoted user's very next tool call. The unit suite pins this with a same-handler, role-flipped-between-calls test.

decisionShared secret asserts role: "admin" explicitly; everything else defaults to viewer

callerFromAuthInfo grants admin only on the literal extra.role === "admin" — missing AuthInfo, missing extra, unknown values, malformed identity fields all collapse to viewer with no identity (fail-closed). The org secret is admin because verifyMcpToken says so, never via fallback. This keeps spec 034's shared-secret behaviour byte-identical for org-wide tools.

tradeoffStatic tool discovery; enforcement at invocation only

createMcpHandler registers tools in a callback with no request context, so all credentials see the same 14 tools listed. Accepted: tool names leak no data, and the denial message names the required role so assistants can explain the refusal. Mitigations for the "silent 15th tool" risk: the unit suite derives its expected-tool list from the union of the three access-class lists, so an unclassified new tool fails the registration test; and the 11 admin tools carry a "Requires an admin-role token." description suffix so viewer-bound assistants stop calling them speculatively.

decisionRefusal over silent substitution for self-scoped tools

A viewer asking for someone else's email gets an explicit isError refusal, not their own data relabeled — a silently-substituted answer would look like a wrong answer to the calling assistant. get_user_cost_profile.email became optional (defaults to the token owner), which is also a small UX win for admins. The shared secret has no owner, so its omitted-email case asks for an explicit address — exactly how 034-era clients always called it.

deviationNone of substance from plan.md

The implementation landed as designed (plan §3–§5). Only naming nuance: the viewer-without-identity case in resolveSelfEmail reuses SELF_ONLY_MESSAGE rather than a fourth constant — a viewer credential with no bound email cannot be helped by passing one, and a dedicated message would describe a state that shouldn't exist.

verificationGates: 615/615 unit tests, clean typecheck, zero lint warnings

  • tests/unit/mcp/access.test.ts (new, 23 tests): role parsing incl. least-privilege defaults, full resolveSelfEmail matrix with case/whitespace variants, per-call (live-role) enforcement.
  • tests/unit/mcp/tools.test.ts (extended to 55 tests): per-tool deny/serve matrix across viewer / admin / shared-secret for all 11 admin tools (denial = shared message + data fn not called), self-scope pinning incl. filter passthrough, catalog utilization flag, missing-authInfo fail-closed.
  • store.test.ts / auth.test.ts / data.test.ts updated for the new shapes; the viewer catalog test proves the count aggregate is skipped (only two queued selects consumed).

verificationLive probe (dev server, port 3001): propagation chain confirmed end-to-end

The one thing unit tests can't see is whether mcp-handler actually delivers AuthInfo into tool callbacks at runtime. Verified statically (withMcpAuth sets req.auth; the transport passes authInfo: req.auth into handleRequest) and live with the shared secret: get_budget_status returned real budget JSON, get_user_cost_profile without an email returned the exact explicit-email validation error, list_ai_tools included utilization, and a bogus mcp_at_ token got a clean 401 (OAuth lookup path live against the preview DB).

Not probed live: a real viewer-bound OAuth token. Minting one outside the OAuth flow means inserting forged token hashes into the shared preview DB — declined by policy. Viewer behaviour rides the same extra.authInfo channel just proven live and is pinned by the 55-test unit matrix; the remaining risk is negligible. First real-world viewer connect via Claude Desktop will confirm.
