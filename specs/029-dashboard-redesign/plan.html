Feature 029 · Implementation plan

Dashboard Redesign

A slim plan that prioritizes existing data, reuses report-side components, and lands the admin + viewer dashboards together in a single PR across four small phases.

Single PR · 4 phases No schema changes
README design overview admin.html admin viewer.html viewer

Decisions baked into this plan

Four product calls were made before writing this plan; each shrinks scope:

  • "Available tools" panel → read-only catalog link. No access_requests table; viewers get a link to a now-viewer-accessible read-only /tools page.
  • Trial badge / "last call N min ago" chip → use only data that exists today. Assignment row badges show active / inactive (driven by licenseAssignments.status + revokedAt). Sync chip is sourced from anthropicSyncStatus — "Anthropic data · synced 12 min ago", not "last API call".
  • Activity timeline → admin: 2 sources (ingestionLog + recent licenseAssignments); viewer: 1 source (their own assignment history). No changeHistory join, no syncEvents union.
  • Spend over time → 2 layers: Licenses + Anthropic API. Reuses periodsWithActual directly; no Copilot per-month aggregation.

Non-goals: no new tables, no new enum values, no new sync paths, no new background jobs, no test infrastructure additions. If a card can't be backed by an existing query (or a thin wrapper around one), it doesn't ship.

Phasing (single PR)

Four phases, mergeable as one. Each phase is independently shippable so the PR can be split if review demands, but the default is to land as one.

Phase 0foundation, shared utilities Phase 1admin dashboard Phase 2viewer dashboard Phase 3polish & verification

Phase 0   Foundations (~1 dev-day)

Cheap reshuffles that unlock both dashboards. No UI visible yet.

0.1 — Split src/app/page.tsx into role-routed components

  • Move the existing AdminDashboard and ViewerDashboard functions into src/components/dashboard/admin/admin-dashboard.tsx and src/components/dashboard/viewer/viewer-dashboard.tsx. page.tsx shrinks to a session-checked dispatcher (session.user.role === "admin").
  • No behavior change. This is the seam Phase 1 and Phase 2 each write into.

0.2 — Lift two report sub-components to components/shared/

  • spend-progress-bar.tsx — extracted from reports/budget/at-a-glance.tsx (the layered actual / projected / ceiling-tick bar). The current implementation embeds it inline; lift unchanged, change the import in at-a-glance.tsx.
  • budget-health-hero.tsx — already in reports/overview/; re-export from components/shared/ so both the dashboard and the report import the same instance.

0.3 — Open /tools read-only to viewers

  • Remove the AuthGuard requiredRole="admin" wrapper from src/app/tools/page.tsx.
  • Guard admin-only actions (create/edit/delete buttons, row actions) inside the page with a session.user.role === "admin" check — viewers see the table only.
  • Sanity-check no server action on this page leaks data viewers shouldn't see (read-only list is fine — tool catalog is not sensitive).

0.4 — One small shared helper

  • src/lib/format-relative.ts — formatRelativeAge(date): "12 min ago" | "2 hours ago" | "yesterday". Used by both dashboards' sync chips and activity timelines. ~25 lines, no deps.

Acceptance

  • ✓ pnpm typecheck, pnpm lint clean.
  • ✓ Existing admin dashboard and reports render identically (visual diff).
  • ✓ Viewer can reach /tools, sees read-only table, no admin buttons.

1.2 — One thin new query: getRecentDashboardActivity({limit})

  • Two parallel selects:
    • ingestionLog: newest 5 ordered by createdAt DESC.
    • licenseAssignments: newest 5 ordered by GREATEST(assignedAt, revokedAt) DESC, with user + tool joins.
  • Map each to { id, kind: "ingestion" | "assignment", timestamp, payload }, merge, sort, slice to limit. ~40 lines in src/actions/dashboard.ts.
  • Admin-only via requireAdmin().

  • components/dashboard/admin/this-month-card.tsx — small, snapshot tile.
  • components/dashboard/admin/kpi-grid.tsx — 4× KpiWithMom.
  • components/dashboard/admin/spend-trend-chart.tsx — Recharts stacked BarChart with 2 series (Licenses, API), forecast bars at 0.5 opacity, ChartTooltipContent with currency formatter + percent share.
  • components/dashboard/admin/insights-grid.tsx — reuses WhatChanged with 2 added insight rules: workspace approaching limit (from getActiveAlerts()), sync freshness (from getSyncStatus()).
  • components/dashboard/admin/top-tools-card.tsx — same column shape as report's tool adoption table; top-5 only; add inline 12-month sparkline via existing Sparkline.

Phase 3   Polish & verification (~0.5 dev-day)

Catch the things that look small in mockups but matter in the actual app.

3.1 — Responsive sweep

  • Manually verify sm / md / lg breakpoints in dev (1280, 1024, 768, 390 widths). The mockups assume lg; sm collapses the 4-column KPI grid to 2 and the hero stacks.

3.2 — Light-mode parity

  • Open the app in light theme and confirm: the spend-bar destructive overlay, the sync-stale amber, and the badge backgrounds all use design tokens (not hard-coded RGBs).

3.3 — Loading states

  • Wrap both dashboards in an <Suspense> boundary with a skeleton card grid that matches the section heights. Avoids layout shift.

3.4 — Tests (minimal)

  • Unit: add a Vitest test for getRecentDashboardActivity merge-sort behavior (mocked rows).
  • Integration: one test per dashboard hitting the real DB seed — admin sees their KPIs, viewer sees only their own data when authenticated as a non-admin user.
  • No new E2E in this PR — Playwright spec can come in a follow-up if the team wants it.

3.5 — Browser smoke

  • Run pnpm dev, log in as admin and as a viewer, click through Budget hero → /reports/budget, click through "Browse all tools" link, confirm activity timeline updates after a manual invoice ingestion.

Risks & how the plan handles them

RiskMitigation
Lifting components from reports/ breaks the reports page. Phase 0 ships the lift + import-swap with zero visual change. Reports are visually diffed in QA before any dashboard work begins.
Viewer dashboard accidentally reads org-wide data. All viewer-side queries go through getViewerDashboardData(userId), which self-checks like getUserCostData. Integration test in Phase 3 logs in as a non-admin and asserts only their data is returned.
The activity timeline becomes noisy. Limit to 8 entries; only two sources. If it's still noisy, a follow-up adds filters — out of scope here.
Sync chip says "synced 12 min ago" but the data is actually stale because workspace sync failed. Use workspaceSyncCompletedAt over lastSyncCompletedAt (same precedence as existing getSyncStatus()); surface lastSyncError as a tooltip on the chip when present.
Opening /tools to viewers leaks something sensitive. The page is a read-only list of tool names, vendors, and access tiers — already shown indirectly via assignments. No costs, no users, no API keys. Reviewer confirms before merge.
The PR is too large to review. Phasing aligns with logical commits. The team can request splitting into 4 PRs without rework: each phase typechecks and runs on its own.

Explicit non-goals (do not implement in this PR)

  • Trial / expiry concept on assignments (no expiresAt, no trial badges).
  • License access-request workflow (no access_requests table, no pending status, no admin approval UI).
  • Per-user Copilot attribution.
  • Per-user spend cap (only workspace-level exists today).
  • Intraday last-call timestamp on Anthropic usage.
  • changeHistory join into the activity timeline.
  • Copilot per-month series in the spend chart.
  • Date-range selector on the admin dashboard (always "current month + YTD"; reports own the date-range UX).
  • E2E / Playwright coverage of the new dashboards.

Each is a sensible follow-up candidate, but none belong in this PR.

What I still want to know

None of these block the plan, but they shape v2:

  • Should the activity timeline live as a sticky sidebar instead of a column panel? (Trade-off: visible always, but eats horizontal room on smaller screens.)
  • If the team uses Workflow DevKit for sync, would surfacing the last sync run's status link directly to the run be useful, or is the chip enough?
  • Is "12 more tools available" worth computing, or just say "Browse all tools →"? (Count needs the catalog query; the link doesn't.)
