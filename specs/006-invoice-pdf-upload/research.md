## Decision 1: PDF Text Extraction Library

### Context
The feature needs to extract machine-readable text from a PDF invoice uploaded by the user so it can be passed to an AI model for structured field extraction.

### Candidates Evaluated

| Criterion | `pdf-parse` (v1.1.1) | `pdfjs-dist` (v5.5.x) | `unpdf` (v1.4.x) |
|---|---|---|---|
| Maintenance | Abandoned (~2019) | Active (Mozilla) | Active (UnJS) |
| Vercel serverless | Breaks on cold start (hardcoded test file path hits at import time) | Works with `serverExternalPackages` config; large bundle | Works out of the box, no config required |
| TypeScript | Requires `@types/pdf-parse` separately | Types bundled | Types bundled (`.d.mts`) |
| Bundle size | ~1 MB (wraps pdfjs internally) | Tens of MB + optional canvas (~180 MB) | ~1.83 MB, 0 runtime dependencies |
| Edge-compatible | No | No | Yes |
| Text extraction quality | Wraps pdfjs | Reference implementation (most accurate) | Wraps pdfjs-dist v5.x — identical quality |
| Known issues | `ENOENT` crash on Vercel serverless; abandoned upstream | Must set `serverExternalPackages`; function size risk | None reported in serverless context |

### Decision: **`unpdf` v1.4.x**

**Rationale**: Zero Vercel configuration, first-class TypeScript, ships the same PDF.js v5 engine as `pdfjs-dist` (identical extraction fidelity), small bundle, and designed for serverless/edge. `pdf-parse` is abandoned with a known production-breaking serverless bug. `pdfjs-dist` requires manual `next.config` surgery and risks the 250 MB Vercel function limit with `canvas` installed.

**Usage pattern (in a Route Handler)**:
```ts
import { extractText, getDocumentProxy } from 'unpdf'

const buffer = await fetchBlobAsArrayBuffer(pathname)
const pdf = await getDocumentProxy(new Uint8Array(buffer))
const { text } = await extractText(pdf, { mergePages: true })
```

## Decision 2: PDF File Storage

### Context
The archived invoice PDF must be persistently stored and downloadable by authenticated admins. The project runs on Vercel with Neon PostgreSQL.

### Candidates Evaluated

| Factor | Neon PostgreSQL `bytea` column | Cloudflare R2 (private bucket) |
|---|---|---|
| Max file size | 1 GB per value (PostgreSQL limit) | 5 TB per object |
| Retrieval performance | ~10× slower than filesystem | Direct from R2 via presigned URL |
| DB impact | Bloats WAL, backups, replication | Zero DB impact |
| Neon's own guidance | Explicitly not recommended for files | Recommended hybrid: store key in Neon |
| Additional service | None (simpler) | Requires Cloudflare account + R2 bucket |
| Cost | Larger DB = higher Neon compute cost | Free tier: 10 GB storage + 1M ops/month |
| Presigned URLs | N/A | ✅ Yes — time-limited PUT and GET URLs |
| Atomic consistency | Can be in the same DB transaction | Must handle orphan cleanup manually |
| ACID safety | Fully ACID | Not transactional — must delete object on DB failure |

**Vercel Function body limit**: Vercel Functions have a hard **4.5 MB request body limit**. Invoice PDFs can be up to 5 MB. Server Actions that receive the raw file binary will fail for larger files. This rules out sending the file through a Server Action.

### Decision: **Cloudflare R2 with presigned PUT URL upload pattern**

**Rationale**: Neon's own docs explicitly recommend against `bytea` for file storage. Cloudflare R2 is the simplest available alternative: S3-compatible API (no new SDK to learn), generous free tier (10 GB/month), zero egress fees, and — critically — **presigned URLs**. Presigned PUT URLs allow the browser to upload directly to R2 without going through a Vercel Function, completely bypassing the 4.5 MB body limit. Presigned GET URLs let the download Route Handler redirect the browser to a time-limited, private R2 URL without proxying bytes through Vercel (avoids egress cost).

**Key implementation notes**:
- SDK: `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner`. R2 is S3-compatible; the endpoint is `https://<CLOUDFLARE_R2_ACCOUNT_ID>.r2.cloudflarestorage.com`.
- Store only `blob_pathname` (the R2 object key, e.g. `invoices/<uuid>.pdf`) in Neon — never the binary.
- Presigned PUT URL valid for 5 minutes — generated by `POST /api/invoices/upload-url`; client PUTs the file directly.
- Presigned GET URL valid for 5 minutes — generated by `GET /api/invoices/[id]/pdf` Route Handler; browser follows the 302 redirect.
- Orphan protection: if the Neon DB write fails after a successful upload, call `DeleteObjectCommand` to clean up.
- Local dev: add `CLOUDFLARE_R2_ACCOUNT_ID`, `CLOUDFLARE_R2_ACCESS_KEY_ID`, `CLOUDFLARE_R2_SECRET_ACCESS_KEY`, `CLOUDFLARE_R2_BUCKET_NAME` to `.env.local` manually (no `vercel env pull` needed).

**Upload flow**:
1. Client selects PDF → calls `POST /api/invoices/upload-url` (server generates presigned PUT URL + objectKey)
2. Client `fetch(uploadUrl, { method: "PUT", body: file })` → PDF goes directly to R2
3. Client receives `{ objectKey }` and triggers extraction

**Download flow**:
```
GET /api/invoices/[id]/pdf
  → auth check (NextAuth session)
  → fetch objectKey from Neon
  → getSignedUrl(GetObjectCommand, expiresIn: 300)
  → Response.redirect(presignedUrl, 302)
```

## Decision 3: Invoice Data Extraction Approach

### Context
After a PDF is uploaded, the system must automatically extract invoice number, invoice date, and total amount. The codebase already uses Anthropic's Claude API (project uses `@anthropic-ai/sdk`).

### Candidates Evaluated

**Approach A: Regex/heuristic extraction**
- Parse raw PDF text, apply regex patterns for invoice number, date, total
- Pros: zero cost, no network call, deterministic
- Cons: fragile on varied vendor formats; hard to distinguish grand total from subtotals; no confidence signal; requires ongoing pattern maintenance for new vendors

**Approach B: Claude Haiku (LLM) with forced tool use**
- Pass extracted PDF text to `claude-haiku-4-5` with `tool_choice: { type: "tool" }` forcing structured JSON output
- Returns `invoice_number`, `invoice_date`, `amount_cents`, per-field `confidence` ("high" | "medium" | "low")
- Pros: handles arbitrary vendor formats and multilingual invoices; returns `null` when uncertain (instead of silently wrong); confidence score enables UI affordances; `tool_choice` guarantees structured output
- Cons: ~1-3s latency, requires `ANTHROPIC_API_KEY`; <$0.25/year cost at 500 invoices

### Cost analysis (Approach B)

| Volume | Avg. tokens | Cost/invoice (Haiku) | Annual total |
|---|---|---|---|
| 100 invoices/year | ~2,100 in / ~100 out | ~$0.0002 | ~$0.02 |
| 500 invoices/year | ~2,100 in / ~100 out | ~$0.0002 | ~$0.10 |

### Decision: **Approach B (Claude Haiku) as primary, Approach A as fallback**

**Rationale**: The economics are negligible (<$0.25/year). LLM extraction is robust across vendor formats. The confidence field provides a machine-readable signal that drives "please review" UX — something regex cannot provide. The codebase already uses the Anthropic SDK (`@anthropic-ai/sdk` is a constitution-compliant existing dependency). Approach A serves as a silent emergency fallback if the Claude API is unavailable, marking all confidence fields as "low".

**Extraction tool schema**:
```ts
{
  name: "extract_invoice_fields",
  input_schema: {
    type: "object",
    properties: {
      invoice_number: { type: ["string", "null"], description: "Vendor invoice identifier, e.g. INV-1042. Null if not found." },
      invoice_date: { type: ["string", "null"], description: "Invoice issue date in YYYY-MM-DD format. Null if not found." },
      amount_cents: { type: ["integer", "null"], description: "Total amount due in integer cents (e.g. $12.50 → 1250). Grand total only. Null if not found." },
      confidence: {
        type: "object",
        properties: {
          invoice_number: { type: "string", enum: ["high", "medium", "low"] },
          invoice_date: { type: "string", enum: ["high", "medium", "low"] },
          amount_cents: { type: "string", enum: ["high", "medium", "low"] }
        },
        required: ["invoice_number", "invoice_date", "amount_cents"]
      }
    },
    required: ["invoice_number", "invoice_date", "amount_cents", "confidence"]
  }
}
```

**Fallback strategy**:
```
PDF uploaded → text extraction (unpdf)
  ├─ text empty or < 50 chars → reject: "PDF has no readable text layer"
  └─ text OK → call Claude Haiku (tool_choice forced)
       ├─ API error / timeout (< 5s) → regex heuristics, all confidence: "low"
       └─ success → Zod validate result
            ├─ null field → leave form input blank, highlight amber
            ├─ confidence "low" → highlight amber with tooltip
            └─ all high/medium → pre-fill, admin confirms before save
```

## Decision 4: New Database Table vs. Extending `billedCosts`

### Context
The spec states the invoice archive is standalone (not linked to budget periods). The existing `billedCosts` table requires a `periodId` foreign key, making it unsuitable for standalone invoice archival.

### Decision: **New `invoices` table**

**Rationale**: Forcing the archive into `billedCosts` would require `periodId` to be nullable (a schema change that affects existing budget workflows) and would conflate two distinct concerns. A new table is the minimal, clean solution that satisfies the spec assumption: "The invoice archive is a standalone section."

The new table maps directly to the extracted fields plus storage metadata:

| Column | Type | Notes |
|---|---|---|
| `id` | serial PK | |
| `invoice_number` | varchar(255) NOT NULL | Vendor-assigned invoice identifier |
| `invoice_date` | date NOT NULL | Date on the invoice |
| `amount_cents` | integer NOT NULL | Grand total in cents |
| `blob_url` | text NOT NULL | Vercel Blob permanent URL |
| `blob_pathname` | text NOT NULL | Vercel Blob pathname (used for download proxy) |
| `uploaded_by` | integer FK → users.id NOT NULL | Admin who uploaded |
| `created_at` | timestamp NOT NULL DEFAULT now() | |
| `updated_at` | timestamp NOT NULL DEFAULT now() | |
