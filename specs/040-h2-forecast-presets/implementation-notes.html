Design decisions (ambiguous spots, choices made)

"Replace the three presets with the H2 prediction in a similar manner" → three H2 speed variants interpretation

The request names one H2 prediction but asks to replace all three presets "in a similar manner". Decision: keep the slow / central / fast triad the UI is built around (tiles, ghost lines, comparison rows), but make all three variants of the same H2 migration plan at different speeds: H2 Gradual (API −25%/period, Claude +10/period @ 35% Premium, Copilot flat), H2 Plan (API −35%, Claude +15 @ 40%, Copilot −1/period — the central prediction and new default), H2 Accelerated (API −50%, Claude +20 @ 40%, Copilot −2/period). Cursor and MS Copilot stay flat in all three. The user's stated ranges (10–20 seats/period, 35–40% Premium, "maybe 40 would be good") map onto the three variants directly, with 40% on the central plan.

API fade-out encoded as compound decline presets

"Fade out very fast, down to almost zero seats, maybe only having a few applications and a few users" — a compound negative rate decays toward zero but never reaches it, matching "a few remain". From the live 42 active API keys over the ~7 remaining FY2026 periods: −25% → ≈ 5–6 keys, −35% → ≈ 2 keys, −50% → ≈ 0.3 keys at year-end. Per-key burn is held flat (burn growth 0%, no cap): the seat fade is the story, and surviving applications are assumed to burn today's average. A linear "−N keys/period" alternative hits exactly zero and then clamps — rejected because the brief explicitly keeps a residue of apps/users.

Yearly billing = 0.8 × live monthly tier prices, smoothed per period billing

The stated prices — monthly $25/$125, yearly $20/$100 — are exactly a 20% discount on both tiers. The engine applies CLAUDE_YEARLY_FACTOR = 0.8 to the loader-supplied stdPrice/premPrice rather than hardcoding 2000/10000¢, so the toggle stays anchored to the live access_tiers rows (verified: Standard Seat 2500¢, Premium Seat 12500¢ — the factor reproduces the stated yearly prices to the cent). Yearly billing is modelled as a smoothed effective per-period rate (annual ÷ 12), not a January lump sum — the burn-up chart keeps its monthly meaning; payment-timing simulation is out of scope.

Billing lives in ToolParams, persists across preset switches engine/UX

billing?: "monthly" | "yearly" sits on the claudeSeats tool's params (undefined = monthly; stamped by inputsFromPreset only when yearly so monthly inputs stay deep-equal to pristine presets), keeping the engine signature (tool, params, k) and state serialization unchanged. Because it's a procurement assumption rather than a scenario lever, the client threads the current cadence through inputsFromPreset(ds, key, billing) when applying a preset and when scoring the preset tiles / ghost lines / comparison rows, so all comparisons stay like-for-like. Toggling cadence marks the plan Custom (same as editing the ceiling); "Reset to H2 Plan" restores monthly + the live ceiling.

Deliberate asymmetry on tile click: clicking a preset tile resets the edited ceiling to the live one (unchanged 036 behavior — the ceiling is part of the what-if frame) but keeps the billing cadence — flipping scenarios shouldn't silently flip how the org pays for Claude seats. This is new behavior with no existing analogue; an earlier draft claimed it "mirrors the ceiling", which was wrong (the ceiling only persists in the scoring path, not the apply path) — corrected during the challenge pass.

Preset keys renamed, not reused refactor

PresetKey becomes h2Gradual | h2Plan | h2Accelerated. Reusing the old keys with new math would silently repoint everything that says "expected" (default seeding, reset, tests) at different numbers; the rename makes the type-checker surface every call site. Ghost-line colors keep their positions (gradual→chart-4, plan→chart-3, accelerated→chart-2).

Tradeoffs (alternatives weighed)

Discount factor vs explicit yearly prices on the tool billing

Explicit stdPriceYearly/premPriceYearly fields on ForecastTool would let the data layer own both price points — but there is no yearly tier in the DB to read them from, so they'd be hardcoded constants anyway, just with more plumbing. The factor is one named constant in the engine with the price pairs cited in a comment. If yearly pricing ever stops being exactly 20%-off-monthly, switch to explicit fields — noted as the follow-up trigger.

Burn behaviour of the surviving API keys presets

Arguably the last few surviving applications are the heaviest consumers, so per-key burn could rise as light users leave (survivorship bias). Modelling that would need a burn-vs-rank distribution the presets can't honestly claim; the presets hold per-key burn flat and leave burnPct live-editable for anyone who wants to model survivorship. Flagged as an open question below.

Open questions (for review)

Exact fade percentages confirm

−25 / −35 / −50%/period are tuned so the central plan lands ≈ 2 API keys at FY-end from today's 42 ("a few applications and a few users"). If "a few" should mean ~5+, the central plan should use −25 to −30%. The values are one-line preset edits.

Should any preset default to yearly billing? confirm

All presets default to monthly (today's reality); yearly is a user-flipped toggle that persists across preset switches. If the H2 plan's intent is to commit annually from the start, the default could flip to yearly — one-line change.
