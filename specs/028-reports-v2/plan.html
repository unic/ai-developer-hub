2.1 · New helper: assignment snapshot at past date

Existing license_assignments has assigned_at and revoked_at. We can compute "active as of any past date" without schema work.

Show sketch — getAssignmentSnapshotAt 
// src/actions/assignments.ts (new export)
export async function getAssignmentSnapshotAt(asOf: Date) {
  return db
    .select({
      id: licenseAssignments.id,
      toolId: licenseAssignments.toolId,
      userId: licenseAssignments.userId,
      costAtAssignmentCents: licenseAssignments.costAtAssignmentCents,
    })
    .from(licenseAssignments)
    .where(
      and(
        lte(licenseAssignments.assignedAt, asOf),
        or(
          isNull(licenseAssignments.revokedAt),
          gt(licenseAssignments.revokedAt, asOf),
        ),
      ),
    );
}

~30 lines including a small per-tool aggregator (countByToolFromSnapshot) used for the MoM license-delta column and the static-rules input.

Phase 3

New Budget tab

3.1 · One server action wraps everything

D-2 decision applied

Every "Actual" value in this report is billedTotalCents + runningCostCents, matching the budget detail page (src/app/budget/[id]/budget-detail-client.tsx:126-131). Running costs come from getRunningCostsForPeriod(periodId) — already used by the detail page; no new helper needed. We fetch one running-cost lookup per period in parallel, exactly like budget/[id]/page.tsx:38-47.

Show sketch — getBudgetReportData 
// src/actions/reports.ts (new)
import { getActiveBudget, getBudgetWithCosts, getBilledCostsTimeSeries,
         getBudgetForecast, getPerToolSpend } from "@/actions/budget";
import { getRunningCostsForPeriod } from "@/lib/budget-utils";

export async function getBudgetReportData() {
  const budget = await getBudgetWithCosts(/* active id */);
  if (!budget) return { kind: "empty" } as const;

  // Fetch running Anthropic API costs for each period (same pattern as budget/[id]/page.tsx)
  const runningResults = await Promise.all(
    budget.periods.map((p) => getRunningCostsForPeriod(p.id)),
  );
  const runningByPeriod: Record<number, RunningCostData> = {};
  budget.periods.forEach((p, i) => {
    if (runningResults[i]) runningByPeriod[p.id] = runningResults[i]!;
  });

  // Derive period-level Actual = billed + running (the v1 contract)
  const periodsWithActual = budget.periods.map((p) => ({
    ...p,
    runningCents: runningByPeriod[p.id]?.runningCostCents ?? 0,
    actualCents: p.billedTotalCents + (runningByPeriod[p.id]?.runningCostCents ?? 0),
  }));

  const [series, forecast] = await Promise.all([
    getBilledCostsTimeSeries(budget.id),  // then we layer runningByPeriod onto each point
    getBudgetForecast(budget.id),         // driven by Actual = billed + running (see 3.5)
  ]);

  const pastMonth = pickPastMonth(periodsWithActual);  // see helper below
  const perToolPastMonth = pastMonth
    ? await getPerToolSpend(pastMonth.startDate, pastMonth.endDate)
    : [];

  return { kind: "ready", budget, periodsWithActual, runningByPeriod,
           series, forecast, pastMonth, perToolPastMonth } as const;
}

// "Most recent past period that has ANY actual spend (billed OR running)"
function pickPastMonth(periods: PeriodWithActual[]) {
  const today = new Date();
  return periods
    .filter((p) => new Date(p.endDate) < today && p.actualCents > 0)
    .at(-1) ?? null;
}

The "past month" predicate switches from billed > 0 to actual > 0 so a brand-new month with only Anthropic API usage (no invoice yet) still qualifies as a real spotlight target.

3.5 · How forecast uses Actual

getBudgetForecast today regresses on billedTotalCents per completed period. With v1, the input series must be Actual (billed + running) so the projection reflects total run-rate including live API usage.

Show the one-line change in getBudgetForecast 
// src/actions/budget.ts (~line 598-635)
// before:
const completedPeriods = budget.periods.filter(
  (p) => new Date(p.endDate) < today && p.billedTotalCents > 0
);
const history = completedPeriods.map((p) => ({
  monthLabel: p.periodLabel,
  amountCents: p.billedTotalCents,
}));

// after — Actual includes running Anthropic API costs:
const runningResults = await Promise.all(
  budget.periods.map((p) => getRunningCostsForPeriod(p.id)),
);
const actualByPeriod = new Map(
  budget.periods.map((p, i) => [
    p.id,
    p.billedTotalCents + (runningResults[i]?.runningCostCents ?? 0),
  ]),
);
const completedPeriods = budget.periods.filter(
  (p) => new Date(p.endDate) < today && (actualByPeriod.get(p.id) ?? 0) > 0,
);
const history = completedPeriods.map((p) => ({
  monthLabel: p.periodLabel,
  amountCents: actualByPeriod.get(p.id)!,
}));

Same regression math; different input. The change is contained to getBudgetForecast — callers are unaffected.

3.4 · Acceptance criteria

  • Every "Actual" number rendered in the Budget tab equals the corresponding budget detail page value to the cent (validated against the same active budget in an integration test).
  • Visiting /reports?tab=budget with no active budget shows the empty state ("Create a budget to see this report") and a CTA to /budget/new.
  • With an active budget, the page renders without waterfall fetches — running-cost lookups happen in a single Promise.all over periods.
  • Past-month spotlight selects the most recent period where endDate < today AND actualCents > 0. If none qualifies (brand-new fiscal year, no spend anywhere), the section is hidden.
  • Past-month spotlight Actual tile displays the inline split "$X billed + $Y API" when running > 0; collapses to just "$Z" when running = 0.
  • Plan vs Actual chart stacks billed + running within each past-month bar; legend shows three series (Planned, Billed, API). Bars for months with running = 0 display as solid single-color (no stack artifact).
  • Forecast chart hides forecast line + cumulative when forecast.insufficientData is set (less than 3 completed periods).
  • Per-tool breakdown sorts by YTD spent desc; ties broken by tool name. The "Anthropic API" row is always sorted positionally to its computed total (not pinned).
  • Per-tool breakdown shows a one-line footer noting that invoiced costs without tool attribution are excluded from the table but included in the org Actual total.
  • pnpm typecheck, pnpm lint, pnpm test all clean. Lighthouse score for /reports?tab=budget ≥ 90 (Performance & Accessibility).

6 · Data flow

Server-side request lifecycle
ReportsPage (server component)
  ├─ parseTab(searchParams) → "overview" | "budget"
  │
  // Always
  ├─ Promise.all([
  │     getUsers(), getTools(), getAssignments(),
  │     getActiveBudget(),
  │     getAssignmentSnapshotAt(lastMonthEnd),  // NEW
  │   ])
  │
  // Only when activeTab === "budget"
  └─ getBudgetReportData()           // NEW orchestrator in src/actions/reports.ts
        ├─ getBudgetWithCosts(activeId)
        ├─ Promise.all(periods.map(p => getRunningCostsForPeriod(p.id)))  // same as budget/[id]/page.tsx:38
        ├─ derive periodsWithActual[] : { ...period, runningCents, actualCents }
        ├─ Promise.all([
        │     getBilledCostsTimeSeries(id),  // merged with running per period in the component
        │     getBudgetForecast(id),         // now regresses on Actual = billed + running
        │   ])
        ├─ pickPastMonth(periodsWithActual)  // most recent past period where actualCents > 0
        └─ getPerToolSpend(start, end)

The overview tab does not pay the Budget tab's fetch cost (and vice versa). Server-side rendering means a single round-trip per tab; no client-side data fetching needed.

7 · Test plan

Unit (Vitest)

  • insights-static.ts — 4 rules × (positive case, null case, edge case) = ~12 cases.
  • pickPastMonth(periods) — chooses last period meeting both predicates; returns null when none qualify.
  • countByToolFromSnapshot — groups snapshot rows by toolId, computes deltas vs current.

Integration (Vitest + real DB)

  • getAssignmentSnapshotAt — seed assignments with various assigned/revoked dates, assert the right active set at three points in time.
  • getBudgetReportData — happy path (active budget, 4 completed months) returns kind: "ready" with all expected slices populated; no-active-budget returns kind: "empty".
  • Billed + running parity — given a seeded budget with both billed_costs and anthropic_workspace_costs, assert that the totals exposed by getBudgetReportData equal those computed by the budget detail page logic to the cent (totalBilled + totalRunning = the report's Actual YTD).
  • getBudgetForecast — with the new Actual-based input, regression coefficients differ from the billed-only baseline when running > 0; with running = 0 the result is unchanged from the prior implementation.

E2E (Playwright)

  • Navigate to /reports. Default tab is Overview. Click Open Budget report button — verify URL becomes ?tab=budget and Budget content renders.
  • Visit /reports?tab=trends — assert URL normalizes to ?tab=overview (or the tab bar shows Overview as active).
  • Empty-state test: with no active budget, the Budget tab shows the CTA and the Overview's budget-health hero is hidden.

Visual / a11y

  • Lighthouse CI on /reports?tab=budget with seeded data — Performance ≥ 90, Accessibility ≥ 95.
  • Manual check: dark + light themes, keyboard navigation across all chart cards, screen-reader labels on all KPI tiles.

8 · Risks & mitigations

RiskLikelihoodMitigation
Overview becomes slower because of the extra snapshot query. Low Snapshot is a single indexed query on license_assignments; same shape as the existing fetch. Add a EXPLAIN sanity check during PR review.
"Past month" definition picks a stale period if invoices land late. Low The filter requires actualCents > 0 (billed + running). Running Anthropic costs land daily, so a month with any API usage qualifies even before its invoice arrives. UI labels the spotlight with the actual month name so the user can verify.
Running and billed double-count if an Anthropic invoice is also entered into billed_costs for the same period. Medium Same risk exists on the budget detail page today and is treated as an operational discipline issue, not a system one. v1 documents the behavior in the per-tool table footer ("Running costs reflect live API usage; once invoiced, manually delete the running attribution or expect overlap"). Follow-up work could reconcile automatically via G-3 + an Anthropic-source tag on billed_costs.
Per-tool table can't attribute invoiced costs to a specific tool. Medium Footer on the table makes this explicit: invoiced costs without tool attribution roll into the org-level Actual but not into any tool row. Same constraint as the existing budget detail page. Closure path tracked as G-3.
Forecast chart looks empty in Q1 (fewer than 3 completed months). Low getBudgetForecast already returns insufficientData; component renders a placeholder card with the message.
Stale state from cached page after a new budget is created. Low Existing budget actions call revalidatePath('/reports') on write. Verify after Phase 3 lands.
