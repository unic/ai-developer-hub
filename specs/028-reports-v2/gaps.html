2 · Gaps

Each gap is classified blocking (the mock UI cannot ship as drawn without it), deferrable (mock UI is graceful-degradable; v2 ships a simpler version), or trivial (small helper, fold into v2).

G-1

Per-tool budget allocation

deferrable · needs product decision
Mock shows
The Budget "Per-tool budget breakdown" table has columns YTD planned, Variance, and Annual cap per tool — implying each tool has its own planned allocation.
Reality
budget_periods.planned_amount_cents is org-level only. No tool_id column anywhere on budget_periods or annual_budgets. No table maps a tool to a planned amount.
Close by
Either (a) add a new budget_tool_allocations table (period_id, tool_id, planned_amount_cents) with a setter UI, or (b) derive per-tool plan from access_tiers.monthly_cost_cents × max_licenses (treats current capacity as "plan"). Option (a) is honest; (b) is a UX shortcut. Decision needed — see D-1.
v2 degrades to
Per-tool table shows YTD spent · run-rate · projected EOY · % of org spend only. No "planned" / "variance" / "annual cap" columns. Status chip becomes derived (e.g. "above run-rate" if EOY > YTD-implied trajectory).
G-2

Unified actual spend (billed + running API)

closed in v1 · matches budget detail pattern
Mock shows
An "Actual" total that includes both invoiced costs and live API usage (Anthropic running costs), with per-period attribution.
Reality
The pattern already exists on the budget detail page (src/app/budget/[id]/budget-detail-client.tsx:126-131): totalActual = totalBilled + totalRunning, where totalRunning sums getRunningCostsForPeriod(periodId).runningCostCents across periods. The per-period row shows the breakdown with an "(API)" annotation and an expandable per-workspace list.
v1 ships
The Budget report adopts the exact same formula: actualCents = billedTotalCents + runningCostCents for every period, KPI tile, chart, and the per-tool breakdown. The Anthropic API contribution appears as its own row in the per-tool table sourced from getRunningCostsForPeriod. Per-workspace breakdown is shown on demand via a disclosure, mirroring the detail page's expandable rows.
Residual
What's still not in v1: per-tool attribution of invoiced billed_costs rows — see G-3. Without that, the per-tool breakdown table can attribute spend to (a) license-based tools via getPerToolSpend and (b) Anthropic API via running costs, but invoiced amounts (e.g. a Copilot invoice) only show up in the org-level Actual total, not against a specific tool row. This is identical to the budget detail page's current limitation.
G-3

billed_costs.tool_id for per-tool invoice attribution

deferrable
Mock shows
Past-month spotlight lists "top variance drivers" per tool, implying we know which tool an invoiced cost came from.
Reality
billed_costs has only description (free-text, e.g. "Invoice 4711 — Anthropic") and vendor_reference. No FK to ai_tools. Invoice matching (src/lib/sync/sources/invoice-matching.ts) lands invoices on periods but doesn't tag a tool. The budget detail page lives with the same limitation today.
Close by
Migration: add nullable tool_id INTEGER REFERENCES ai_tools(id) on billed_costs. Backfill from vendor_reference heuristic or leave null. Update invoice matching to populate when confident.
v1 degrades to
Per-tool table attributes (a) license-based seats via getPerToolSpend and (b) Anthropic API via running costs. Invoiced amounts roll into the org-level Actual but do not appear as their own per-tool rows. Past-month spotlight drivers use license-delta diffs only.
G-4

MoM snapshot of active assignments

trivial · fold into v2
Mock shows
Overview KPI strip shows MoM deltas ("+22 licenses", "+8.2% spend"). What-changed-this-month insight cards. Rank-shift markers on the tool table.
Reality
No helper exists, but the data is derivable: license_assignments.assigned_at and revoked_at let us count assignments active "as of" any historical date.
Close by
Add getAssignmentSnapshotAt(date: Date) in src/actions/assignments.ts — filter assigned_at <= date AND (revoked_at IS NULL OR revoked_at > date). Wrap with a memoizing per-tool aggregator for the MoM diff. ~40 lines.
Status
Listed in plan.html Phase 2 as a small helper inside v2.
G-5

Narrative insight generation

deferrable
Mock shows
"What changed this month" cards with human-readable sentences ("Cursor Pro grew 22 → 32 seats", "8 of those Copilot seats are inactive").
Reality
None of this exists. Needs a small rules engine that takes (current snapshot, prior snapshot, usage stats) → produces a ranked list of { severity, headline, body } insights.
Close by
New src/lib/reports/insights.ts: handful of rules (license-count change, spend %, inactivity flag, tier change). Each rule returns a typed insight or null. Sort by absolute impact in cents. ~150 lines, no schema work.
v2 degrades to
The "What changed this month" section ships as a static, hand-coded version on first release showing the same four card slots populated by hard-rules (license-count MoM, spend MoM, inactive-seat count from existing assignments query, and the budget-health summary). Slightly less rich than the mock but no AI/rules-engine work. Full rules engine lands in a follow-up.
G-6

Per-month variance drivers (per tool)

deferrable
Mock shows
Past-month spotlight ranks the 5 tools that drove the variance vs plan, with $ contribution and %.
Reality
Variance vs plan requires per-tool plan (G-1). Without that, we only have variance vs last month's run-rate, which is a different (less honest) signal.
Close by
Hard-depends on G-1. Once per-tool plan exists, a simple "actual − planned grouped by tool" query closes this.
v2 degrades to
Past-month spotlight shows: planned total · actual total · variance %. No per-tool driver breakdown. Replaced by a "what grew / what shrunk" list using G-4 snapshot diff (license count changes, not $ variance).
G-7

Forecast confidence band

deferrable · low priority
Mock shows
The cumulative forecast chart has a shaded ±10% band around the projected line and a "crosses ceiling on Dec 2" annotation.
Reality
forecastBudget returns point estimates. No residual stddev / confidence interval. No crossing-date derivation.
Close by
Extend forecastBudget() to also return residualStdCents and ceilingCrossingMonth (solve cumulative ≥ ceiling). ~30 lines in src/lib/forecast.ts.
v2 degrades to
Cumulative chart shows point forecast as a dashed line with no band. Crossing date omitted. Everything else in the Forecast section ships.
G-8

Circle × tool-mix breakdown

deferrable
Mock shows
"Spend by circle" table has a horizontal stacked bar per row showing the mix of tools that make up each circle's spend.
Reality
buildCircleReport sums per circle. Doesn't break out by tool_id.
Close by
Extend buildCircleReport to also return byTool: { toolId, toolName, cents }[] per circle. ~15 lines.
v2 degrades to
Circle table ships without the mix bar. Header column "Mix" drops. Other columns (users, licenses, monthly cost, $/user) ship as drawn.
G-9

Tool rank shifts and % of org spend

deferrable
Mock shows
Overview tool-adoption table has a rank-shift marker (e.g. ▲4) and a "% of org spend" column.
Reality
Rank shift depends on G-4 (snapshot helper). "% of org spend" depends on G-2 (unified total). Without G-2, the percentage would be license-only — misleading.
v2 degrades to
Tool-adoption table keeps active-users + expected-monthly + MoM-license-delta (G-4 closes this trivially) but drops rank-shift and the percentage column.

3 · Decisions

D-2 is decided. D-1 is still open but does not block v1 — the per-tool breakdown ships without a "planned" column on each row.

D-1 open

How do per-tool budgets work?

Closes G-1 · G-6

  • Option A — Allocate a planned amount per tool per period (new budget_tool_allocations table + UI in Budget detail page). Honest but adds a planning step for admins.
  • Option B — Derive per-tool plan from current capacity (access_tiers × max_licenses). Zero admin effort but treats run-rate as the plan.
  • Option C — Skip per-tool plans entirely. Per-tool table shows actual + projected only; variance lives only at org level.
D-2 decided · 2026-05-19

How do usage-based costs enter the budget total?

Closes (partially) G-2 — full closure still depends on G-3.

Decision

Adopt the existing budget detail page pattern: actualCents = billedTotalCents + runningCostCents for every period. billedTotalCents comes from billed_costs (invoiced spend, includes Copilot/ChatGPT/etc. invoices when entered). runningCostCents comes from getRunningCostsForPeriod(periodId) — live Anthropic API usage from anthropic_workspace_costs. Both contributions are shown side-by-side in the report, with an "(API)" annotation where running costs are present, mirroring budget-detail-client.tsx.

No new sync work, no new schema, no Marketplace integration. Both billed and running are required in v1.

4 · What ships in v1

With G-2 closed via the budget-detail pattern and the other 8 gaps deferred, the v1 PR ships:

  • Trends / Usage / Forecast tabs deleted (3 tabs of dead code removed).
  • Overview keeps every existing element and adds: budget-health hero, MoM license deltas (via G-4 trivial helper), expected-monthly sparkline, and a static-rule "what changed" section.
  • New Budget tab where every Actual number = billed + running Anthropic API costs: at-a-glance hero, past-month spotlight (with billed/running split), monthly plan-vs-actual chart (Actual stacks billed + running), forecast cumulative chart (Actual time series), and per-tool breakdown that includes an "Anthropic API" row sourced from running costs alongside the license-derived tools.

See plan.html for the single-PR implementation plan.
