Budget tab — are the "planned" values linked to the active budget?

Trace of every "planned" reference on the Budget tab back to its source. The short answer: mostly yes — per-period plans flow directly to most places. But three surfaces silently average the per-period values together, which mis-reads as a fixed monthly plan when allocations are uneven.

README ↗ plan.html ↗ gaps.html ↗

1 · Source of truth

The Budget detail page (src/app/budget/[id]/budget-detail-client.tsx) writes planned amounts into two DB columns:

ColumnScopeSet by
annual_budgets.total_amount_cents Annual ceiling — one value per budget Budget create form + "Update total" dialog on detail page
budget_periods.planned_amount_cents Per-period allocation — one value per period (12 monthly or 4 quarterly) Per-row input on the budget detail page → updateBudgetAllocations

Each period can hold a different planned amount. The sum of all periods' allocations may equal the annual ceiling (fully allocated) or be less (partially allocated) — never more (the action rejects it).

3 · The actual problem

Three surfaces collapse the 12 per-period plans into a single average.

When admins allocate equally across periods — which is the default the create-budget flow produces if the user leaves all rows untouched at $0 (well, technically $0 each, but that's the pattern) — the average matches the per-period value and everything reads correctly. When admins allocate unevenly (e.g. Q4-heavy seasonal, ramp-up, or only-funded-the-first-three-months), the average is a number that doesn't match any actual period's plan, and the report visually suggests a uniformity that isn't there.

3.1 · Concrete example

Suppose the admin allocates $42,000 with Q4-loaded distribution: 

Jan: $1,000  Feb: $1,000  Mar: $1,000  Apr: $1,500   May: $2,000
Jun: $2,500  Jul: $3,000  Aug: $3,500  Sep: $4,000   Oct: $5,500
Nov: $7,000  Dec: $10,000                       Total: $42,000

The at-a-glance shows:

  • Annual ceiling: $42,000 · subtext: "12 × $3,500.00 planned" — but no single month is planned at $3,500.
  • Avg monthly run-rate: $4,949.95 · subtext: "vs $3,500.00 planned (+41.4%)" — comparing against the global average when, for Apr, the planned was actually $1,500.
  • Plan-vs-actual chart bars correctly show $1k → $10k ramp ✓ but the reference line at $3,500 cuts across them in a way that doesn't represent any real target.

3.2 · Quarterly budgets

A budget created with periodType: "quarterly" has 4 periods, not 12. The at-a-glance subtext would render "4 × $X planned" (calculation is generic — periods.length) but the rest of the page still says "monthly" everywhere (KPI label: "Avg monthly run-rate"; past-month spotlight: "Past month"; chart subtitle: "monthly planned vs billed"). This isn't strictly a planned-value issue but it surfaces the same way to the user.

3.3 · Initial state (zero allocations)

generatePeriods() creates each period with planned_amount_cents: 0. Until the admin opens the budget detail page and saves allocations, every "planned" value in the report is $0 — which is technically correct (nothing is allocated yet) but produces uninformative output: variance becomes "—" (we divide by 0), the reference line is hidden, the chart shows planned bars at height 0.

4 · What's working correctly

  • Per-month planned bars in the Plan-vs-Actual chart render the actual value from each budget_periods.planned_amount_cents. If you change April's allocation on the detail page, April's bar moves here on the next render. ✓
  • The past-month spotlight uses the spotlighted period's own planned amount. Variance %, variance $, the inline bar, and the headline all reflect the period-specific allocation. ✓
  • The annual ceiling tile and the forecast chart's ceiling line use the budget total directly. ✓

5 · Options to fix

Pick one option per group (A/B/C, D/E, F/G). I'll only act on the choices you confirm.

Group 1 — "12 × $3,500.00 planned" subtext on Annual ceiling

A1

Replace with the total only. "$42,000 across 12 periods" — no implied uniformity. Always honest.

A2

Conditional wording. Show "12 × $3,500.00 planned" only when all periods are equal (or within $1 of each other). Otherwise show "Allocated unevenly — see chart".

A3

Drop the subtext entirely. Annual ceiling stands alone; the per-period breakdown is the chart.

Group 2 — "vs $3,500.00 planned" subtext on Avg monthly run-rate

B1

Compare against planned-to-date instead of the global average. "vs $X planned for the same period range" — much more honest for uneven allocations. Uses sum(plannedAmountCents) over the completed periods divided by their count.

B2

Keep the current behaviour (compare against year-wide average). Simple, easy to read, but mis-represents uneven plans.

B3

Drop the comparison. Show only the run-rate value; the variance vs plan lives in the past-month spotlight already.

Group 3 — Plan-vs-Actual chart's reference line

C1

Drop the average reference line. The per-period planned bars already show the target — a single average line distracts and risks misreading.

C2

Keep but label it. Add an inline label like "avg" so the line is honest about what it represents.

C3

Replace with a different line: the YTD-to-date target line (cumulative planned through "today"). More relevant to the "are we tracking?" question.

Group 4 — Optional (quarterly / zero-state housekeeping)

D1

Adapt wording for quarterly budgets. Replace "monthly" with "per period" or "per quarter" when budget.periodType === "quarterly". Three labels need touching.

D2

Add a "set allocations" CTA at the top of the Budget tab when every plannedAmountCents is 0, linking to /budget/[id].

6 · My recommendation

A1 + B1 + C1 (plus optional D1 if you ever expect quarterly users).

  • A1 — "$42,000 across 12 periods" — is unambiguous and never wrong.
  • B1 — "vs planned-to-date" — answers the real question ("am I burning faster than the plan said I should be by now?") and degrades gracefully even for uneven allocations.
  • C1 — drop the reference line. The bars already show the truth per period. The line was a hold-over from the original mock; it doesn't add information once the bars exist.

All three are small, contained changes — total ~25 lines across two files, no schema work, no contract changes.
