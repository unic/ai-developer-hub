Implementation plan spec/041-forecast-scenario-persistence Challenged & revised — ready to implement

Saved Forecast Scenarios

Ship the follow-up that spec 036 explicitly deferred: persisting named scenarios for the Budget / Cost Forecast Simulation. An admin who has tuned a plan — levers, edited ceiling, billing cadence — can save it under a name, reload it later (or in another browser, or as another admin), rename it, update it after refinement, and delete it when it has served its purpose. Saved scenarios are shared across all admins and scoped to the active fiscal-year budget, exactly the forecast_scenarios table (“JSON params + label + budget_id”) the 036 plan sketched for this follow-up.

Drafted 2026-06-12 · challenged by a 5-lens adversarial panel, revised same day · author: T. Studer · branch: 041-forecast-scenario-persistence · builds on specs 036 + 040 · estimate: ~1.5–2 dev days

First write path in the Scenarios section. 036 and 040 were read-only; this spec adds one new table (migration 0026), one new server-action file, and a save/load/rename/delete UI — while the projection engine’s existing functions, the data loader, and every existing figure remain untouched. A saved scenario stores assumptions (the ForecastInputs parameter set), never computed results: on load it is re-projected against whatever the live dataset says today.

1 · Goal & scope

In scope

  • A forecast_scenarios table (new migration 0026): budget_id FK, unique name per budget (case-insensitive, expression index), params jsonb holding the full ForecastInputs, created_by attribution, timestamps.
  • Server actions: listForecastScenarios (read, active budget, creator name joined), createForecastScenario, updateForecastScenario (overwrite params and/or rename; params optional so rename never silently rewrites assumptions), deleteForecastScenario — all admin-gated, Zod-validated, following the ActionResult + revalidatePath + audit-history conventions. Unique-violation races are caught and mapped to the same friendly duplicate-name error as the pre-check.
  • A deterministic active-budget resolution contract: status = 'active' ordered by fiscal_year DESC, LIMIT 1 — hardens the two-active-budgets state the schema permits and makes the integration tests deterministic.
  • A pure engine helper inputsFromSaved(ds, saved) that re-bases any ForecastInputs onto the current dataset: tools that disappeared are dropped, tools that appeared get defaults. Used for loading saved scenarios and for re-basing surviving client state when the dataset prop refreshes.
  • UI: a persistent Saved scenarios card (load / rename / delete, mono empty state), a Save scenario dialog (single primary button; Update-vs-new resolved by an in-dialog mode toggle), active-state tracking (saved:<id> activates the “Your plan” comparison row), inline StatusText feedback (the Nothing-system replacement for toasts).
  • Unit tests (engine merge incl. billing round-trip, Zod schema matrix, auth gating), an integration test (real-DB CRUD round trip with audit + index assertions, deterministic seeding), and a manual Playwright browser pass against live data.

Out of scope

  • Applying a scenario to the budget of record (writing planned_amount_cents) — still the separate follow-up 036 named; saving assumptions is modelling, not budget editing.
  • Per-user/private scenarios, sharing controls, or roles beyond admin — the whole Scenarios section is admin-only; saved scenarios are one shared pool per budget (last-write-wins; overwrites are recoverable from the audit trail, §5).
  • Saved scenarios as extra ghost lines / comparison rows — the loaded scenario is the “Your plan” line; the three H2 presets stay the fixed comparison frame.
  • Conflict detection / locking between admins editing the same scenario — accepted last-write-wins for v1, mitigated by audit snapshots.
  • MCP exposure of saved scenarios — possible follow-up for the read side, not built speculatively.
  • Scenario history / versioning UI — update overwrites; the audit trail records full param snapshots (recoverable forensically, no restore UI).

2 · What a saved scenario is

A saved scenario is a named, shared parameter set: the exact ForecastInputs the client already holds in state — the edited ceiling (cents) plus the per-tool levers (include / growth model / value / burn growth / burn cap / premium share / billing cadence). It is deliberately not a snapshot of results:

Stored: assumptions

  • params.ceilingCents — the modeled ceiling the plan was tuned against (may differ from the live budget ceiling).
  • params.tools[key] — one ToolParams per tool key (api, claude, copilot, cursor, mscopilot), including the Claude billing cadence when yearly (undefined ≡ monthly survives the JSON round trip — JSON.stringify drops undefined keys).
  • A name (≤ 60 chars, unique per budget, case-insensitive) and created_by attribution (surfaced in the list and the delete confirm).

Recomputed: everything else

  • On load, the engine re-projects the saved params against the current dataset — seats, prices, burn, and elapsed actuals as of today. Year-end, breach, drivers all shift with live data, exactly like a preset.
  • The saved-scenarios list shows each entry’s recomputed year-end and Δ explicitly labelled against its own saved ceiling (“vs saved $X”), so the list reads as “what would this plan mean today” and the differing denominator is visible.
  • A saved scenario whose tool keys drift from the live tool set still loads (§6) — extinct keys dropped, new tools defaulted.

Scope rule: scenarios belong to the budget they were tuned against (budget_id FK). The page always lists scenarios for the active budget — when FY2027 activates, FY2026 scenarios disappear from view but survive in the table (and cascade away only if the budget row itself is deleted).

3 · Data model & migration

One table, following the house style (snake_case DB names, camelCase TS, array-form third argument, <table>_<cols>_idx index names). Next journal entry: 0026. 

// Forecast Scenarios (041-forecast-scenario-persistence)
export const forecastScenarios = pgTable(
  "forecast_scenarios",
  {
    id: serial("id").primaryKey(),
    budgetId: integer("budget_id")
      .notNull()
      .references(() => annualBudgets.id, { onDelete: "cascade" }),
    name: varchar("name", { length: 60 }).notNull(),
    // The full ForecastInputs parameter set (type-only import — no runtime dep).
    params: jsonb("params").$type<ForecastInputs>().notNull(),
    createdBy: integer("created_by").references(() => users.id, {
      onDelete: "set null",
    }),
    createdAt: timestamp("created_at").notNull().defaultNow(),
    updatedAt: timestamp("updated_at").notNull().defaultNow(),
  },
  (table) => [
    index("forecast_scenarios_budget_id_idx").on(table.budgetId),
    // One name per budget, case-insensitive ("Plan B" ≡ "plan b").
    uniqueIndex("forecast_scenarios_budget_name_idx").on(
      table.budgetId,
      sql`lower(${table.name})`,
    ),
  ],
);
  • FK choices. budget_id → cascade: scenarios are owned what-ifs of a budget, worthless without it (matches budget_periods). created_by → set null: attribution is informational; deleting a user must not destroy shared scenarios (so the column is nullable; precedent: ingestion_log.uploadedBy).
  • jsonb typing. $type<ForecastInputs>() with import type { ForecastInputs } from "@/lib/scenarios/budget-forecast" — type-only, erased at compile time, no runtime cycle (the engine itself imports nothing from db). Precedent: users.preferences is $type<UserPreferences>().
  • updatedAt maintained in app code on update (house convention — no $onUpdate).
  • relations() block: budget: one(annualBudgets), creator: one(users), mirroring inviteTokensRelations.
  • Migration workflow: pnpm db:generate → review the emitted SQL (additive only: 1 CREATE TABLE, 2 FKs, 2 indexes) with the drizzle-migration-reviewer agent → pnpm db:migrate against the dev DB. Verified against the installed drizzle-kit 0.31.9: the expression index emits as USING btree ("budget_id", lower("name")).
  • db:push caveat (challenge finding): this is the repo’s first expression index, and drizzle-kit’s push diffing does not reliably detect expression changes inside index definitions — this table must go through generate/migrate, and a push-based dev loop should be sanity-checked once against the dev DB.

4 · Validation & (de)serialization

The boundary rule: validate on write and on read. The jsonb column is an open contract — a row written by an older/newer build, or edited by hand, must never crash the page or feed the engine NaN/Infinity. Writes safeParse the params and store parsed.data (canonical shape); reads safeParse each row and skip (with a console.error) any row that no longer conforms.

Schemas live in src/lib/validators.ts (shared client/server, per house rules): 

export const toolParamsSchema = z.object({
  include: z.boolean(),
  model: z.enum(["flat", "linear", "compound"]),
  val: z.number().min(-100_000).max(100_000),
  burnPct: z.number().min(-100).max(100_000).optional(),
  burnCap: z.number().int().min(0).max(100_000_000).optional(),      // ≤ $1M/user/period
  premShare: z.number().min(0).max(1).optional(),
  billing: z.enum(["monthly", "yearly"]).optional(),
});

export const forecastInputsSchema = z
  .object({
    ceilingCents: z.number().int().min(0).max(100_000_000_000),      // ≤ $1B
    tools: z.record(z.string().min(1).max(40), toolParamsSchema),
  })
  .refine((v) => Object.keys(v.tools).length <= 20, {
    message: "Too many tool entries",
  });

export const forecastScenarioNameSchema = z.string().trim().min(1).max(60);

export const createForecastScenarioSchema = z.object({
  name: forecastScenarioNameSchema,
  params: forecastInputsSchema,
});
export const updateForecastScenarioSchema = z.object({
  id: z.number().int().positive(),
  name: forecastScenarioNameSchema,
  params: forecastInputsSchema.optional(),   // omitted = rename-only, stored params untouched
});
export const deleteForecastScenarioSchema = z.object({
  id: z.number().int().positive(),
});
  • Strip, don’t strict (challenge revision). Plain z.object (Zod’s default strip semantics, the only style used in validators.ts): unknown keys are dropped, not rejected. On write that keeps the stored shape canonical (we insert parsed.data); on read it keeps rows loadable if a future build adds-then-removes a field. .strict() would turn schema drift into save failures and skipped rows — worse availability for zero practical safety gain.
  • Non-finite protection is built in: Zod 4’s z.number() rejects NaN/Infinity by default (.finite() is a documented no-op in v4 and is not used). Nothing non-finite can reach Math.pow.
  • Bounds are generous modelling limits, not business rules — wide enough for any sane what-if, tight enough to keep arithmetic and rendering safe. ceilingCents: 0 is deliberately accepted (the UI guards the accidental-empty-field path, §7).
  • Type-level round trip: two type-only assignments (schema output → ForecastInputs, ForecastInputs → schema input) live in the validator test file and are enforced by pnpm typecheck (tests are in the tsconfig include), not by the vitest run.

5 · Server actions

New file src/actions/forecast-scenarios.ts ("use server") — CRUD stays out of scenarios.ts, which holds only the cached dataset loaders. All four follow the house conventions: requireAdmin() first, safeParse against unknown, ActionResult<T> result shape, audit history, revalidatePath("/scenarios/budget-forecast") after writes.

Active-budget resolution contract (challenge must-fix). All actions resolve the active budget server-side — never trusted from the client — as status = 'active' ordered by fiscal_year DESC, LIMIT 1. The schema permits multiple active rows; an unordered findFirst would be nondeterministic there (and made the integration-test seeding pattern unsafe). Ordering by fiscal year makes production behaviour well-defined and lets tests seed a far-future active budget that deterministically wins resolution.
Action Behaviour
listForecastScenarios() Read. Admin gate returns [] — defense-in-depth only: the /scenarios layout already redirects non-admins and the sibling dataset loader throws first in Promise.all. Resolves the active budget (contract above); returns its scenarios ordered by name, each row’s params re-validated with safeParse (invalid → skipped + console.error). Returns { id, name, params, creatorName, updatedAt } (users left-joined, updatedAt as ISO string). Uncached — the page is already dynamic (auth) and the query is a single indexed select; freshness beats a cache here.
createForecastScenario(input: unknown) Validate → resolve active budget (error: "No active budget" if none) → cap check (≤ 50 per budget, pre-check only — see §10) → case-insensitive duplicate-name pre-check (friendly error) → insert with createdBy: Number(admin.id), unique-violation (PG 23505) caught and mapped to the same duplicate-name error (the race path must honour the ActionResult contract too) → recordCreation("forecast_scenario", id, adminId) → revalidate. Returns { id }.
updateForecastScenario(input: unknown) Validate → load row (error: "Scenario not found") → duplicate-name pre-check excluding self → update name, params (only when provided — rename-only leaves stored params untouched), updatedAt: new Date(), 23505 caught as above → recordUpdate(...) with a name diff when renamed and a full params snapshot ({ params: { old: <previous object>, new: <next object> } }) when params change — so a teammate’s overwritten plan is recoverable from change_history, and a params-only update never hits recordUpdate’s empty-diff early-return (challenge finding) → revalidate. Returns { id }.
deleteForecastScenario(id: number) Validate id → load row → snapshot into the audit trail (deleteBilledCost pattern: name + params recorded as previousValue before db.delete) → delete → revalidate. Returns { id }.
  • change_history.entity_type is a free-form varchar(50) — "forecast_scenario" needs no enum migration.
  • page.tsx loads the list alongside the dataset (Promise.all); after a mutation, revalidatePath + the client’s router.refresh() re-render the page with the fresh list while client state (the user’s current inputs) survives — and is re-based if the dataset itself changed (§7).

6 · Engine changes

One additive pure function in src/lib/scenarios/budget-forecast.ts — no signature changes, no new imports: 

/**
 * Re-base a parameter set onto the current dataset. Tools that no longer
 * exist are dropped; tools that appeared since the params were captured get
 * DEFAULT_PARAMS — so a stale scenario (or surviving client state after a
 * dataset refresh) always yields a complete, renderable input set.
 */
export function inputsFromSaved(
  ds: ForecastDataset,
  saved: ForecastInputs,
): ForecastInputs {
  const tools: Record<string, ToolParams> = {};
  for (const tool of ds.tools) {
    const p = saved.tools[tool.key];
    tools[tool.key] = p ? { ...p } : { ...DEFAULT_PARAMS };
  }
  return { ceilingCents: saved.ceilingCents, tools };
}

Mirrors inputsFromPreset’s shape (copy semantics, dataset-scoped keys) so the client can treat presets and saved scenarios uniformly. Params are copied verbatim — including the claudeSeats billing cadence, which is what makes “load restores the cadence” true (pinned by a unit test). projectForecast, the presets, and all result types are untouched.

10 · Risks & decisions

Topic Decision / mitigation
Shared vs per-user scenarios Shared pool per budget, last-write-wins. The tool exists so budget owners can align on a plan; private drafts would fragment that. Mitigations: creator attribution surfaced in the list and delete confirm; full params snapshots in change_history on update and delete, so an overwritten plan is recoverable forensically. Flagged in the notes as the one interpretive call worth explicit user confirmation.
Stale params vs live dataset Saved params are re-based on load (inputsFromSaved) and re-projected against live data — never stored results. Extinct tool keys dropped, new tools defaulted. The same helper re-bases surviving client state when the dataset prop refreshes mid-session (closes the hidden-tool hole router.refresh() would otherwise open).
jsonb rot Zod safeParse on every read; non-conforming rows are skipped with a logged error instead of crashing the page (covered by an integration case). Strip semantics keep rows loadable across schema evolution; writes store parsed.data, keeping the stored shape canonical.
Duplicate names / races App-level case-insensitive pre-check for a friendly message; uniqueIndex(budget_id, lower(name)) as the DB backstop — and the backstop’s 23505 is caught and mapped to the same friendly error, so the race path honours the ActionResult contract instead of surfacing a Next.js digest (challenge finding).
Unbounded growth Cap of 50 scenarios per budget with an explicit error. Pre-check only — two concurrent creates at 49 can land 51 rows; accepted as harmless (no DB backstop by design; the cap is a UX guardrail, not an invariant).
Active-budget race / split-brain Saving resolves the active budget server-side at write time under the §5 ordering contract. If another admin activates a different budget mid-session, the save lands on the new active budget and the refreshed list shows it; the charts may keep rendering the old budget’s cached dataset for up to 1h (the dataset cache is not tag-invalidated by budget activation — pre-existing). Accepted: budget activation is a rare, admin-driven event; a hard refresh resolves the split view. Documented rather than hidden.
Ceiling semantics on load Loading a saved scenario restores its saved ceiling (full assumption set, exact string sync — no rounding drift). Preset tiles keep 040’s reset-to-live-ceiling behaviour. The two affordances answer different questions (“this plan as tuned” vs “this preset against the live budget”).
Saved-row scoring Rows are scored against their own saved ceiling, with the denominator made explicit in the row (“vs saved $X”) so the two Δ semantics on one page can’t be misread (challenge finding). Scoring against the page’s transient edited ceiling would make the list jitter.
Accidental shared-row overwrite Three guards (challenge findings): preset-tile clicks clear loadedSavedId (no “Update” offer for preset params); the Update offer is derived from the live savedScenarios prop (a concurrently-deleted row withdraws the offer); the save dialog echoes exactly what will be saved and blocks an empty/cleared ceiling field.
Feedback affordance StatusText/useInlineStatus, not Sonner — toasts are deprecated in the Nothing design system (one legacy usage left app-wide). Card-header status + in-dialog status (two-channel house pattern).
Cache coherence The scenario list is an uncached read on a dynamic page; mutations revalidatePath. The dataset loader’s unstable_cache is untouched (scenario writes don’t change live cost data).
Role & sensitivity Admin-only end to end (requireAdmin in every action; the layout already gates). Params contain no secrets — growth assumptions and a ceiling.

  • No active budget → saving fails with a clear error; the page’s existing empty state is unchanged.
