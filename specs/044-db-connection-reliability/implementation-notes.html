Running log for the database connection reliability incident fix: how the diagnosis was grounded, what the challenge pass changed, and what was verified.

2026-08-04 · implemented & verified

Investigation

Diagnosis grounded in production data, not inferencemethod

Root causes were derived from Vercel runtime error groups and logs rather than from reading code and guessing. That is what dated the incident (symptoms first appear 2026-06-16/17), tied symptom A to the :00-past-the-hour cron collision, and excluded today's deploy ea50404 as the trigger.

The pooled-vs-direct question decided everythingkey fact

Whether raising max is safe or catastrophic depends entirely on which Neon endpoint is deployed. Resolved by extracting the host (credentials redacted) from the main checkout's .env.local: ep-little-frost-alw6tlsf-pooler…. Pooled — so raising max adds PgBouncer client sockets, not Postgres backends.

The same fact makes RC-3 worse: Neon's docs list session advisory locks as unsupported on exactly this endpoint.

Challenge pass

Five parallel code explorers (Sonnet), one plan drafter and three adversarial lenses — concurrency, correctness, blast radius (Opus, high effort). All three lenses returned not-ready on the draft: 5 fatal, 13 serious, 4 minor objections. Every load-bearing objection was independently verified before being accepted or rejected.

Workflow defect: the incident brief never reached the agentsdeviation

args was passed as a JSON-encoded string rather than a JSON value, so args.rootCause was undefined and every prompt interpolated the literal text "undefined". The drafting agent flagged this itself.

Impact was contained: the five explorer prompts were self-contained and code-grounded, so exploration was unaffected. The planner and challengers reasoned without symptom data — which is precisely why their conclusions were re-verified against the real logs rather than adopted.

Objection accepted: pool.on("error") alone is insufficientverified

Claim: checked-out clients have no error listener. Verified by probing the vendored driver:

_acquireClient removes idle listener: true
_release re-attaches:                true
query() adds its own once('error'):  false
connect() adds its own:              false

Worse than the objection stated — it assumed query() compensated; in 1.0.2 it does not. So a socket death between statements inside a db.transaction() had nothing listening. Also verified that _acquireClient removes only its named listener, so a listener added via pool.on("connect") survives checkout. Both handlers shipped.

Objection rejected: the "null ws" TypeError crashdisproved

The strongest fatal objection claimed the real crash was an uncaught TypeError: Cannot read properties of null (reading 'close') from the driver's connect-timeout path, invisible to pool.on("error") — and therefore that max must not be raised until it was neutralised.

The code path is real: destroy() → end() → write(alloc(0)) short-circuits and synchronously calls this.ws.close(). But on the Node runtime this.ws is assigned synchronously inside connect(), which newClient calls immediately after arming the timer. The null window only exists on the fetch-fallback (Cloudflare Workers) path, which this app never takes.

Confirmed by direct probe against a non-routable host:

error listeners at construction: 0
CASE1 emit w/o listener: THREW Error - synthetic idle-client error
CASE2 rejected: Error - Connection terminated due to connection timeout
uncaught after connect-timeout: NONE

The connect-timeout path rejects cleanly. Independently, no TypeError group appears in the 7-day production error aggregation, while the EventEmitter path appears 18 times. Conclusion: the objection's mechanism is not reachable here; the gate on raising max was dropped. Its secondary point — 10s is tight against a scale-to-zero compute — was accepted, hence connectionTimeoutMillis: 15_000.

Objection accepted: invoice-sync.ts is dead codeverified

The exploration dossier called it a live second advisory-lock implementation and recommended migrating it. A later lens contradicted this. Checked directly: the lock is guarded by if (!dryRun), and the only caller in the repo (scheduled-jobs-table.tsx:101) passes { dryRun: true }. Unreachable. Removed from scope entirely — this deleted a whole risky workstream.

Objection accepted: the dashboard poll is a self-sustaining load sourceadopted

Not in the original diagnosis and genuinely valuable: a single stranded in_progress row made every open admin tab issue a real query every 5s forever, with no document.hidden check. Fixed both server-side (unconditional sweep) and client-side (10-minute cap plus an abandoned-id guard so the 30s loop cannot immediately re-arm on the same row).

Scope call: the TTL lease was deferreddeviation

The challenge pass argued hard for replacing the advisory lock now. Deferred deliberately — it needs a migration, and this repo has no automated migration step, so it requires a schema-first deploy verified against production. It also cannot be tested here: the worktree has no credentials, and the integration suite crashes the vitest worker without them rather than failing cleanly.

What shipped instead makes the existing lock loud and self-healing rather than silent: no-op releases are logged, the release is total, bookkeeping can no longer mask a real error, and stranded rows are swept. The observed manifestation of symptom A was connection starvation, which RC-1's fix addresses directly.

vercel.json comment reverteddeviation

A _comment key was added to explain the stagger, then removed: vercel.json is schema-validated and unknown top-level keys fail the deploy. Rationale lives in the plan doc instead.

Review pass

PR #126. Sole reviewer: the GitHub Copilot review bot. One inline comment, accepted.

Accepted · the reaper could out-live-run a long backfillfixed

Copilot: "an active backfill that legitimately exceeds 60 minutes can be incorrectly reaped on the next cron attempt, even though the job is still running."

Valid, and the same hazard the challenge pass raised independently. In practice the maxDuration = 300 added in this same PR bounds every entrypoint — cron routes and the /settings/sync segment that dispatches the manual trigger and backfill server actions — so no run can currently reach 60 minutes. But that made the sweep's safety rest on an implicit invariant: raise the ceiling later and it would silently begin reaping live backfills.

Fixed by making the invariant explicit and giving backfills their own headroom:

  • SYNC_MAX_DURATION_SECONDS now mirrors the route ceiling in the same module, so the margin is expressed against the thing that actually bounds a run.
  • STALE_EVENT_AFTER_MS became per-operation — 1h regular (12× the ceiling), 6h backfill (72×) — and the sweep predicate is now an OR over operationType.
  • Two invariant tests: every cutoff must exceed 10× the ceiling, and backfill must exceed regular. These fail if someone raises maxDuration without revisiting the cutoffs.
