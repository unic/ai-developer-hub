Database Connection Reliability

Production incident fix. Three error signatures on ai-developer-hub traced to the shared Neon connection layer: process-killing crashes from unhandled connection faults, connection starvation from a max: 1 pool under Fluid Compute, and a sync lock that cannot work on Neon's pooled endpoint.

2. Root causes

RC-1 · max: 1 pool starved by concurrent worksymptom A + B

src/lib/db/index.ts constructs a module-level singleton with max: 1. The original design note (specs/001 research.md:24) justifies this as "one connection per serverless function instance" — an assumption that predates Fluid Compute, which reuses one instance across concurrent invocations.

Three amplifiers stack on it: both hourly crons fired at 0 * * * *; src/actions/dashboard.ts:126 fans out 9 concurrent queries then 3 more; getAssignments() (src/actions/assignments.ts:637) is unbounded with three lateral joins.

Evidence chain at 12:00 UTC: api-costs cron starts 12:00:41 → usage cron's first query fails 12:00:49 → GET / fails 12:00:50 and 12:01:06, all with connect timeouts.

RC-2 · No error listener on either pool objectsymptom C

Verified empirically against @neondatabase/serverless 1.0.2. Two distinct objects, both unguarded:

  • Idle clients — the driver re-emits a dead socket's error onto the Pool. pool.emit("error", …) with no listener throws synchronously (confirmed by probe). This is the production stack: idleListener → emit → Unhandled error.
  • Checked-out clients — _acquireClient removes the driver's idle listener on checkout, and in 1.0.2 neither query() nor connect() re-attaches one (probed: both false). While a query is in flight the error rejects that promise; between statements inside a db.transaction() there is nothing to route it to.

Under Fluid Compute one uncaught exception tears down an instance serving many concurrent invocations — hence exit 129 across unrelated routes.

RC-3 · Session advisory locks are unsupported on the pooled endpointlatent

Production DATABASE_URL is ep-little-frost-…-pooler…. Neon's connection-pooling documentation lists "Session-level advisory locks" under Not supported with pooled connections (PgBouncer pool_mode=transaction).

The repo already knew: vitest.config.integration.mts:14 documents this exact failure and works around it by repointing DATABASE_URL at DATABASE_URL_UNPOOLED — but only for tests. Production was never protected.

So withSyncLock's mutual exclusion is not merely racy across checkouts; it is structurally unreliable, and can fail in both directions (a leaked lock that blocks forever, or a re-entrant false grant on a shared session).

RC-4 · Failures were invisible, and one stranded row generated permanent load

cron-handler.ts returned HTTP 200 for every outcome, including unexpected errors — which is why 63 cron failures over seven weeks never showed as anything but a green tick.

Separately, the sync dashboard's 5s fast poll exits only when nothing is in_progress, and the 30s poll re-arms it whenever it sees one. A row stranded by a killed sync therefore made every open admin tab query the database every 5 seconds indefinitely — and unlike the 30s loop, the fast loop did not check document.hidden.

Why max: 10 is safe here

Neon's pooler accepts max_client_conn=10000 and sizes its server pool at 0.9 × max_connections. Raising the client-side max adds sockets to PgBouncer, not Postgres backends. Had DATABASE_URL been the direct endpoint this change would be unsafe — that was the gating question, and it is resolved.

4. Deliberately deferred

The adversarial pass surfaced a wider set of real defects. These are excluded from the incident fix because each needs a migration, live database credentials, or a data audit — none of which are available in a credential-less worktree, and none of which should be entangled with a fix that needs to ship.

D-1 · Replace the advisory lock with a TTL row leasenext

A sync_locks table (source_type PK, holder, expires_at) with an atomic INSERT … ON CONFLICT … WHERE expires_at < now() acquire and a holder-guarded release. Immune to both the scatter and re-entrancy failures of RC-3.

Blocked by: needs migration 0030 and there is no automated migration step (build is next build; db:migrate is manual), so it requires a schema-first deploy verified against production before the reading code ships. Also needs the real concurrency test at tests/integration/sync/lock.test.ts:22, still an it.todo.

D-2 · Convergent writes for invoice matchingmoney

billed_costs has no unique constraint, and invoice matching corrects via DELETE+INSERT keyed on its own snapshot. Every safety argument there rests entirely on the lock. A partial unique index on (period_id, vendor_reference) plus an upsert would make it safe regardless of lock behaviour. Needs a duplicate audit first, since overlapping runs may already have occurred.

D-3 · Retry once on connection-level errors

idleTimeoutMillis is a setTimeout, and timers do not advance while a Fluid instance is frozen between invocations — so the first query after a resume can still be handed a stale socket. A single retry would close this. Deferred because doing it properly means a query-layer wrapper across ~57 consumers and wants real-DB testing.

D-4 · Performance follow-ups

Dashboard fan-out dedup (getBudgetWithCosts is computed three times per render); bounding getAssignments(); backfill resumability (a 24-month Copilot backfill cannot fit in any maxDuration and has no checkpoint).

D-5 · Dead code: invoice-sync.ts advisory lock

Its lock is guarded by if (!dryRun) and the sole caller (scheduled-jobs-table.tsx:101) passes dryRun: true. Unreachable — hence excluded from the framework rewrite rather than migrated alongside it. Separate cleanup.

5. Operational notes

Pre-existing leaked locks are not cleared by this changeaction

If an advisory lock is currently leaked on a pooler backend, nothing here releases it — it persists until that backend recycles. If a source stops syncing after deploy, a Neon compute restart is the fastest remedy.

Behaviour change: cron responsesmonitoring

Cron endpoints now return 409/500 instead of a blanket 200. Any monitoring that asserted "cron returns 200" will start reporting the failures that were always happening. That is the point, but it should be expected rather than mistaken for a new regression.
