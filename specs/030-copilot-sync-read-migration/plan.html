Implementation Plan: Copilot + Members Sync Migration

Spec ID: 030-copilot-sync-read-migration  ·  Branch: fix/copilot-sync-read-paths (rename to chore/sync-events-consolidation on push)  ·  Date: 2026-05-21  ·  Owner: tobias.studer@unic.com  ·  Bug fix Scope expansion: GitHub members
Two bugs, one fix. The Copilot UI shows "Last sync" frozen at 2026-03-25 because Copilot reads still query the legacy github_sync_events table while writes now go to sync_events. GitHub Member sync is in the inverse trap: it still writes to github_sync_events, but the /settings/sync dashboard reads only sync_events, so the github_members row on the dashboard never shows real activity. Consolidating both flows onto sync_events in one PR removes the legacy table from active use entirely.

1. Summary

Consolidate the GitHub Copilot and GitHub Member sync flows onto the new sync_events framework so both write through withSyncLock and both are read by the same query helpers. This unfreezes the Copilot "Last sync" indicator, populates the dormant github_members row on /settings/sync, and deletes the dead legacy orchestrator (runCopilotSync).

What changes

  • Copilot reads: 3 server actions rewritten to query sync_events (source_type = github_copilot_billing).
  • Members writes: confirmGitHubSync() wrapped in withSyncLock; writes to sync_events (source_type = github_members) instead of github_sync_events.
  • Shared: 1 new helper module src/lib/sync/queries.ts.
  • Cleanup: Delete runCopilotSync, the obsolete getSyncHistory() in github-sync.ts, and the unused pass-through in src/lib/sync/sources/github-members.ts.

What does NOT change

  • github_sync_events table is kept in place (no DROP migration in this PR) — see §D5.
  • No schema migrations required.
  • The Copilot UI components themselves: contract preserved.
  • The Member Sync Sheet flow (preview, conflict resolution): only its persistence path changes.
  • Cron schedule entries in vercel.json.

3. Root cause analysis (both flows)

3.1 Copilot — split-brain reads

The write path was migrated on 2026-03-25:

// NEW (live): src/lib/sync/sources/github-copilot.ts
withSyncLock({ sourceType: 'github_copilot_billing' }, ...) → INSERT INTO sync_events

// OLD (dead since 2026-03-25): src/lib/copilot-sync.ts → runCopilotSync()
INSERT INTO github_sync_events ...

But three server actions still query github_sync_events with syncType='copilot', so ORDER BY completed_at DESC LIMIT 1 returns the last legacy row (2026-03-25) forever.

3.2 Members — write path never migrated

The mirror image: confirmGitHubSync() (src/actions/github-sync.ts:134–513) still writes directly to github_sync_events with syncType='members'. There is a stub wrapper at src/lib/sync/sources/github-members.ts that accepts pre-computed counts and calls withSyncLock, but nothing calls it. Meanwhile the /settings/sync dashboard reads only sync_events, so the github_members row never lights up after a manual sync.

Why this duplicates the bug. The Copilot bug is "reads point at the wrong table." The members bug is "writes point at the wrong table." Both come from the same incomplete migration; fixing them together costs little extra effort and lets us retire github_sync_events as a follow-up.

4. Scope & out-of-scope

In scope

  • Copilot reads → sync_events. Rewrite getCopilotSyncStatus, getCopilotActivityTimeline, getCopilotBillingSyncHistory.
  • Members writes → sync_events. Wrap confirmGitHubSync() in withSyncLock({ sourceType: 'github_members' }); map members-specific counts onto the generic createdCount / updatedCount / skippedCount / errorCount contract (see §7).
  • Status mapping helper. New file src/lib/sync/queries.ts with getLastCompletedSyncEvent, listSyncEvents, and mapOutcomeToLegacyStatus. Used by Copilot read actions; available to future sources.
  • Dead-code removal.
    • runCopilotSync in src/lib/copilot-sync.ts:481–592 (zero callers — confirmed by audit).
    • getSyncHistory() in src/actions/github-sync.ts:515–557 (legacy reader; superseded by getSyncHistory() in src/actions/sync.ts; no UI references).
    • Pass-through wrapper in src/lib/sync/sources/github-members.ts — replaced by inline withSyncLock usage inside confirmGitHubSync().
  • Tests. Unit tests for the new helper; integration tests that prove both the Copilot last-sync read advances and the members row on the dashboard updates after a confirm.

Out of scope (deliberately)

  • Dropping github_sync_events. Keep the table in place for one release as a safety net; a follow-up PR can drop it once we've confirmed no surface depends on historical rows. See §D5.
  • Persisting members-specific counts (totalMembers, matchedCount, conflictCount, …). The new schema has only generic counts. We accept the loss of granular history since no UI currently displays those columns from history; the in-flight Member Sync Sheet still surfaces them at preview/confirm time from live data.
  • Connection-level lastSyncAt. githubConnections.lastSyncAt is updated by the members orchestrator and read by the GitHub integration card. Leave that update in place; do not retarget the card. Removing the column would be a destructive schema change with no UI benefit.
  • UI label tweaks. The Member Sync Sheet's preview counts come from a live GitHub API call, not from github_sync_events — no copy change needed there.

6. Design decisions

D1. Preserve the CopilotSyncStatus public shape

The UI consumes lastSyncStatus: "completed" | "partial" | "failed" | null. The new framework uses outcome: "success" | "partial" | "failed" | "in_progress". Map at the server-action boundary so no .tsx changes ripple out:

const lastSyncStatus =
  lastEvent?.outcome === "success" ? "completed"
  : lastEvent?.outcome === "partial" ? "partial"
  : lastEvent?.outcome === "failed"  ? "failed"
  : null; // 'in_progress' is filtered out by the query

D2. Drop connectionId as a Copilot read filter

The new sync_events table is connection-agnostic — the Copilot orchestrator picks the single active connection at runtime. Drop the connectionId filter in Copilot reads. (Multi-connection support is future work and would require a schema extension regardless.)

D3. Wrap confirmGitHubSync() with withSyncLock directly

Rather than route through the stub wrapper in src/lib/sync/sources/github-members.ts, call withSyncLock from inside confirmGitHubSync(). This keeps the orchestration (transaction, conflict resolution, count tabulation) co-located with the side effects it produces, and it lets withSyncLock's lifecycle handle the in_progress → success/partial/failed transitions instead of duplicating that logic.

// src/actions/github-sync.ts — confirmGitHubSync (shape)
return withSyncLock(
  { sourceType: 'github_members', triggeredBy: actor.id },
  async (eventId) => {
    // existing logic: validate, open tx, insert/update users, link members
    // …
    // (still update githubConnections.lastSyncAt in the same tx)
    return {
      createdCount: importedCount,
      updatedCount: matchedCount + manuallyMatchedCount,
      skippedCount: unmatchedCount,
      errorCount: conflictCount,
    };
  }
);

The advisory lock keyed on github_members prevents two members syncs running at once — a meaningful guarantee given the interactive nature of the flow.

D4. Map members-specific counts → generic counts

The new schema has four generic count columns. Map members concepts onto them as below (see §7 for the full table). Accept loss of totalMembers (snapshot of org size) — it's not displayed in any history UI and is re-derivable from a live GitHub API call.

D5. Keep github_sync_events in place this PR

Both Copilot and members will write/read only sync_events after this change. github_sync_events becomes dormant. Two options:

OptionProsConsPick?
A. Drop the table in this PR with a Drizzle migration. Codebase ends with a single sync-events table; less confusion for newcomers. Destructive; loses historical rows from before 2026-03-25 (mostly members data). Couples the bug fix to a schema change. No
B. Leave the table; remove all code references; drop in a follow-up PR after one stable release. Reversible: if a regression appears, restoring old reads is one revert. Historical data preserved for one release as a debugging aid. One more PR to schedule. Yes

D6. Centralize Copilot queries in a small helper module

One new file src/lib/sync/queries.ts with three functions. Source-type-agnostic, so future migrations can reuse it. See §8 for the full source.

8. Change-by-change implementation

Change 8.0 — New file src/lib/sync/queries.ts

import { db } from "@/lib/db";
import { syncEvents } from "@/lib/db/schema";
import { and, desc, eq, ne } from "drizzle-orm";
import type { SyncSourceType } from "@/lib/sync/framework";

export async function getLastCompletedSyncEvent(sourceType: SyncSourceType) {
  return db.query.syncEvents.findFirst({
    where: and(
      eq(syncEvents.sourceType, sourceType),
      ne(syncEvents.outcome, "in_progress"),
    ),
    orderBy: [desc(syncEvents.completedAt)],
  });
}

export async function listSyncEvents(sourceType: SyncSourceType, limit: number) {
  return db
    .select({
      id: syncEvents.id,
      startedAt: syncEvents.startedAt,
      completedAt: syncEvents.completedAt,
      outcome: syncEvents.outcome,
      createdCount: syncEvents.createdCount,
      updatedCount: syncEvents.updatedCount,
      errorCount: syncEvents.errorCount,
      errorMessage: syncEvents.errorMessage,
    })
    .from(syncEvents)
    .where(eq(syncEvents.sourceType, sourceType))
    .orderBy(desc(syncEvents.startedAt))
    .limit(limit);
}

export function mapOutcomeToLegacyStatus(
  outcome: "in_progress" | "success" | "partial" | "failed" | null | undefined,
): "completed" | "partial" | "failed" | null {
  if (outcome === "success") return "completed";
  if (outcome === "partial" || outcome === "failed") return outcome;
  return null;
}

Change 8.5 — Rewrite confirmGitHubSync() in src/actions/github-sync.ts

Wrap the existing body in withSyncLock. Remove the four direct touches to githubSyncEvents (L170–179 insert, L454–465 success update, L500–506 failure update). The lock helper takes over the lifecycle. Keep the githubConnections.lastSyncAt update — it's a separate concern used by the integration card.

Skeleton 
export async function confirmGitHubSync(input: ConfirmGitHubSyncInput) {
  /* …existing input validation, actor lookup, connection lookup… */

+ const result = await withSyncLock(
+   { sourceType: "github_members", triggeredBy: actor.id },
+   async (_eventId) => {
      const counts = {
        importedCount: 0,
        matchedCount: 0,
        manuallyMatchedCount: 0,
        unmatchedCount: 0,
        conflictCount: 0,
      };

      try {
        await db.transaction(async (tx) => {
          /* …existing user inserts, conflict resolution, link writes… */
          /* …compute counts.* values from preview + resolutions… */

          await tx
            .update(githubConnections)
            .set({ lastSyncAt: new Date() })
            .where(eq(githubConnections.id, connection.id));
        });
      } catch (err) {
        return {
          createdCount: counts.importedCount,
          updatedCount: counts.matchedCount + counts.manuallyMatchedCount,
          skippedCount: counts.unmatchedCount,
          errorCount: counts.conflictCount + 1,
          errorMessage: err instanceof Error ? err.message : String(err),
        };
      }

      return {
        createdCount: counts.importedCount,
        updatedCount: counts.matchedCount + counts.manuallyMatchedCount,
        skippedCount: counts.unmatchedCount,
        errorCount: counts.conflictCount,
      };
+   },
+ );

  return { success: true, eventId: result.eventId };
}

Subtlety: the original action handles a thrown error by writing a failed row and rethrowing. withSyncLock already does that on a thrown callback. Two ways to handle our case:

  1. Throw inside the callback on hard failures — withSyncLock marks the row failed and rethrows. Use for unexpected exceptions.
  2. Return counts with errorCount > 0 for soft failures (e.g. conflicts that prevent some rows but not others) — withSyncLock picks partial or failed automatically based on the create+update vs error counts.

The skeleton above uses option 1 implicitly (if the tx throws, return a populated counts object and surface the message). Either approach is fine; pick one consistent style at implementation time.

12. Risks & rollback

RiskLikelihoodMitigation
Hidden caller of runCopilotSync or legacy getSyncHistory. Low Strict-mode TypeScript + grep audit. CI fails before merge.
Status-enum mapping bug for Copilot. Low Unit test covers all five branches.
Loss of totalMembers snapshot breaks an unanticipated consumer. Low Audit confirmed no UI surface displays it from history. Document the loss in the migration note.
Members advisory lock collides with a legitimate in-progress sheet flow if the user retries quickly. Medium The lock releases automatically on commit/rollback. Surface a friendly toast for the "Sync already in progress" error in the sheet UI if needed (follow-up if the existing error path isn't already user-friendly).
Conflict-count mapped to error_count changes the outcome computation in withSyncLock in unexpected ways (e.g. a sync with 5 conflicts but 1000 successful matches is now partial not completed). Medium Document the new outcome semantics. This is arguably more accurate than the legacy completed-with-conflicts state.

Rollback. Revert the PR. No schema changes, no destructive operations — clean revert. Historical Copilot rows in sync_events remain (harmless); members continue to write to github_sync_events again.
