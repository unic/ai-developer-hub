Implementation Notes — Copilot + Members Sync Migration

Spec: specs/030-copilot-sync-read-migration/plan.html  ·  Branch: worktree-copilot-bugfix  ·  Started: 2026-05-21

Running log of design decisions, deviations, tradeoffs, and open questions while implementing the plan. Last-write-wins ordering — newest sections appended at the bottom.

T5: Members write path

Design Preserve disaggregated action return shape

The action's data field still returns the original six-field breakdown (enrichedCount, importedCount, manuallyMatchedCount, createdCount, skippedCount, conflictCount) because GitHubMemberSyncSheet uses it to display the post-confirm summary. Only the persistence to sync_events uses the generic four-count shape. This means the UI sees no regression.

Tradeoff Hard errors throw vs. soft errors return

Plan §8.5 gave two options for error handling inside withSyncLock's callback. I went with a hybrid:

  • Validation errors accumulated during the tx (duplicate email, conflicting GitHub login) become entries in the existing errors[] array, which I now pass through to withSyncLock as a non-null errorMessage. conflictCount flows into the generic errorCount. withSyncLock then picks partial or failed based on writes-vs-errors.
  • Unexpected exceptions from the tx bubble up and let withSyncLock mark the row failed + rethrow. The outer try/catch converts that to { success: false, error }.

The legacy implementation silently dropped the errors[] array (never propagated to the caller). The new path also doesn't show those errors to the caller in the success response, but they now do persist on the sync_events row's error_message column — visible in /settings/sync's history. That's a small visibility improvement.

Deviation Removed github_members dispatcher case in src/actions/sync.ts

The plan said to delete src/lib/sync/sources/github-members.ts. Doing so broke a dynamic import in src/actions/sync.ts:56 (the generic triggerSync dispatcher). The plan didn't anticipate this caller, because the audit identified the stub as having no UI callers — but the dispatcher was a programmatic caller.

Fix: replaced the dispatcher branch with return null and a comment that members sync is interactive (mirroring the existing anthropic_team_invoices branch). The dispatcher's null path returns a friendly "this source does not support manual triggering" error if anyone ever hits it. Confirmed via the audit that no UI surface calls triggerSync('github_members') — the "Sync Now" button on the scheduled-jobs row instead opens GitHubMemberSyncSheet.

T2–T4: Copilot read paths

Tradeoff Timeline status mapping fallback

The plan said to map outcome → legacy status via the helper. The activity-timeline rendering, however, was already lenient (it just passed status through as a string). To avoid silently swallowing the in_progress state on a live-running sync, the timeline now does:

status: mapOutcomeToLegacyStatus(evt.outcome) ?? evt.outcome

i.e. success → "completed", partial → "partial", failed → "failed", and in_progress falls through as the literal string "in_progress". Same shape the UI saw before (the legacy table used in_progress too), so no UI change needed.

Alternative: filter out in_progress rows in listSyncEvents. Rejected because the timeline should show currently-running syncs for visibility.

Deviation getCopilotBillingSyncHistory exposes createdCount as billingProcessed

Plan §7.1 mentioned this mapping. Implementation keeps the public field name billingProcessed identical (the UI label stays "Billing processed") and just plumbs row.createdCount through. This means no UI changes are needed and the semantic shift is invisible at the call site. If we later split billing vs seats vs metrics counts in the new framework, we can reintroduce a distinct field.

Design Property-holder pattern for closure-mutated state

TypeScript's strict mode wouldn't narrow a let detailedCounts: T | null = null after a != null guard once the variable was mutated inside an async closure — it treats the read as never (the closure mutation isn't tracked across the await boundary). Workaround: wrap in a mutable object, const detailed: { counts: T | null } = { counts: null }. Property access through a const-bound object narrows properly. Documented at the declaration site.

PR #95 review responses

The Copilot PR reviewer left three inline comments. All three addressed in a follow-up commit.

Design 1. Lock acquired before GitHub API fetch

Reviewer: "confirmGitHubSync calls fetchAndMatchMembers() (GitHub API + per-member profile fetch loop) before acquiring the withSyncLock advisory lock. That means two concurrent confirms can both burn rate limit / do expensive work."

Applied: Moved fetchAndMatchMembers() inside the withSyncLock callback. The second concurrent confirm now fails at the lock with "Sync already in progress" before issuing any GitHub calls. If the fetch itself fails inside the lock, the callback returns counts with errorCount: 1 + the fetch error message, so the failure shows up in the sync history (an unexpected upside — previously a rate-limit error from the preview-style call was invisible). The outer action still returns { success: false, error } for the UI via a new prefetchError guard.

Note for the preview path: fetchGitHubSyncPreview (called from the sheet on open) still calls fetchAndMatchMembers() outside any lock. That's the right call — it's a read-only preview, doesn't write, and multiple admins should be able to inspect concurrently. Only the confirm path holds the advisory lock.

Design 2. errorMessage capped + summarized

Reviewer: "errorMessage is built by joining all validation errors, which can get very large… Consider truncating to a reasonable max length (similar to the 1000-char cap in withSyncLock's failure path) or storing only the first N errors plus a summary count."

Applied: Extracted a summarizeErrors(errors[]) helper into src/lib/sync/error-message.ts. It honors the same 1000-char cap as withSyncLock's catch path, greedily includes complete messages until the budget runs out, and appends a … (+N more) suffix so the UI surfaces the dropped count. Covered by a 5-case unit test, including the edge case where the very first message alone overflows the cap.

Design 3. Spec snippet drift fixed

Reviewer: "The implementation-plan snippet for getLastCompletedSyncEvent orders by completedAt, but the actual code… orders by startedAt… Updating this snippet would prevent the spec from drifting from the merged implementation."

Applied: Updated the snippet in plan.html §8.0 to orderBy: [desc(syncEvents.startedAt)] with a comment explaining the index motivation. Also added the missing skippedCount column to the listSyncEvents projection and added mapOutcomeForDisplay to the snippet (it was introduced post-review).
