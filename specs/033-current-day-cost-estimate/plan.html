Current-day cost estimate ("predicted today")

Anthropic cost_report only ever returns complete UTC days, so the workspace / global cost views are always missing today — and the whole current month until the 2nd (see spec 033's sibling fix, PR #105). Meanwhile we already have a real, hourly-fresh per-user cost for today. This proposal surfaces a clearly-labelled estimated current-day figure so month-to-date totals and month-end projections are accurate sooner — especially near month end, where budget decisions are made.

1 · The problem & what we already have

There are two Anthropic cost data sources in the app, and they have very different freshness:

SourceTableGrainHas "today"?Sync
Per-user usage (usage_report) anthropic_usage_metrics user × model × day, with real computed_cost_cents YES — hourly, incl. today hourly (0 * * * *)
Workspace / global cost (cost_report) anthropic_workspace_costs workspace × day, cost_cents NO — complete days only hourly, but only writes finished days

The dashboards, the workspace budget list, the org-credits panel and the budget pages all read the workspace table — the one that never has today. So every "month-to-date" and "projected month-end" figure is silently running a day behind (and is empty for the whole current month on the 1st). The per-user table already holds a real, ~hourly-fresh cost for today (schema.ts:553-591, written by anthropic-sync.ts's todaySyncWindow()/fetchTodayAggregated() hourly path, costed via anthropic-pricing.ts). That is the signal we can lean on.

2 · Two separate issues hide here

Worth separating, because one is a near-zero-risk fix and the other is the actual feature you asked for.

BugProjection denominator is off by a day

projectMonthEnd(mtd, daysElapsed, daysInMonth) (utils.ts:86-93) is called with daysElapsed = Math.max(1, getDate(today)) (queries.ts:84-88, anthropic-global.ts:835, anthropic-users.ts:812, workspace-budget-list.tsx:27) — but mtd comes from the workspace table that excludes today. The numerator skips today; the denominator counts it. Result: it under-projects all month, and projects 0 on the 1st. This alone hurts month-end budget management — and is fixable independently of any prediction.

FeatureNo current-day figure at all

Even with the denominator fixed, today's actual spend is invisible in the workspace/global views until the next day. Near month end that is exactly when you want it. The fix: derive a calibrated estimate of today's cost from the per-user data we already have, and surface it as a distinct, clearly-labelled value.

3 · Hard constraint — per-user costs do not equal workspace costs

This is the single most important design constraint, and the codebase already documents it: "Per-user totals do not sum to org / workspace totals … Different rounding, different aggregation windows. The two will not reconcile exactly." — specs/027-claude-users-subpage/data-model.md:107 (also 016/026).

Why they diverge for the same day:

  • Different endpoints. Per-user = usage_report tokens × a hardcoded pricing table; workspace = cost_report billed dollars. Spec 016 notes cost_report coverage differs (e.g. Priority Tier).
  • Pricing-table drift. Unknown/new models fall back to the highest Opus price (anthropic-pricing.ts:85-95); rate changes, batch/service-tier discounts aren't modelled.
  • Unmapped spend. Any API key not registered as a Hub license assignment is dropped (anthropic-sync.ts if (!userId) continue;) — present in cost_report, absent from per-user. Pure under-count.
  • Rounding at different grains.
Consequence: we must not treat "sum of per-user today" as the workspace cost. The honest move is to use it as a signal and calibrate it against how the two sources actually relate on recent complete days.

4 · Estimation approach (the maths)

One small, pure, well-tested helper. No new tables, no new packages.

// src/lib/anthropic/estimate-today.ts  (NEW, pure + unit-tested)
export function estimateTodayCostCents(input: {
  todayUserCostCents: number;        // SUM(usage_metrics.computed_cost_cents) WHERE date = today (real, hourly)
  recentUserCostCents: number;      // SUM over last N COMPLETE days, per-user source
  recentWorkspaceCostCents: number; // SUM over the SAME N complete days, workspace source
}): { estimatedTodayCents: number; calibration: number; confident: boolean } {
  // Calibration = how much bigger the billed workspace total runs vs our per-user estimate.
  const raw = input.recentUserCostCents > 0
    ? input.recentWorkspaceCostCents / input.recentUserCostCents
    : 1;
  // Clamp to a sane band so a noisy week can't 3× the number; fall back to 1.0 when thin.
  const calibration = clamp(raw, 0.5, 2.0);
  const confident = input.recentUserCostCents > 0 && input.recentWorkspaceCostCents > 0;
  return {
    estimatedTodayCents: Math.round(input.todayUserCostCents * (confident ? calibration : 1)),
    calibration, confident,
  };
}

The estimate is today's spend so far (cumulative to the current hour), not a full-day extrapolation — it's the most defensible "as up to date as possible" number. For the projection, this estimated-today is added to MTD and the off-by-one denominator is corrected, so month-end pacing stops under-counting. We deliberately do not extrapolate the partial day to a full day in the MTD figure (that would overstate actuals); the run-rate already handles the remaining days.

Self-correcting. When tomorrow's real cost_report day lands, the estimate for that date disappears and is replaced by the actual — the estimate only ever occupies the single trailing "today" slot. Calibration is recomputed each load from the latest complete days.

5 · Build plan — phases, tasks & acceptance criteria

Scope is Tier B, shipped as one PR in three ordered phases: data → maths → UI. Each phase is independently reviewable and leaves the app working. The former "Tier A" projection fix is folded into Phase 2; the former "Tier C" budget integration is out of scope.

5.1 · Data contracts & constants (agree these first)

// src/lib/anthropic/estimate-today.ts
export const CALIBRATION_LOOKBACK_DAYS = 7;   // complete days used to calibrate
export const CALIBRATION_MIN = 0.5;          // clamp band — a noisy week can't 2×/½× the figure
export const CALIBRATION_MAX = 2.0;

// The estimate carried on every DTO that currently exposes month-to-date cost.
// `null` ⇒ no estimate to show (no per-user data today, or usage sync stale) ⇒ UI falls back to actual-only.
export type TodayEstimate = {
  cents: number;          // calibrated estimate of today's spend SO FAR (cumulative to now)
  rawUserCents: number;   // uncalibrated per-user sum for today
  calibration: number;    // ratio applied (1.0 when not confident)
  confident: boolean;     // had ≥1 recent complete day in BOTH sources to calibrate
  asOfIso: string;        // timestamp of the per-user usage sync → drives the freshness label
};
Final projection model (current month)

Reuse projectMonthEnd(spentSoFar, daysElapsed, daysInMonth) utils.ts:86-93 unchanged; fix the inputs so numerator and denominator agree (both include today):

const daysElapsed   = getUTCDate(today);                       // includes today
const spentSoFar    = mtdActualCents + (todayEstimate?.cents ?? 0); // complete days + today's est.
const projected     = projectMonthEnd(spentSoFar, daysElapsed, daysInMonth);

Past months: unchanged (daysElapsed = daysInMonth, no estimate). forecastWorkspaceMonth forecast-workspace.ts: set today's dense-series slot to todayEstimate.cents (instead of 0) and add it to mtdCents.

Scope guard (must hold for every task): the estimate is a separate field — never merged into totalCents, getRunningCostsForPeriod, or any alert threshold. Per-user detail pages already read today's real per-user cost directly and need no calibration (they are the source) — calibration applies only where we compare against the workspace/global cost_report figure.

7 · Data flow

load dashboard / workspace detail
   │
   ├─ existing: SUM(anthropic_workspace_costs.cost_cents)  →  MTD actual (complete days)
   │
   ├─ NEW: SUM(anthropic_usage_metrics.computed_cost_cents WHERE date = today)      → todayUserCostCents
   ├─ NEW: SUM(usage_metrics) & SUM(workspace_costs) over last N complete days      → calibration inputs
   │            (per-workspace variant joins anthropic_sync_status.resolved_workspace_id)
   │
   └─ estimateTodayCostCents(...)  →  { estimatedTodayCents, calibration, confident }
                │
                ├─ KPI DTO:   totalCents (actual, unchanged)  +  estimatedTodayCents (separate field)
                ├─ projection: projectMonthEnd(MTD + estimatedToday, completedDays-correct, daysInMonth)
                └─ charts:     append dashed "today (est.)" point  (never merged into the actual series)
The estimate is computed at the read/aggregation boundary and carried as a distinct field — it is never written to anthropic_workspace_costs. That keeps every existing SUM query, getRunningCostsForPeriod, and the alert thresholds reading actuals only unless we explicitly opt them in (Tier C).

8 · UI — how "estimated" stays visually distinct

See the mockup: mockup.html renders all four views — the KPI strip ("incl. est. today" + est. chip & tooltip), the daily chart with the ghost "today (est.)" bar, the cumulative pacing chart with the projection anchored at today, and the 1st-of-month before/after.

We reuse the projection vocabulary the app already ships, so nothing new to design:

  • Dashed / ghost bar for "today (est.)" on daily charts — same treatment as the existing projected bar (fillOpacity 0.28, strokeDasharray "3 3", twelve-month-bar-chart.tsx:144-155).
  • Dashed projection line in the cumulative pacing chart already exists and even has a "today" reference line (cumulative-pacing-chart.tsx:177-243) — we just anchor it at MTD + est. today.
  • Sub-labels on KPI tiles: "Month-to-date · incl. est. today" and a tooltip explaining the estimate is derived from per-user usage and calibrated to recent billed days.
  • A small est. chip + tooltip noting per-user and workspace figures don't reconcile exactly (consistent with the existing reconciliation footnotes).

9 · Test plan

  • Unit: estimateTodayCostCents — calibration clamp (0.5–2.0), thin-data fallback to 1.0, zero today, zero recent, rounding.
  • Unit: projection denominator — MTD excl. today ÷ completed days; 1st-of-month no longer yields 0; mid-month matches hand-calc.
  • Unit: per-workspace estimate joins resolved_workspace_id correctly (incl. NULL default workspace).
  • Component/DTO: estimatedTodayCents is a separate field; actual totalCents unchanged; charts append exactly one trailing est. point.
  • Verify on a Neon branch with production data (same method used for PR #105): compare estimated-today vs the actual that lands the next day for a few days to sanity-check calibration.

10 · Risks & mitigations

RiskMitigation
Estimate diverges from the real cost (pricing drift, unmapped spend, priority tier).Calibrate against recent complete days; clamp the ratio; label clearly as "est."; never present as actual. Self-corrects next day.
Estimate silently inflates a "hard" number (budget actual, alert threshold).Keep it a separate field; Tiers A/B do not touch getRunningCostsForPeriod or getActiveAlerts. Tier C adds a distinct estimated field only.
Calibration noisy when org has little recent data.confident=false → fall back to uncalibrated per-user sum (still better than nothing) or hide the estimate entirely (config-able).
Users with no resolved API key contribute nothing.Same limitation as today's per-user views; documented in tooltip. Calibration ratio partially compensates at the global level.
Scope creep into budget pages.Approved scope stops at Tier B; budget integration is a deferred follow-up spec.

12 · Explicitly out of scope

  • Persisting a synthetic "today" row into anthropic_workspace_costs — rejected: it would silently leak the estimate into every SUM query, budget actuals, and alerts with no way to distinguish it.
  • Full-day extrapolation of the partial current day into the MTD actual figure (overstates spend; the run-rate covers remaining days).
  • Changing the annual OLS budget forecast (forecast.ts) — operates on monthly period actuals, unrelated.
  • Backfilling estimates for past days — the estimate only ever occupies the single trailing "today" slot.
  • Budget-layer integration (former Tier C) — feeding the estimate into getRunningCostsForPeriod / budget actuals / reports. Deferred to a follow-up spec.
  • Moving alert thresholds with the estimate — getActiveAlerts keeps reading actual-only MTD. (The cron forecast alert benefits from the run-rate fix, but its firing logic is unchanged.)
