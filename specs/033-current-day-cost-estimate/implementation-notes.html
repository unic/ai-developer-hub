D1 · Estimate computed in queries.ts (uncached layer), not the cached actions

The cron Teams evaluator reads loadDashboardKpis / loadCostHistory directly (uncached, "wants fresh reads"); the dashboard wraps them in unstable_cache. Putting the estimate in the query layer means the evaluator gets a fresh estimate every cron run, and the dashboard inherits the existing refresh cadence (manual sync / tag revalidation) — identical freshness to the actuals beside it.

D2 · asOf = sentinel row last_sync_completed_at (per-user usage sync)

The estimate is only as fresh as the hourly per-user usage sync. That completion timestamp is written on the user_id = 0 sentinel row by anthropic-sync.ts (the per-user path), distinct from workspace_sync_completed_at (the cost_report path). The freshness label reads the former.

D3 · null estimate when stale or zero — UI falls back to actual-only

Per the plan's null rule, the query layer returns null when (a) there is no per-user usage for today (rawUserCents === 0), or (b) the usage sync is stale (asOf older than the existing 70-minute threshold). A stale estimate is worse than none, so we hide rather than dim. See tradeoff T2.

D4 · UTC day boundary for daysElapsed

All four projection callers used getDate() (local) while the cost tables key on UTC calendar dates. Switched to a UTC day count (and getCurrentMonth(), already UTC, for the "is current month" test) so numerator and denominator agree with the data's day boundary.

D5 · App design tokens, not mockup hex

The mockup uses literal lime #d4f057. The real charts use var(--chart-1) with the existing ghost vocabulary (fillOpacity 0.28, strokeOpacity 0.6, strokeDasharray "3 3" for bars; the pacing projection line keeps its existing "4 3"). Per CLAUDE.md ("design tokens only — no hardcoded color"), the estimate reuses those tokens, so it reads as "ghost/projected" in whatever theme is active rather than a fixed lime.

D6 · KPI headline stays the actual total; estimate is a labeled sub-line

The mockup merges actual + est into the headline ("$43,960"). The plan §6.1 instead says the tiles get an "incl. est. today" sub-label. Followed the plan: the Total · {month} / Projected headline values are unchanged (actual total; projection already folds in the estimate via the maths layer), and a est.-chipped sub-line ("incl. +$X est. today") surfaces the estimate. This is the more conservative reading and keeps the headline number un-inflated, matching the "never merged into totalCents" guard. The big projected number does reflect the estimate (that's the whole point of the projection fix).

D7 · Stacked "today (est.)" bar via a reserved series key

The org daily chart is a stacked bar chart. The estimate is a single org total (not a per-workspace breakdown in that chart), so the server appends one trailing row keyed under a reserved __estimated__ series (mirroring the existing __other__/__default__ keys, which are intentionally duplicated client-side). The client renders it as one dashed ghost bar, and only in the org-wide ("All workspaces") view. The workspace detail daily chart appends a per-workspace ghost bar from that workspace's own estimate.

D8 · /claude page now computes "today"/"current month" in UTC

The page passed getDate(now) / format(now,"yyyy-MM") (local) into the pacing chart's today line and the KPI loaders. Switched to now.getUTCDate() and getCurrentMonth() so the dashboard's "today" matches the UTC day the cost tables and the estimate gating use (and the already-UTC available-months list).

V1 · User-detail page gets the UTC fix but no estimate field

The plan lists anthropic-users.ts among the four projection callers (Tier A). But the per-user detail page's currentMonthCents comes from anthropic_usage_metrics, which already includes today (hourly). It is the source — the scope guard says it needs no calibration. So its numerator already includes today and only the denominator needed the UTC alignment; no todayEstimate is threaded onto UserDetail. This matches the spec's intent, just makes explicit that the "off-by-one" framing doesn't apply there.

T1 · Per-workspace calibration vs. a single global ratio

Each workspace's estimate is calibrated against its own recent per-user-vs-cost_report ratio (clamped 0.5–2.0, falls back to ×1 when thin). Alternative: one global ratio applied to every workspace's raw per-user sum. Per-workspace is more honest where mix differs, and the clamp + confident fallback guards thin data. Global aggregate uses the summed components (one global ratio for the org KPI).

T2 · Hide a stale estimate vs. dim it

The plan offered "dim it / hide". Chose hide (null) for safety — a dimmed-but-stale number can still be misread as current. The freshness label still shows the sync age while fresh.

Q1 · Teams cron alerts now include the estimate in the run-rate (confirm)

Per plan Phase 2 (T2.2) the cron Teams forecast (forecast-workspace.ts via teams/evaluator.ts) now fills today's missing cost_report slot with the per-workspace estimate. This is a real behavior change: a workspace can tip into at_risk / cross its cap a little earlier (more accurate, no longer diluted by a phantom $0 today). The 80/100/120 utilization thresholds are unchanged (they read actual cost_report only). Flagging because it changes when production alerts fire. The plan calls this an intended "benefit"; confirm you're happy with it.

Q2 · Dashboard estimate freshness follows the existing cache cadence

The estimate lives inside the same unstable_cache reads as the actuals, busted by manual sync / revalidateTag (the hourly crons don't revalidate — pre-existing). The cron Teams evaluator reads uncached, so it always sees a fresh estimate. No new cron revalidation was added (would change existing caching behavior). If you want the dashboard estimate to refresh hourly without a manual sync, that's a small follow-up (have the usage cron revalidateTag("anthropic-workspace-costs")).
