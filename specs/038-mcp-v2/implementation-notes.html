decisionSpec folder numbered 038

Specs run through 037 (037-tier-cost-propagation); this feature is specs/038-mcp-v2/. The original MCP server spec is 034; this builds on it rather than amending it.

decisionEmbedded OAuth AS over external IdP / PAT-style keys

Claude Desktop & claude.ai custom connectors cannot send custom headers, so any header-token scheme fails the primary requirement. An external IdP would federate identity for a single consumer of an app whose users live in its own Postgres. Full rationale in brainstorm.html §2; risk discussion in implementation-plan.html §4.

tradeoffOpaque hashed tokens (DB lookup per call) over JWTs

Chose instant revocation + user-deactivation guarantees over saving one indexed SELECT per tool call. For an internal admin tool the read is negligible; "revoke" in the settings UI must actually mean revoke.

deviationNo silent re-approve on the consent screen

The plan leaned toward auto-issuing a code when the user already holds a live grant for the same client. Implemented always-show-consent instead: silent re-approve means issuing a code (a DB write) during a server-component render, which Next.js semantics discourage (renders may be replayed/prefetched). Cost is one extra click per re-connect, and with 60-day rotating refresh tokens that screen appears rarely.

decisionRedirect URI policy: https + loopback http only — no custom schemes

Claude's documented callbacks are https://claude.ai/api/mcp/auth_callback and port-agnostic http://localhost/… (RFC 8252 §7.3 — port ignored at match time, implemented and unit-tested). Private-use schemes like cursor:// are rejected at registration. If a custom-scheme client ever matters, it's a one-line relaxation in isAllowedRedirectUri plus a deny-list for javascript:/data: — deliberately not pre-built.

decisionScope handling: offline_access tolerated, always grant mcp:read

Claude appends offline_access when a server lists it; we don't list it but tolerate it being requested (refresh tokens are always issued anyway). Any other unknown scope is rejected with invalid_scope so the consent screen never under-describes what's granted.

deviationNew tools query the DB directly instead of "lifting" page queries into src/lib

The plan said to lift session-checking action queries (e.g. _getUserList) into shared lib modules. Dropped that: exporting anything from a "use server" file mints a callable server-action endpoint, and refactoring 700-line action files to share internals would churn admin-page code in an MCP PR. Instead each tool runs a focused read-only query in src/lib/mcp/data.ts (the pattern spec 034 already used for Copilot). getBudgetReportData is the exception — it performs no session check and is imported directly, exactly like the existing actions/budget imports. Consequence: MCP results are deliberately leaner than the admin pages (e.g. the cost dashboard omits the page's pacing curve and calibrated today-estimate). The /simplify pass flagged the duplication risk and two real drift points were fixed (the sync-lock sentinel user is now excluded from list_claude_users like the admin query does, and the default-workspace label matches the dashboard's capitalization); the structural duplication is accepted and documented rather than refactoring anthropic-users.ts/anthropic-global.ts inside this PR.

decisionAuthorization model unchanged: any authenticated MCP credential sees all read-only data

OAuth adds who (user-bound tokens, per-user revocation) but not per-role filtering: a viewer-role user's token reads the same org-wide spend data as an admin's, matching the shared-secret behavior spec 034 shipped and the data-is-viewer-safe judgment made there. Per-user spend (list_claude_users) is visible org-wide in the admin UI only — flagging this explicitly as something to confirm (see open questions).

decisionToken-endpoint rate limit keyed on IP + client_id

Hosted Claude egresses every tenant through 160.79.104.0/21, so a pure-IP limiter could lock out unrelated users. Registration stays per-IP (10/10 min); token grants are 60/10 min per IP+client.

decisionsafeEqual moved to src/lib/oauth/validate.ts

mcp/auth.ts now imports from the OAuth layer, which itself needs safeEqual — keeping it in mcp/auth.ts would create an import cycle. Re-exported from the old location so existing imports/tests are untouched.

tradeoffOpportunistic cleanup instead of a cron job

Expired codes/tokens are deleted piggy-backed on issuance writes. Registered clients are never auto-pruned (a client row is ~200 bytes and registration is rate-limited); accepting slow accumulation over another scheduled job. Revisit if DCR abuse ever shows up in practice.

Open questions

open questionShould viewer-role tokens see org-wide per-user spend?

Today: yes (matches spec 034's shared-secret model — anyone with the org secret saw everything). If that's not acceptable now that tokens are user-bound, the hook exists: verifyMcpToken already puts userId/email into AuthInfo.extra, so role-scoping individual tools is a follow-up, not a redesign.

Resolved 2026-06-11: answered "no" — implemented as feature specs/039-mcp-role-scoping/. Viewer tokens are denied the 11 org-wide tools, the two personal tools are pinned to the token owner, and list_ai_tools drops utilization for viewers; the shared secret stays admin-equivalent.

open questionAccess-token TTL: 1 hour

Chose the strict OAuth 2.1 posture (1 h access / 60 d rotating refresh). If hourly refresh traffic ever bothers you in logs, bumping ACCESS_TOKEN_TTL_MS is a one-line change.

open questionP2 tools shipped — confirm they earn their keep

list_invoices and get_copilot_analytics were the designated drop-candidates if review finds the tool count excessive (14 total). Both are thin; flagging rather than pre-cutting.
