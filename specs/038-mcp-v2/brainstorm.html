Spec 038 · Brainstorm

MCP v2 — OAuth Connectivity & Tool Expansion

ai-developer-hub · 2026-06-11 · builds on spec 034 (read-only MCP server, PR #112)

The Hub already ships a read-only MCP server at /api/mcp/mcp (Streamable HTTP via mcp-handler 1.1.0) guarded by a single shared bearer secret (MCP_SERVER_SECRET). Two asks for v2:

  • Connectivity — make the Hub addable as a custom connector in Claude Desktop / claude.ai and via claude mcp add in Claude Code, which means a real OAuth flow instead of a copy-pasted secret.
  • Capability — extend the seven existing tools with the highest-value data the app already computes.

1What Claude clients actually require

Verified against the Claude connector docs (June 2026) and mcp-handler's authorization guide:

RequirementDetail
TransportStreamable HTTP — already in place (/api/mcp/mcp).
Resource metadata (RFC 9728)Claude probes /.well-known/oauth-protected-resource/api/mcp/mcp first, then the root path; alternatively a WWW-Authenticate: Bearer resource_metadata="…" on the 401. mcp-handler ships protectedResourceHandler for this.
AS metadata (RFC 8414)/.well-known/oauth-authorization-server advertising authorize/token/register endpoints, code_challenge_methods_supported: ["S256"].
Dynamic Client Registration (RFC 7591)Claude registers itself as a public client (no secret) by POSTing JSON to the registration endpoint. No manual client setup possible for claude.ai/Desktop free-form connectors (advanced settings allow a pre-provisioned client id, but DCR is the zero-friction path).
PKCES256 on every authorization request; OAuth 2.1 — no implicit grant, exact redirect URI matching.
Redirect URIsHosted Claude (web/Desktop/mobile): https://claude.ai/api/mcp/auth_callback. Claude Code: loopback http://localhost:<ephemeral-port>/callback — the AS must ignore the port component per RFC 8252.
Token endpointAccepts application/x-www-form-urlencoded; RFC 6749 error codes (invalid_grant for a dead refresh token, not invalid_request). Refresh-token rotation expected for public clients. 10 s timeout budget.
Implication. mcp-handler covers only the resource-server half (token verification hook + resource metadata route). The authorization-server half — authorize page, consent, code & token issuance, DCR — does not exist anywhere in the stack and is the core of this feature. NextAuth v5 (credentials provider) is a session library, not an OAuth provider; it gives us the logged-in admin/viewer identity we anchor the consent screen to, nothing more.

2Auth approaches considered

rejected A. Keep shared secret only

Claude Desktop custom connectors have no header field for arbitrary bearer tokens; only Claude Code supports --header. One org-wide secret means no per-user identity, no revocation granularity, and manual secret distribution. Fails ask #1 outright.

rejected B. External identity provider (Auth0 / Clerk / Entra ID)

Offloads the hard OAuth parts, but: the Hub's users live in its own Postgres users table with bcrypt credentials — wiring an external IdP means federating identity for exactly one consumer, a new SaaS dependency, new secrets, and tenant setup the team doesn't otherwise need. Entra ID DCR support is poor. Disproportionate for a single internal app.

rejected C. Per-user long-lived API keys (PAT style)

A "create MCP token" button under settings, pasted into Claude Code via --header. Simple, but Claude Desktop/claude.ai custom connectors can't send custom headers, so it fails ask #1 for the desktop app; it would only serve Claude Code. Could exist as a fallback, but it's not the headline.

recommended D. Minimal embedded OAuth 2.1 authorization server

Implement the four endpoints inside the app, anchored on the existing NextAuth session for the authorize step:

Claude                        Hub (Next.js)
  |                              |
  |  GET /api/mcp/mcp  ───────► | 401 + WWW-Authenticate: resource_metadata=…
  |  GET /.well-known/oauth-protected-resource/api/mcp/mcp ─► points at Hub-as-AS
  |  GET /.well-known/oauth-authorization-server ──────────► endpoints + S256
  |  POST /api/oauth/register (DCR, public client) ────────► client_id
  |  browser: GET /oauth/authorize?…&code_challenge=…
  |     └─ no session → /login?callbackUrl=…  (existing flow)
  |     └─ session    → consent screen → issue code (10 min, single-use)
  |  POST /api/oauth/token (code + PKCE verifier) ─────────► access + refresh
  |  POST /api/mcp/mcp  Bearer <access> ───────────────────► tools, scoped to user

Three new tables (mcp_oauth_clients, mcp_oauth_codes, mcp_oauth_tokens), tokens stored as SHA-256 hashes (the invite_tokens pattern), rotating refresh tokens, exact-match redirect URIs with the RFC 8252 loopback-port exception. The shared secret stays as a parallel path for headless/CI clients. Every grant is tied to a real Hub user, so MCP access inherits account lifecycle: deactivate the user → tokens die.

Scope model: single mcp:read scope for now (server is read-only by design — spec 034). Writing tools would be a separate feature with per-scope consent.

Improvements to existing tools

  • list_ai_tools — add active license counts and maxLicenses utilization per tool (cheap join; turns a static catalog into an inventory answer).
  • get_user_cost_profile — on email miss, return near-match candidates (powered by the same lookup as find_users) instead of a bare error.
  • All tools — add MCP annotations: { readOnlyHint: true } so clients can skip confirmation prompts.

4Security considerations

  • Token storage — only SHA-256 hashes in Postgres; raw tokens exist client-side only. Access tokens short-lived (≈1 h), refresh tokens rotating with reuse detection (rotated-token replay revokes the family).
  • Consent is user-anchored — the authorize page sits behind the normal NextAuth login; agent accounts (isAgent) are refused consent. Viewer-role users get the same read-only tools as admins — acceptable because spec 034 already deemed every exposed field viewer-safe (no API keys, no hashes); revisit if a write tool ever lands.
  • Redirect URI policy — exact string match against registered URIs; the only relaxation is ignoring the port for http://localhost / http://127.0.0.1 loopbacks (RFC 8252 §7.3). No wildcards, no open redirects; state echoed verbatim.
  • DCR abuse — registration is unauthenticated by spec. Mitigations: store only validated metadata, cap stored clients, prune clients with no tokens, and rate-limit via the existing rate-limit.ts helper. A registered client grants nothing without a logged-in user consenting.
  • No new write surface — the MCP server stays read-only; OAuth only changes who can read, from "anyone with the org secret" to "named users who consented".
  • Revocation — settings page lists a user's active grants (client name, last used) with revoke; deactivating a user revokes everything via the token check joining users.status.

5Recommended scope for v2

Ship: embedded OAuth 2.1 AS (option D) with DCR + PKCE + rotating refresh tokens, shared-secret path retained · five P1 tools + two P2 tools · the three existing-tool improvements · grants management in settings · migration with three new tables.

Defer: license-request/ingestion tools, scenario calculators, MCP resources, scoped write access, pre-provisioned client management UI.

Open questions for the implementation plan

  • Access-token TTL: 1 h (strict OAuth 2.1 posture) vs 24 h (fewer refresh round-trips). Leaning 1 h since Claude refreshes automatically.
  • Should the consent screen be per-client-forever (silent re-approve on the same client) or re-prompt each authorize? Leaning silent re-approve when an unexpired grant for the same client exists.
  • Where the well-known routes live: Next.js route handlers under src/app/.well-known/…/route.ts — need to confirm middleware matcher exclusion.
