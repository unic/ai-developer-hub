Implementation notes spec/043-mcp-write-tools Challenge pass logged

MCP Write Tools — running notes

Design decisions, deviations, tradeoffs, open questions, and the adversarial challenge pass for spec 043. Appended as work proceeds.

Started 2026-08-04 · author: T. Studer · branch worktree-mcp-write-tools

Process

Explored and designed by a 12-agent dynamic workflow rather than by hand, because the write surface touches three subsystems whose invariants live in different files: 5 parallel inventory agents (MCP layer · user writes · assignment writes · tool/tier writes · actor & non-session-write plumbing), 3 competing design lenses (shared-core · thin-adapter · agent-safety), a judge, then 3 adversarial challenge lenses. 1.32M subagent tokens, 0 errors, ~22 min wall clock.

The three design lenses were deliberately given conflicting biases so the judge had a real decision to make rather than three variations of one idea. That paid off: the winning spine came from the shared-core lens, but its confirm: z.boolean() guardrail was worthless and got replaced wholesale by the agent-safety lens's plan token.

Decisions taken without sign-off

Both were surfaced to the user, who was away; both are cheap to reverse and are flagged in the plan's opening callout.

  • Writes require a new mcp:write scope, so existing OAuth grants stay read-only until the connector is re-authorized once. Decisive evidence: src/app/oauth/authorize/page.tsx:108 tells the person clicking Allow “No write access.” Shipping writes over that grant makes the consent screen a false statement to a human. The alternative (role-only) was rejected for that reason alone; it is otherwise simpler and would need no reconnect.
  • create_user mints an invite token but returns only a pointer, never the /setup-password URL. Keeps a live 72h credential out of the transcript while leaving the account in exactly the state a UI-created user is in — which also avoids inventing the Hub's first-ever users row with no invite token.

Scope reductions (mine, and why)

  • Tool-catalogue writes deferred (create_ai_tool / update_ai_tool / archive_ai_tool). The user's ask named users, assignments and tiers explicitly, then “things like that”. Catalogue creation is procurement with no delete path, and update_ai_tool's only interesting field (maxLicenses) is overwritten nightly by the Copilot cron on the largest seat pool. Cutting these takes the surface from 12 tools to 9 and removes the archive trapdoor and the duplicate-name race.
  • Reactivation cut — not merely deferred. The judge proposed set_user_status handling both directions and treated reactivation as a licenses/UI-parity question. It is actually a security question; see the blocker below.

Challenge pass — 29 findings, 4 blockers

Every finding below was re-verified against the real code before being accepted; the panel was explicitly told that a finding contradicted by the code is worse than no finding. All four blockers held up.

Blockers

  • Reactivation is a credential re-grant. deactivateUser (src/actions/users.ts:180-208) flips status and cascade-revokes licenses, but never clears passwordHash, never sets mustChangePassword, and never touches mcp_oauth_tokens. src/lib/auth.ts:51 gates password login on status alone, and verifyAccessToken re-reads status = 'active' live against tokens with 60-day refresh lifetimes. So a one-line reactivation restores an offboarded leaver's old password and re-arms every dormant grant they still hold. Resolution: reactivation removed from the spec; set_user_status became deactivate_user. Noted as a pre-existing hole worth its own fix (deactivation should revoke token families).
  • “One active assignment per (user, tool)” is not enforced by the DB. license_assignments_active_lookup_idx (schema.ts:279-283) is index(), not uniqueIndex(); there is no partial unique index on the table at all. The design dropped the UI's deactivate-and-replace in favour of read-then-refuse — which converts the TOCTOU window from “collapses to one row” into “produces two active rows”, double-billing a seat in every aggregation that sums cost_at_assignment_cents, and no tool in the surface can detect it. Resolution: partial unique index in migration 0030 + 23505 mapped to the friendly refusal, so the invariant is a DB guarantee. Fixes the UI action and the license-request flow too.
  • Removing the capacity minus-1 branch regresses the UI. The judge's rationale explicitly claimed the MCP refusal “removes the whole capacity-check-minus-one special case”. But copilot-sync.ts:73-80 sets maxLicenses = billing.seat_breakdown.total on every sync, so Copilot sits routinely at exactly capacity, and assignments.ts:82-84's minus-1 is what lets an admin retier an existing holder through the assign dialog. Resolution: branch stays verbatim in the core, gated on caps.replaceAssignments — unreachable from MCP, intact for the UI wrapper. Unit test pins both directions.
  • expectedTierName does not identify a tier. Tier names are unique only per tool (access_tiers_tool_name_idx on (toolId, name)), and the real ones are generic: copilot-sync.ts:83-95 creates tiers named “Business” and “Enterprise” under GitHub Copilot. An agent told “set the Enterprise seat price to $60” can grab Copilot's Enterprise id instead of Claude's, pass a matching name echo, and reprice every active Copilot seat. Resolution: the tier tools take expectedToolName + expectedTierName, and set_tier_price additionally expectedMonthlyCostCents — which also makes staleness detectable on the first call, before a preview is even generated.

Majors accepted

  • Sync-owned fields refused. A set_tier_price on a Copilot tier reports success and is silently reverted at 06:00 UTC by copilot-sync.ts:103-121 (hardcoded business: 1900, enterprise: 3900), with zero audit rows — so the agent's report becomes false within 24h and nothing explains why. Refused with a message naming the sync as the owner. Contributed to deferring update_ai_tool entirely.
  • update_user loses email. resetUserPassword (invite.ts:239-247) and sendInviteEmail (:279-287) both mail a fresh 72h token to the current users.email. An agent able to rewrite that field has an account-takeover primitive, and expectedEmail is no defense — the echo matches because the agent reads the correct current address out of find_users.
  • Secrets refused in the handler, not the schema. The design's z.string().refine(() => false) decoy rejects at the SDK's input-validation boundary, outside format.ts's controlled formatting — so the repo cannot assert a submitted live key is absent from the error response or the transport log, and the decoy's whole purpose is to induce the agent to send one at least once. Now a plain optional string, refused as the first statement inside the handler, with the prohibition led in the description so the model reads it before composing the call.
  • No-op is success, not isError. Returning an error for “already inactive” contradicts idempotentHint: true. Concretely: a committed revoke_license whose response is lost to the 60s maxDuration cutoff, retried, answers “Error: Assignment is already inactive” — the model reads failure and its plausible recovery is deactivate_user, cascading a revoke across every license the person holds. Cores return a discriminated no-op; the UI wrapper keeps today's error string so UI behavior is unchanged.
  • Plan tokens get iat/TTL and a caller binding. As designed they were unbound, non-expiring bearer capabilities — liftable from a shared transcript weeks later and committable by a different credential. Now sub = clientId:userId, 10-minute TTL, and an HKDF-derived signing key so this surface cannot become an oracle on the session-cookie key. Also corrected the rationale: the token proves state-binding, not human review — in an auto-approving client preview and commit are consecutive calls with no human turn between. destructiveHint: true is the actual human gate.
  • set_tier_price is destructiveHint: true. “No row is destroyed” was the wrong test for an irreversible bulk overwrite of financial snapshots whose prior values exist only in the audit rows this spec is newly adding.
  • Propagation row set comes from SELECT … FOR UPDATE inside the transaction, not from the preview's captured set — otherwise the audit rows describe a different row set than the WHERE tier_id = $1 AND status = 'active' update rewrote, with previousValues that were never in the rows.
  • Cents guard is two-sided. Only the high side was guarded; monthlyCostCents: 19 for a $19 seat passes min(0) and understates that tool's spend 100× through propagation. 1..99 refused with both readings spelled out, 0 stays legal.
  • source is required — at the type level. The challenge pass argued for NOT NULL with no DB default, on the grounds that a default lets any call site that forgets the argument silently label its row a human UI edit, the exact forensic lie the column exists to prevent. Required + options-object (not a 6th positional arg after an optional one) so the compiler flags all existing call sites. The no-default half was reversed later — see “NOT NULL with no default is undeployable” below. The shipped column is varchar(20) NOT NULL DEFAULT 'ui', and the compiler — not the DB — is what forces provenance.
  • Cores return their own revalidate list. updateTier's invalidation set is conditional on whether the price changed (tools.ts:294-330), computed from the diff inside the function — a wrapper cannot reproduce it. Getting it wrong serves /budget and /reports from cache built on the old snapshots.
  • Gate partition tested per tool. Today's exhaustiveness test only checks that a tool name is classified, so a write tool that forgot the gate would compile and pass green. Added per-tool assertions for viewer refusal (core never invoked), kill switch, missing scope, absent authInfo, and readOnlyHint === false with the mirror assertion on read tools.
  • list_ai_tools gains includeInactive. data.ts:95/105 filter to active tools and tiers, so deactivating a tier made its id unobtainable from MCP — a one-way trapdoor behind a boolean that looks two-way.
  • Actor isAgent refused. BUILT_IN_DENY_PATHS encodes the standing policy that an automated agent must never reach user creation or deletion; the /api/mcp entry there is already inert because MCP sits in the middleware matcher's negative lookahead. A two-line check on the resolved actor keeps the policy true if the login/consent isAgent refusals are ever relaxed.

Findings rejected or downgraded

  • users.createdVia column + excluding MCP-created users from sendBatchInviteEmails — the finding (real: invite.ts:312 selects every user with mustChangePassword = true and mails a live setup link) is correct that an MCP-created row is not inert. But once create_user's email is constrained to an allow-listed org domain, the residual case is “an admin later batch-invites an org-domain user they asked the agent to create” — which is intended behavior, not a hole. Dropped the column; kept the domain allowlist, which is what actually stops attacker@gmail.com.
  • Pointing copilot-sync.ts at the extracted core — correct and worth doing, but out of this spec's blast radius. Recorded as a known limitation in the plan rather than silently leaving the “one implementation of each mutation” claim overread.

Open questions

  • MAX_REPRICE_ROWS and the implausible-price ceiling are policy numbers, not engineering ones. Starting values: 250 rows and $2,000/seat/month (200,000 cents) — chosen to leave a wide margin over the real catalogue (Claude Enterprise ≈ $150/seat, Copilot Enterprise $39/seat). Worth confirming against the live tier catalogue.
  • MCP_WRITE_EMAIL_DOMAINS default: the domain of SYSTEM_ADMIN_USER_ID's email (unic.com). Contractors on other domains would need the UI.

Implementation log

Implemented 2026-08-04 · verified typecheck / lint / unit

  • The audit writers moved out of a "use server" file. Not planned — found while wiring the cores. src/actions/history.ts exported recordCreation(entityType, entityId, changedBy, …) with no auth check of its own, and every export of a "use server" file is a client-callable RPC endpoint. That was an audit-forgery primitive (write any row, attributed to anyone). The four writers now live in src/lib/history.ts (a plain module, which the cores need anyway); only getEntityHistory stays behind "use server", because Server Components import it there.
  • 44 call sites migrated by codemod across 13 files, with balanced-paren parsing rather than regex so multi-line calls and the positional tx form folded correctly. Provenance was assigned per file rather than blanket-ui: github-sync/invoice-sync/invoice-matching → sync, invoice-derived billed costs → ingest, the rest → ui. Two raw db.insert(changeHistory) calls (budget.ts, budget-extensions.ts) the codemod could not see were fixed by hand — the compiler found them, which is the whole argument for making source required.
  • The generated migration was wrong and had to be hand-edited. drizzle-kit generate emitted ADD COLUMN source varchar(20) NOT NULL with no default, which cannot be applied to a table that already has rows. Rewritten as add-nullable → backfill ui → SET NOT NULL. The partial unique index also aborts on pre-existing duplicates, so a DO block now reports the count via RAISE NOTICE and collapses all but one row per (user, tool) before the index is created. Both details written here were later reversed against real data: the survivor is the earliest assigned_at, not the highest id, and the column ships with a DEFAULT 'ui' — see the two items below and the Neon-branch section.
  • NOT NULL with no default is undeployable — reversed by 0031. The planned shape (NOT NULL, no DB default, so nothing but the compiler can supply provenance) cannot be rolled out in either order. Migrate first → the live pre-043 code calls recordCreation / recordUpdate / recordStatusChange without a source, so every audited write in the app fails with 23502 until the new code goes live. Deploy first → the new code writes a column that does not exist yet. There is no safe ordering without a default, so 0031_change_history_source_default.sql supplies one and the shipped column is varchar(20) NOT NULL DEFAULT 'ui'. pnpm db:migrate applies every pending file in one run, so 0030 and 0031 land together and the NOT-NULL-without-default state is never visible to application traffic — 0030 must never be applied on its own. The default is not what enforces provenance: source is still a required field on HistoryOptions, so the compiler still forces all 44 call sites to state it; the default only backstops a raw db.insert(changeHistory) that bypasses the helpers, and both such calls are explicit anyway.
  • Migration is 0030, not 0027. The plan was written against a stale count; src/lib/db/migrations/ already had through 0029. Corrected throughout both documents.
  • Caps gained a fifth axis, syncOwnedFields. The first draft gated the Copilot-price refusal on !caps.secrets as a proxy for “is this MCP”, which is exactly the kind of implicit coupling that rots. It is now its own named capability: true for the UI (which has always been able to edit that price and get overwritten at 06:00), false for MCP.
  • The cents guard lives at the MCP edge, not in the core. Same reasoning: it is an LLM-specific narrowing like the calendar-date refine, and applying it inside the core would change UI behavior for a legitimately unusual price.
  • The canary could not stay byte-identical, and that was predicted. The plan said commit 1 would be a pure relocation with tier-cost-propagation.test.ts untouched and green. In practice the audit-into-transaction change, the per-row audit rows and the locking SELECT all landed together, so the test needed the { update, insert, select } tx stub the challenge pass said it would. It now asserts the properties that actually matter: 1 tier row + 1 per repriced seat, every audit write carrying the tx client, and the audited row set coming from the in-transaction locking read rather than the preview. Grown from 4 tests to 15.
  • Test results. 703 unit tests, 701 passing. tests/unit/mcp/write.test.ts adds 63 covering the gate partition (viewer / missing scope / kill switch / absent authInfo / shared secret / unbound / agent actor — each asserting the core was never invoked), the plan-token protocol (issue, commit, fabricated value, cross-credential, stale plan), secret refusal without echoing the submitted value, the two-sided cents guard, and no-op-as-success. The two remaining failures are pre-existing load flakes in files this spec never touched — anthropic-users-phase3 takes 18s in isolation against a 5s per-test timeout, and system-admin-user-id 2.6s; both pass alone.

Verification against the Neon branch (2026-08-04)

The user provisioned a branch of production. The pre-flight paid for itself immediately: it found two bugs in the migration that no unit test could have reached.

Bugs the real data exposed

  • The survivor rule was backwards. The DO block kept max(id), documented as “the most recent assignment survives”. The branch’s one duplicate is marta.kachniarz@unic.com / GitHub Copilot Business, where id 391 carries assigned_at = 2026-07-16 and id 102 carries 2026-07-17 — the higher id is the OLDER assignment, because the license-request workflow inserts backdated rows. Picking by id would have silently moved that seat’s start date forward a day. Now ORDER BY assigned_at ASC, id ASC.
  • revoked_at = now() would not have fixed the history. getAssignmentSnapshotAt selects assigned_at <= asOf AND (revoked_at IS NULL OR revoked_at > asOf). With now(), the spurious row still satisfies revoked_at > asOf for every PAST date, so the double-count would have survived its own remediation in every point-in-time report, permanently. Changed to revoked_at = assigned_at — a zero-duration row that counts at no asOf at all. Verified after migrating: a snapshot at 2026-07-20 now counts that seat ONCE.

Thresholds calibrated against the real catalogue

  • Largest tier is Claude “Standard Seat” at 116 active seats — under MAX_REPRICE_ROWS = 250, so a legitimate reprice of the biggest tier is not blocked. Priciest is boost-leader at $200/mo, far under the $2,000 implausibility ceiling. No tier sits in the 1–99¢ band the low-side guard rejects. All three numbers are correctly placed.
  • change_history was 1,933 rows / 544 kB, so the backfill and SET NOT NULL are trivial — no lock-duration concern. The branch was also missing 0029 (from merged PR #124), so two migrations applied.

Migration result

  • source landed as varchar(20) NOT NULL; all 1,933 rows backfilled to ui. (This run predates 0031, which adds the DEFAULT 'ui' the shipped column carries — see above.) Partial unique index created with the right predicate. Zero duplicates remain. Org-wide active spend went 1,359,200¢ → 1,357,300¢ (−$19.00), which is the double-billed seat being corrected.

Runtime facts the unit suite structurally could not establish

Every unit test mocks @/lib/db, so these were guesses until tests/integration/mcp-write-cores.test.ts (17 tests) ran:

  • isUniqueViolationOn(err, "license_assignments_one_active_idx") does match a real Postgres 23505 — the constraint-name extraction was an untested guess.
  • SELECT … FOR UPDATE works through the neon-serverless driver inside db.transaction(). There is no other row-locking call anywhere in this repo, so this had zero precedent.
  • The UI retier path still works and does not trip the new unique index — the single largest regression risk in the whole refactor, since assignLicense’s deactivate-then-insert runs inside one transaction against a now-unique predicate.
  • Propagation rewrites active rows, leaves inactive ones on their historical snapshot, and writes 1 tier + 1 per-seat audit row with source='mcp'. The deactivation cascade writes a full JSON snapshot per revoked seat.
  • Full integration suite: 69 passed, no regressions in the budget / invoice / sync suites the 44-call-site codemod touched.

Live MCP session over Streamable HTTP

  • tools/list returns 23 tools (14 read + 9 write) with correct annotations over the wire — destructiveHint true on exactly deactivate_user, revoke_license, set_tier_price.
  • A read-only token is refused with the reconnect message; a submitted apiKey is refused without the value appearing in the response; a wrong expectedUserEmail is refused naming the actual holder; correct args succeed.
  • set_tier_price preview returns the per-seat breakdown plus a planToken and writes nothing; a fabricated token ("true" — the value an LLM would invent) is refused without echoing the real one; the genuine token commits; a replay is refused because the price basis moved.
  • Audit attribution confirmed end to end: all three rows recorded changed_by = maciej.zielinski@unic.com (the human the OAuth token is bound to) with source = 'mcp'. This was the user’s original question, and it now has a demonstrated answer rather than an argued one.
  • All smoke fixtures removed afterwards; org spend returned to 1,357,300¢ and zero source='mcp' rows remain.

Reusable pre-flight

  • The duplicate check is committed as scripts/preflight-duplicate-assignments.ts (read-only, no --apply mode, safe against production) so the production rollout does not depend on a query pasted out of a chat log. Its ORDER BY is deliberately identical to migration 0030's, so its KEEP / will-be-revoked column is what 0030 will actually do rather than an approximation — if one changes, both must.
  • Both branches were exercised against the Neon branch: with the index temporarily dropped and the duplicate restored it predicted KEEP=391, revoke=102, −1900¢, matching what the migration had really done; with the index present it takes the already-applied early return. The branch was then restored byte-for-byte (index recreated, row 102 back to zero-duration inactive, org spend 1,357,300¢, zero duplicates).
  • Dates in this document are the values to_char reports. An earlier reading via assigned_at::date showed them a day earlier because the neon driver localizes a naive timestamp on that cast; the ordering the survivor rule depends on is identical either way.

Browser pass over the UI write paths (2026-08-04)

The refactor moved every existing UI write behind src/lib/core/*, so the largest risk in this spec was never the MCP surface — it was breaking the dialogs an admin uses daily. tests/e2e/043-write-paths.spec.ts drives them with real clicks under a minted Nighthawk agent session. 5/5 passing.

  • /users, /assignments, /tools and /tools/:id all render with no Next error boundary — i.e. no Server Component throws from the moved code or the new change_history.source column.
  • Assign through the real dialog (cmdk user picker, two Radix selects, submit) creates the row with the cost snapshotted from the tier (1000¢), license_assignments.source = 'manual', and a change_history row with source = 'ui' — proving the Server Action wrapper still resolves requireAdmin() into a uiContext() and that revalidatePath ran (the row is on the page after reload).
  • Retier through the same dialog is the test that mattered most. assignLicense deactivates the existing active row and inserts a new one inside ONE transaction, now against a partial unique index on (user_id, tool_id) WHERE status='active'. It succeeds: exactly one active row at the new price (4000¢), the old row retained as inactive history. Had the index ordering interacted badly with that transaction, every licence upgrade in the app would have started failing with a 23505 — and no unit test would have shown it.
  • Tier price change via the Edit Tier dialog (whose input is in DOLLARS — displayed /100, submitted ×100) propagates: tier → 5500¢ and the held seat follows to 5500¢, with a per-seat costAtAssignmentCents audit row. The spec-037 propagation survives being routed through setTierPriceCore and the updateTier wrapper that splits price from metadata.
  • Fixtures torn down; the branch is back to 1,357,300¢ active spend, zero duplicate pairs, zero source='mcp' rows.

Incidental findings

  • This repo has no playwright.config.*, so playwright test runs on defaults — notably a 30s test timeout, which the first compile of a route on pnpm dev can exhaust on its own. The spec calls test.setTimeout(180_000) in beforeEach and documents why. Worth adding a real config eventually; out of scope here.
  • The spec is describe.configure({ mode: "serial" }) and the tests genuinely depend on each other (assign → retier → reprice mirrors how an admin works). Running a subset with -g fails on missing fixture state — that is the intended design, not a flake.

Not done

  • Nothing has touched production. Everything above ran against a Neon branch. Production still needs migrations 0030 and 0031 applied — in the same pnpm db:migrate run, never 0030 alone — and the same duplicate-remediation will run there — its effect on reported spend must be re-measured against production data, not assumed to be the same −$19.00.
  • MCP_WRITE_ENABLED is not set in any environment. The write tools are registered but refuse every call until it is, which is the intended staged-rollout posture.

Reconciliation with 042 + 044 (merge of origin/main, 2026-08-07)

While 043 was in review, main gained ea50404 (042, approvable tier changes on active licence assignments) and 7e94118 (044, connection-fault handling). 042 and 043 had independently built three overlapping abstractions. This is what each collapsed to, and why.

  • Tier-change semantics: 042's buildTierChange wins, and updateAssignmentCore now calls it. 043's inline tier branch was deleted. It had re-derived the cost re-snapshot but had no sync-managed refusal, so MCP's update_assignment could retier a Copilot seat and have the 06:00 cron silently revert it — the regression this merge existed to prevent. 042's race-guarded conditional UPDATE (WHERE id AND status='active' AND tierId=<read value>, zero rows → "changed while you were editing it") came across with it, so MCP now hard-fails a lost race instead of reporting a write that did not land. approveRequest remains a third caller of buildTierChange — it cannot route through the core because it writes inside its own transaction alongside licenseRequests, with the ApprovalError throw discipline and the RACE_LOST sentinel. That does not break the one-implementation rule: buildTierChange is the single implementation of the semantics, updateAssignmentCore of the assignment write.
  • Sync authority: 042's src/lib/assignments/sync-authority.ts is the only one. 043's isSyncOwnedTool / SYNC_OWNED_TOOL_NAMES (a hardcoded Set, name-only) were deleted. SYNC_OWNED_PRICE_MESSAGE survives — it is price-policy copy, distinct from SYNC_MANAGED_TIER_ERROR, which is seat-policy copy. setTierPriceCore uses the pure isSyncManagedToolName, deliberately not the async connection-gated variant: a price refusal that depends on the connection would let MCP reprice Copilot tiers during a momentary sync outage and get reverted the moment it came back. Narrowing accepted: 043's check was case-insensitive on a trimmed name, 042's is === "GitHub Copilot"; a differently-cased row would no longer be price-refused, but it would also not be sync-managed by the authority that drives the UI badge and both assignment-level refusals, so consistency across all five call sites beats the corner.
  • Two different sync policies, both kept. A per-seat tier change is refused for every caller, UI included — that is 042's shipped behaviour and caps-gating it would revert it. A tier price change stays caps-gated: main never removed the UI affordance for editing a Copilot tier price, so UI_CAPS.syncOwnedFields = true remains factually correct. The rows have different owners and different remediation ("change the plan in GitHub" vs "change it in GitHub billing").
  • Cache invalidation composes; the list and the transport split. New pure module src/lib/assignments/cost-paths.ts holds COST_SURFACE_PATHS and assignmentCostPaths() — the single definition. revalidate.ts keeps both exported function names and becomes a thin replayer over it, for Server Actions that do not go through a core (today only src/actions/license-requests.ts). CoreResult.revalidate stays the transport for everything that does. The cores never import revalidate.ts: it statically imports next/cache, which 043 deliberately keeps out of the MCP module graph. No write uses both transports.
  • One deliberate divergence from main's revalidate condition. Main busts the cost surfaces only when 'tierId' in changes. The merged core uses 'tierId' in changes || 'assignedAt' in changes, because assignedAt is the left edge of the seat's held-window — overlapsPeriod and the report/budget queries all filter on it, so backdating a seat moves its cost into earlier periods. Main leaves /, /budget and /reports/budget stale on a backdate; this does not. It is a fix, not a copy error — do not "restore" main's version.
  • MCP inherits a second sync refusal: revoke_license. revokeLicenseCore had no sync check at all, so an agent could revoke a Copilot seat, report a released cost, and have syncSeatAssignments reactivate the row at 06:00 with no audit trail. Now refused, caps-gated, so the UI is unchanged — it already withholds this itself (assignments-client hides Revoke on source='copilot-sync' rows). deactivateUserCore deliberately does not refuse — that would make deactivate_user unusable for most of the org — it returns a warning naming the sync-managed seats instead.
  • Audit writers: 043's src/lib/history.ts wins outright. 042 added one writer call site to src/actions/license-requests.ts, the one file 043 never touched; after the merge @/actions/history exports no recordUpdate, so this was a hard build break, not a style point. Migrated to the options-object signature with { tx, source: "ui" }. Every other writer importer on main was already migrated on this branch.
  • 042's tier timeline now shows provenance. getAssignmentTierHistory selected only the actor's name, so an MCP retier rendered identically to a human form edit — discarding exactly what migration 0031 was for. It now returns source and the detail page badges any entry whose source is not ui. Typed string, not ChangeSource: the column is a plain varchar, and the !== "ui" predicate stays correct (and fails toward showing provenance) for a value written before the union catches up.
  • 044 needed no code change here — nothing in 043 touches src/lib/db/index.ts, and no export on the db binding changed. Worth watching after deploy though: 044 raised the pool from max: 1 to 10 while setTierPriceCore holds FOR UPDATE locks on access_tiers and every active assignment for that tier. Genuinely concurrent repricing is reachable for the first time; the locks are correct and MAX_REPRICE_ROWS bounds the hold, but a slow reprice under load is the symptom to expect.

Follow-ups this merge deliberately did not take

  • The assign dialog's retier still writes two rows, and still double-counts the switch month. Re-submitting "Assign License" for a user who already holds the tool deactivates the old row and inserts a new one. Under 042's own no-proration argument, both rows are attributed to the period they span. This is pre-existing main behaviour, unchanged by the merge, and unreachable from MCP (caps.replaceAssignments = false refuses it and names update_assignment instead). Candidate spec 045: route the dialog to updateAssignment when the user already holds the tool. Changing it in a merge commit would also invalidate the partial unique index's reason to exist on that path, the capacity minus-1 rule, the inactive row that preserves the pre-change cost snapshot for closed periods, and the e2e assertions that pin all of it.
  • The same dialog also bypasses the sync-managed refusal entirely. assignLicense has no sync check on main either, so a Copilot seat can still be retiered through it in the UI. Also pre-existing, also unreachable from MCP — but it is now the only remaining way to retier a Copilot seat outside GitHub. If that is unacceptable it needs its own spec.
