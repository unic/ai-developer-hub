MCP Write Tools

The Hub's MCP server is read-only by construction (spec 034, 14 tools, every one annotated readOnlyHint). This spec gives an admin connected over OAuth the ability to act: create and update users, deactivate a leaver, assign / retier / revoke licenses, and manage access tiers including the org-wide price change. The write path is actor-parameterized — every mutation lands a change_history row attributed to the real human behind the token, identical to a UI edit.

Drafted 2026-08-04 · explored + designed by a 12-agent dynamic workflow (5 inventory · 3 design lenses · judge · 3 adversarial lenses), revised same day · author: T. Studer · branch: worktree-mcp-write-tools · builds on specs 034 / 038 / 039 · estimate: ~3–4 dev days

Two decisions taken without sign-off. The user was away when these were surfaced; both are called out here because both are cheap to reverse. (1) Writes require a new mcp:write scope, so every existing OAuth grant stays read-only until the human re-authorizes the connector once — chosen because src/app/oauth/authorize/page.tsx:108 currently promises the person clicking Allow “No write access.”, and shipping writes over that grant would make the consent screen a false statement. (2) create_user mints an invite token exactly as the UI does but returns only a pointer, never the /setup-password URL, so a live credential cannot land in a chat transcript.

1. Why the actor has to become a parameter

Every write in the app today lives in a "use server" action that gates on requireAdmin() — which reads the NextAuth session. An MCP caller has no session, and change_history.changedBy is integer NOT NULL REFERENCES users.id (schema.ts:405), so it needs a real user id.

The tempting shortcut is a security hole. Adding an optional ctx parameter to the existing server actions — assignLicense(input, ctx?) — would let any authenticated client invoke the action with a forged ctx claiming role: "admin", because every export of a "use server" file is a client-callable RPC endpoint whose arguments are attacker-controlled. The actor must therefore be injected in a module that is not "use server", with the action as a thin wrapper that derives the actor from the session itself.

So: business logic moves to src/lib/core/*.ts (plain modules) taking an explicit WriteContext. The existing server actions become session-deriving wrappers; the MCP tools become token-deriving wrappers. One implementation of each mutation, two callers. This is the same adapter relationship src/lib/mcp/data.ts already has to @/actions/budget. 

// src/lib/core/context.ts
export interface WriteCaps {
  /** May accept/return provisioned secrets. MCP: false. */
  secrets: boolean;
  /** May mint invite URLs / reveal credentials. MCP: false. */
  credentials: boolean;
  /** May target admin or agent rows, or change role/email. MCP: false. */
  privilegedTargets: boolean;
  /** May silently deactivate-and-replace an active assignment. MCP: false. */
  replaceAssignments: boolean;
}

export interface WriteContext {
  actorId: number;
  source: ChangeSource; // 'ui' | 'mcp' | 'sync' | 'ingest'
  caps: WriteCaps;
  /** Human-readable echoes the core verifies against the row it loaded. */
  expect?: { userEmail?: string; toolName?: string; tierName?: string; monthlyCostCents?: number };
  /** false = run every precondition + build the diff, then stop before any write. */
  commit: boolean;
}

caps is enforced inside the cores, next to the row they just loaded — not at the tool boundary. That way “MCP never touches a secret, never mints an invite URL, never promotes an admin” still holds for a tool someone adds later without reading this spec.

2. The write gate

One wrapper in src/lib/mcp/access.ts, structurally analogous to the existing adminOnly(), is the only way a write core is reachable from MCP. The conjunction is deliberate and has no fallback branch: 

writeGate(run) = (args, extra) => {
  // 1. Kill switch — read per request, NOT via the memoized env object,
  //    mirroring src/lib/mcp/auth.ts:38's process.env read.
  if (process.env.MCP_WRITE_ENABLED !== "1") return errorResult(WRITE_DISABLED_MESSAGE);

  const caller = callerFromAuthInfo(extra?.authInfo);

  // 2. Live role (re-read from users.role on every request by verifyAccessToken).
  if (caller.role !== "admin") return errorResult(ADMIN_REQUIRED_MESSAGE);

  // 3. Explicit write consent. The shared secret's scopes are the hardcoded
  //    [MCP_SCOPE] literal (auth.ts:52), so it fails here with no special case —
  //    an unbound credential can never attribute a write, so it must not write.
  if (!extra?.authInfo?.scopes?.includes(MCP_WRITE_SCOPE))
    return errorResult(WRITE_SCOPE_REQUIRED_MESSAGE);

  // 4. A bound identity is required — this is what makes the audit row real.
  if (typeof caller.userId !== "number") return errorResult(WRITE_NEEDS_BOUND_USER_MESSAGE);

  // 5. Defense in depth: agent rows are denied every operation
  //    BUILT_IN_DENY_PATHS forbids over HTTP (src/lib/agent-auth.ts:18-28).
  if (await isAgentUser(caller.userId)) return errorResult(AGENT_ACTOR_REFUSED_MESSAGE);

  return safeJsonResult(() => run(args, { actorId: caller.userId, source: "mcp", caps: MCP_CAPS, commit: ... }));
}
Why the shared secret stays read-only. MCP_SERVER_SECRET resolves to { role: "admin" } with no userId (auth.ts:52). Every write it performed would have to be attributed to SYSTEM_ADMIN_USER_ID — an innocent named admin who cannot repudiate it — and would be indistinguishable from a cron write. Steps 3 and 4 exclude it without a single branch dedicated to it. Headless write automation, if it is ever wanted, should get its own OAuth-bound service identity.

3. Tool surface (9 tools)

Nine write tools, covering exactly what was asked for: users, assignments, tiers. Every tool that accepts a numeric id must also accept a human-readable echo of that row, verified against the row the core loaded — a hallucinated or stale id is the single most likely failure mode on this surface.

Tool Echo guard Annotations Notes
create_user — destructive:false, idempotent:false Email must match MCP_WRITE_EMAIL_DOMAINS. Role forced viewer. Mints invite token like the UI; returns a pointer, never the URL.
update_user expectedEmail destructive:false, idempotent:true No email (takeover primitive), no role, no status. Refuses admin/agent targets.
deactivate_user expectedEmail destructive:true, idempotent:true Plan-token gated. Preview enumerates every license that will cascade-revoke. Refuses self, admins, and the last active admin. Deactivate only — see §8.
assign_license expectedUserEmail destructive:false, idempotent:false Refuses when the user already holds the tool (points at update_assignment) and when tool.requiresApiKey. Cost snapshotted from the tier, never from input.
update_assignment expectedUserEmail destructive:false, idempotent:true The tier-change tool. Re-snapshots cost from the new tier. Full calendar-date validation.
revoke_license expectedUserEmail destructive:true, idempotent:true Plan-token gated. Gains a Zod schema it lacks today.
create_access_tier expectedToolName destructive:false, idempotent:false Cents sanity guard in both directions.
update_access_tier expectedToolName + expectedTierName destructive:false, idempotent:true monthlyCostCents structurally absent — cannot propagate by accident.
set_tier_price expectedToolName + expectedTierName + expectedMonthlyCostCents destructive:true, idempotent:true Plan-token gated. The org-wide write — isolated so its preview can be loud. Refuses sync-owned tiers.
Why expectedTierName alone is not enough. Access-tier names are unique only per tool (access_tiers_tool_name_idx on (toolId, name)), and the real ones are generic words shared across tools: copilot-sync.ts:83-95 creates tiers literally named “Business” and “Enterprise” under GitHub Copilot. An agent told “set the Enterprise seat price to $60” can pick Copilot's Enterprise tier id instead of Claude's, pass expectedTierName: "Enterprise", and sail through — repricing every active Copilot seat. Hence the tool-name + tier-name + current-price triple.
Secrets are refused in the handler, not the schema. apiKey / licenseCode are declared as plain optional strings and rejected as the first statement inside the handler, before actor resolution and before any DB read. A z.refine(() => false) decoy would reject at the SDK's input-validation boundary — outside format.ts's controlled error formatting — so the repo could not assert that a submitted live key is absent from the response or the transport log. Both tool descriptions lead with “Never send an API key or license code to this tool” so the model reads it before composing the call.

4. Plan tokens

confirm: z.boolean() is not a guardrail against an LLM — the model satisfies it in the same turn it invents the call. The three destructive tools instead take an optional planToken: omit it to get a preview plus a token; call again passing the token back verbatim.

  • HMAC-SHA256 over the canonicalized resolved plan, keyed by hkdf(AUTH_SECRET, "mcp-plan-token-v1") — a derived key, so this new signing surface can never become an oracle on the session-cookie key. Verified with the existing safeEqual.
  • Payload carries iat with a hard 10-minute TTL and sub = clientId:userId, so a token cannot be lifted from a shared transcript weeks later and committed by a different credential.
  • Bound to the mutable state that matters (tierId + priceBefore), not to the affected-row id set — so a benign concurrent assignment does not force a pointless re-preview, while a concurrent price move still hard-fails.
  • Mismatch never echoes the expected value. The message is exactly “Call this tool again WITHOUT planToken to get a fresh preview and token.”
  • The token proves state-binding, not human review. In an auto-approving client, preview and commit are consecutive tool calls with no human turn between them. destructiveHint: true is what actually asks the human; the token is what stops a commit against state the agent never read.

commit: false short-circuits the core after every precondition and the full diff, but before any db.insert / db.update and before any record* call — which is what makes the preview provably write-free rather than write-free by inspection.

5. Schema changes (migrations 0030 + 0031)

Change Why
change_history.source varchar(20) NOT NULL DEFAULT 'ui', existing rows backfilled to 'ui' Distinguishes an agent-driven write from the same human's UI edit. Provenance is enforced at the type level: source is a required field on the history helpers' options object, so the compiler flags all ~19 existing call sites. Originally planned with no default — the argument being that a default silently labels any forgetful call site as a human edit, the exact forensic lie the column exists to prevent. Reversed during implementation: a NOT NULL column with no default is undeployable in either direction (migrate first → the live pre-043 code inserts without source and hits 23502; deploy first → the new code writes a column that does not exist yet). Migration 0031 therefore sets DEFAULT 'ui' purely for deploy safety; it only backstops a raw db.insert(changeHistory) that bypasses the helpers.
UNIQUE INDEX license_assignments_one_active_idx ON (user_id, tool_id) WHERE status = 'active' The plan asserts “at most one active assignment per (user, tool)” and nothing in the DB enforces it today. Replacing the UI's deactivate-and-replace with a read-then-refuse turns the TOCTOU window into duplicate active rows, which double-bill a seat in every aggregation. Same partial-unique pattern as invite_tokens_active_user_idx. Postgres 23505 on this index maps to the friendly refusal, so the guarantee comes from the DB rather than a pre-check — which also fixes the existing UI action and the license-request flow.

Migration must be generated with db:generate/db:migrate, not db:push — partial/expression indexes do not survive push diffing. It runs a duplicate pre-check first and ships the remediation SQL (keep max(id), mark the rest inactive). license_assignments.source already exists (varchar(50) default 'manual', schema.ts:273) so MCP-created assignments need no migration — they just write source: 'mcp'.

Each core returns its own revalidate path list rather than letting the wrapper guess: updateTier's invalidation set is conditional on whether the price actually changed (tools.ts:294-330), and a wrapper cannot reproduce that condition without being told. Getting it wrong serves /budget and /reports from cache computed off the old cost snapshots.

7. Challenge pass — what changed

A 3-lens adversarial panel (security & privilege · data integrity · LLM misuse) returned 29 findings against the judge's design; 4 were blockers. All were re-verified against the real code before acceptance. The revisions that changed the design:

  • Reactivation cut entirely. The design had set_user_status handling both directions. But deactivateUser never clears passwordHash and never revokes mcp_oauth_tokens, and auth.ts:51 gates login on status alone — so reactivation is a credential and session re-grant: an offboarded leaver's old password works immediately and their 60-day refresh tokens start returning 200 again. Reactivation belongs to a human in the UI, and it is a capability the Hub does not have today at all.
  • The capacity minus-1 branch stays. The judge wanted the “capacity-check-minus-one special case” deleted along with replace semantics. But copilot-sync.ts sets maxLicenses to the synced seat total, so Copilot sits routinely at exactly capacity, and that branch is what lets an admin retier an existing holder through the UI dialog. Deleting it from the shared core would regress the UI. It stays verbatim, gated on caps.replaceAssignments — unreachable from MCP, intact for the wrapper.
  • update_user loses email. resetUserPassword and sendInviteEmail both mail a fresh 72h token to the current users.email. Letting an agent rewrite that field is an account-takeover primitive that expectedEmail does not defend against at all — the echo matches, because the agent reads the correct current address straight out of find_users.
  • Sync-owned fields are refused. set_tier_price on a Copilot tier and update_ai_tool(maxLicenses) on the Copilot tool would report success and be silently reverted at 06:00 UTC by the cron, with zero audit rows. Both refuse with a message naming the sync as the owner. (This is why update_ai_tool is deferred — see §8.)
  • “Already in target state” is success, not error. Returning isError for a no-op contradicts idempotentHint: true and drives bad recoveries: after a transport timeout on a committed revoke_license, a retry answering “Error: Assignment is already inactive” reads as failure, and the model's plausible next move is deactivate_user — cascading a revoke across every license the person holds. The cores return a discriminated no-op the MCP adapter maps to a success payload; the UI wrapper keeps rendering today's error string, so UI behavior is unchanged.
  • set_tier_price is destructiveHint: true. The design said false because “no row is destroyed” — the wrong test. It irreversibly overwrites the cost snapshot on every active seat, and destructiveHint is precisely what makes an auto-approving client stop and ask the human.
  • The propagation row set comes from a locking read. Deriving the per-row audit entries from the preview's captured set would describe a different row set than the one the WHERE tier_id = $1 AND status = 'active' update actually rewrote, recording previousValues that were never in the rows. Commit re-reads SELECT ... FOR UPDATE inside the transaction and uses that set for the cap, the old values, and the audit inserts.
  • Cents guard is two-sided. The design only refused implausibly large values. Passing dollars-as-dollars (monthlyCostCents: 19 for a $19 seat) passes min(0) and understates that tool's spend 100× through the propagation path. Values in 1..99 are refused with both readings spelled out; 0 stays legal for free tiers.
  • A writeGate test partition, not just a name list. Today's exhaustiveness test only checks that a tool name is classified, so a write tool that forgets the gate would compile and pass. New it.each blocks assert, per write tool, that a viewer is refused with the core mock never invoked, that the kill switch refuses, that a missing scope refuses, that absent authInfo refuses, and that readOnlyHint === false — with the mirror assertion that every read tool's is true, so the two sets cannot blur.

8. Deferred & known limitations

  • Tool-catalogue writes (create_ai_tool, update_ai_tool, archive_ai_tool) are deferred. Adding rows to the AI-tool catalogue is a procurement act with no delete path, and update_ai_tool's only interesting field (maxLicenses) is cron-owned on the largest seat pool. create_access_tier works fine against existing tools, which is what “change tiers” actually needs.
  • User reactivation — deferred to the UI with a human owner, for the credential-re-grant reason in §7. If it is ever built, it must randomize passwordHash, set mustChangePassword, and revoke the user's OAuth token families in the same transaction.
  • copilot-sync.ts keeps its own copy of the tier-price propagation transaction (lines 103-121), writing zero change_history rows. Pointing it at the extracted core is the right follow-up, but it is not in this spec's blast radius. Stated plainly so the “one implementation of each mutation” claim is not overread: after this ships, the audited implementation is the one humans and agents call, and the unaudited one still runs nightly on cron. A change_history query filtered on source will therefore look complete while omitting the largest automated repricing event in the system.
  • The kill switch is not hot. MCP_WRITE_ENABLED is read per request rather than through the memoized env object, but a Vercel env-var change still does not reach warm instances until they recycle or a redeploy lands. The spec says “takes effect on redeploy / as instances recycle”, not “immediately”.
  • Deactivation deletes the record of what was held. The cascade writes per-assignment audit rows carrying a JSON snapshot (toolId/toolName/tierId/tierName/cost) so the set is at least reconstructible — but nothing restores it, and deactivate_user's response says so explicitly.
  • Tool count. 9 write + 14 read = 23 tools in one server. That is real per-session context cost for every client and raises mis-selection risk; it is the main argument for having deferred the catalogue tools.

9. Verification plan

  • Unit — tests/unit/mcp/write.test.ts: the gate partition described in §7; plan-token round-trip, tamper, TTL expiry and cross-credential rejection; secret-field refusal asserting the response text equals "Error: " + MCP_NO_SECRETS_MESSAGE and does not contain the submitted value; echo-mismatch refusals; the cents guard at 0 / 19 / 1900 / ceiling; no-op-as-success.
  • Unit — tests/unit/core/*: caps enforcement (MCP caps refuse admin targets, secrets, replace; UI caps at exactly maxLicenses still permits an existing holder's upgrade); each core's returned revalidate list.
  • Unit — tests/unit/actions/tier-cost-propagation.test.ts byte-identical and green after commit 1; upgraded in commit 2 to a { update, insert, select } tx stub asserting the audit inserts received the tx client and that the row set came from the locking select.
  • Integration — against a real DB: a reprice moves N active rows and leaves inactive ones untouched, writes N+1 change_history rows with source='mcp', and writes zero on rollback; the partial unique index rejects a concurrent duplicate active assignment with 23505.
  • Live MCP smoke test — against pnpm dev: a viewer token refused, an admin token without mcp:write refused, an admin token with the scope previewing and then committing a tier price change, and the resulting audit rows visible in /history.
  • pnpm typecheck · pnpm lint · pnpm test · pnpm test:integration. Never pnpm format repo-wide.
