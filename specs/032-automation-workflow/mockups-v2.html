Mockups v2 — profile+role mapping & copy-paste messages

Revision of the spec 032 license-request workflow after the direction changes of 2026-07-09: the ingest API no longer names a tool — it sends the requester's role and profile, and the Hub derives the tool from the AI Tooling Guide rules; the Microsoft Graph / Teams integration is postponed — every outbound message becomes a copy-paste-ready snippet; unknown requesters are auto-created as Hub users; and approving creates the assignment (with API key capture for key-based tools) — the separate Complete step is retired. Layout mockups for review, not pixel-perfect specs; visual polish follows the app's existing Nothing design at build time.

2026-07-09 · branch: worktree-request-workflow · companion to mockups.html (v1) · author: Claude (Fable 5)

00The mapping rules (from the AI Tooling Guide)

The Microsoft Form now always sends role ∈ development | conception | business and profile ∈ empty (= baseline) | maxed | indie. The Hub owns this table — seeded from the guide, editable in Settings (§05), never hardcoded.

RoleProfileDerived toolDefault tierResolution

Decisions baked into these mockups: the tool/tier decision is always the approver's; Maxed defaults to Standard; Boost is retired (not in the table); the derived tool is a proposal — the approver can override any row's result on the request itself before approving.
New in this iteration (2nd + 3rd review round): approving creates the license assignment in one action — you provision in the vendor UI first, then Approve records the result; the separate Complete step is retired (§06); unknown requesters are auto-created as Hub users at approval (viewer, no invite) — never from rejected requests (§03, §06); API-key tools require the key at approval, stored encrypted, woven into the copyable message (§06); justification is a first-class field (§01, §03). Status flow simplifies to pending_review → approved | rejected | cancelled.

01Ingest contract — before / after

POST /api/license-requests/ingest keeps its bearer auth, idempotency, and Teams thread IDs. The tool fields go away removed; role + profile come in as first-class fields. Form answers arrive as formPayload with labeled questions (Power Automate maps question text, not field-ID hashes — kills the hash-key display problem at the root).

  • 2The Hub resolves the mapping at ingest time and stores both the inputs (role, profile) and the derived result (derived_tool_id, nullable for indie) — so later mapping edits don't silently rewrite history.
  • 3Existing rows (REQ-001) keep working: role/profile are nullable, old requests display their stored tool as before.
  • 4Unknown requesters: ingest still only email-matches (unchanged) — the user is created at approval, not here, so rejected or cancelled requests never leave orphan users behind (§06). Until then the request carries name + email as plain fields.
  • 5Justification is first-class. The Form has separate justification fields per profile (one for maxed add-ons, a separate one for indie); Power Automate maps the profile-appropriate field into the single justification property. Ingest requires it when profile is set, rejects with 422 when missing.

08Out of scope, migration & open questions

  • Dormant, not deleted: Microsoft Graph helper, retry logic, adaptive card, teams_* columns — kept for the future stack migration; all UI references to auto-posting removed.
  • Retired: the Complete dialog and the completed status — approval now creates the assignment (§06). The enum value and completion_message_md stay in the schema for history; the UI treats approved (with assignment) and legacy completed as equivalent terminal happy states. The queue's default facet becomes pending review only (approved is terminal now), and the stats row drops “approved — awaiting procurement”.
  • Migration — REQ-001: approved under v1 semantics, so it has no assignment. Legacy approved rows without an assignment_id show one action: “Record assignment” — step 1 of the approve dialog alone (tier, date, key), no re-approval, no message required.
  • Also in this round (from the audit, not mocked): seed default approval templates per tool (incl. an API-key variant for Claude Console); queue search fix; sidebar pending-count badge; integration tests for ingest + actions.
  • Decided (3rd round): provision-first approval (vendor UI before Approve — the message never lies about access being ready); user creation at approval only, viewer, no invite (invite later via the existing flow if ever needed); justification first-class, required at ingest when a profile is set, sourced from profile-specific Form fields mapped by Power Automate; the detail page shows the requester's existing active assignments as add-on review context (§03).
  • To verify during implementation: the discipline enum accommodates development/conception/business for auto-created users; GitHub Copilot member sync treats request-created users (no GitHub username) as unmatched rather than erroring.
